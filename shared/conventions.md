# Конвенции vassal-litigator

## Расположение документов

**Правило:** Все выходные документы, предназначенные для Сюзерена (юриста), сохраняются в корневой папке дела (CASE ROOT). Папка `.vassal/` зарезервирована исключительно для внутренних агентских файлов и не должна быть доступна пользователю.

Все файлы и папки в корне дела начинаются с даты `ГГГГ-ММ-ДД`.

Примеры:
- Предварительный анализ: `{case-root}/2026-03-26 Предварительный анализ документов.md`
- Позиция по делу: `{case-root}/2026-03-26 Начальная позиция.md`
- Процессуальные документы: `{case-root}/2026-04-01 Истец - исковое заявление/`

Внутренние агентские файлы (которые агент читает, но не показывает Сюзерену):
- `.vassal/case.yaml` — карточка дела
- `.vassal/index.yaml` — реестр документов
- `.vassal/mirrors/` — md-зеркала документов
- `.vassal/analysis/{qualification.md, deadlines.md, ...}` — аналитические блоки (для переиспользования между скиллами)
- `.vassal/history.md` — история действий агента
- `.vassal/raw/` — оригиналы загруженных документов

## Именование файлов

Формат: `ГГГГ-ММ-ДД Отправитель Описание.расширение`

**Область применения:** правило касается **документов сторон** — материалов, поступивших от клиента, оппонента, суда или из публичных источников. Имена внутренних продуктов плагина (анализ, позиции, проекты процессуальных документов) формируются по отдельным шаблонам — см. раздел «Продукты плагина» ниже.

Правила:
- Дата — дата документа (не дата создания файла), формат строго `ГГГГ-ММ-ДД`
- Отправитель — организация или лицо, без кавычек: `ООО «Ромашка»` → `ООО Ромашка`
- Описание — тип документа и/или суть. Номер документа, если есть
- Расширение — никогда не менять
- Кодировка — UTF-8, кириллица
- Если дата неизвестна → `0000-00-00`
- Если отправитель неизвестен → `Неизвестный`
- Дубликат имени → суффикс `(2)`, `(3)` и т.д.

## Именование процессуальных папок

Формат: `{ГГГГ-ММ-ДД} {Сторона} - {действие}`

**`{действие}` — это тип процессуального документа** («исковое заявление», «отзыв на иск»,
«ходатайство об отложении»); если папка объединяет несколько документов по одному поводу —
назначение папки («к судебному заседанию»). Термин фиксируется здесь явно: `add-opponent`
называл третий сегмент двумя способами — `{тип документа}` в одном месте и `{действие}` в
другом (F.17).

Примеры:
- `2026-03-01 Истец - исковое заявление`
- `2026-03-15 Ответчик - отзыв на иск`
- `2026-04-10 к судебному заседанию` (без стороны — общее)

**Несколько самостоятельных документов одной стороны одной датой (F.17).** Одна папка на
**каждый** самостоятельный акт; различаются третьим сегментом — типом документа:
- `2026-04-10 Ответчик - ходатайство об отложении`
- `2026-04-10 Ответчик - отзыв на иск`

Критерий «бандл или самостоятельные акты» — [skills/add-opponent/SKILL.md](../skills/add-opponent/SKILL.md)
(шаг 6): у бандла **один** основной документ, остальные перечислены в его приложениях; у
самостоятельных актов — своя просительная часть и своя подпись у каждого, и ни один не назван
приложением другого.

**Полное совпадение имени** (та же дата, та же сторона, тот же тип документа — два ходатайства
об отложении за один день либо повторный прогон приёма) → суффикс времени `-{ЧЧММ}` после даты,
как у продуктов плагина: `2026-04-10-1435 Ответчик - ходатайство об отложении`. Суффикс `(2)`
для процессуальных папок не используем: он ничего не говорит о содержимом и даёт случайный
порядок.

## Папка «Входящие документы/»

Единая точка входа для всех новых файлов в деле. Создаётся при `init-case`.

Правила:
- Пользователь кладёт сюда любые файлы, которые нужно обработать
- Команды `intake`, `add-evidence`, `add-opponent` берут файлы **только** отсюда, применяя **триаж по источнику** (см. «Маршрутизация приёма по источнику» ниже): каждый скилл обрабатывает свои файлы, «чужие» предлагает оформить нужным скиллом, а не поглощает вслепую
- Область можно ограничить подпапкой или списком файлов аргументом (напр. `/intake Входящие документы/от-клиента/`); без аргумента — вся папка + триаж
- После успешной обработки файлы из «Входящие документы/» **перемещаются в папку «На удаление/»** (пристинные оригиналы opponent/court — в `.vassal/raw/`)

### Папка пуста — единое поведение трёх приёмников (F.15)

Прежняя формулировка («сообщает об этом и завершается») точно описывала только `add-opponent`. Фактически три скилла вели себя **по-разному**, и расхождение нигде не оговаривалось: `intake` смотрел наружу и предлагал обработать найденное, `add-evidence` смотрел в `history.md` и объяснял, куда делись файлы, `add-opponent` просто завершался. Каждый делал треть полезной работы.

**Единая последовательность — обязательна для `intake`, `add-evidence`, `add-opponent`:**

1. **Посмотреть наружу.** Есть ли необработанные файлы в корне дела или в папках, принесённых Сюзереном (вне «Входящие»)? Есть → «Во „Входящие документы/" пусто, но в {место} есть N необработанных файлов — обработать их?». Это **единственная** санкционированная точка приёма файлов не из «Входящие»; работает через тот же механизм области (список файлов).
2. **Посмотреть в `.vassal/history.md`.** Не приобщил ли файлы недавно другой скилл, очистив «Входящие»? Приобщил → «Последнее приобщение: {что / когда / каким скиллом}, файлы уже в деле как `doc-NNN`». Это снимает типовое «я же клал файлы, куда они делись».
3. **Дело уже разложено вручную?** Если в корне видна собственная организация Сюзерена (процессуальные папки, свои имена) и файлы не в индексе — предложить **`update-index`**: он проиндексирует разложенное **на месте**, ничего не переименовывая (см. `skills/update-index/SKILL.md` → «Индексация уже разложенного дела»). Не гнать такие файлы через «Входящие»: приёмник переименует их по своей конвенции и разрушит организацию, которую юрист уже построил.
4. Ничего из перечисленного → «Папка „Входящие документы/" пуста. Положите туда файлы и запустите `{скилл}` снова.»

Триаж по источнику (ниже) применяется к найденному на шаге 1 точно так же, как к содержимому «Входящих»: `intake`, нашедший в корне отзыв ответчика, предлагает `add-opponent`, а не поглощает его.

## Маршрутизация приёма по источнику (source triage)

**Зачем:** три приёмных скилла (`intake`, `add-evidence`, `add-opponent`) читают одну «Входящие документы/». Без разбора источника один скилл поглотит документы другого: запустив `intake` на пачке с отзывом ответчика, пометишь отзыв `source: client`, заведёшь записи и уведёшь оригинал в «На удаление/» — до `add-opponent`, без пристинной копии (chain of custody потерян). Триаж этого не допускает.

**Кто обязан выполнять:** `intake`, `add-evidence`, `add-opponent` — перед Preview. Отдельного чтения не требует: содержимое уже прочитано на этапе извлечения текста / категоризации, где скилл и так определяет отправителя.

### Классификация источника (по содержимому)

Для каждого файла определи класс, сверяя отправителя/подписанта с `case.yaml.parties[]` (кто `our_client`, кто оппонент) и тип документа:

| Класс | Сигналы | Владелец-скилл |
|---|---|---|
| `client` | отправитель = наш клиент ИЛИ контрагент в отношениях с клиентом (договоры, платёжки, переписка) ИЛИ собственный процессуальный черновик клиента | `intake`, `add-evidence` |
| `opponent` | отправитель/подписант = оппонент (роль ответчик / истец-оппонент / третье лицо на его стороне) ИЛИ процдокумент за подписью оппонента (отзыв, возражение, встречный иск, пояснения) | `add-opponent` (`source: opponent`) |
| `court` | тип ∈ {определение, решение, постановление, судебное извещение, протокол-заседания} + реквизиты суда (шапка «Арбитражный суд …», «Именем Российской Федерации», печать суда) | `add-opponent` (`source: court`, без экспресс-анализа оппонента) |
| `ally` | отправитель/подписант = **процессуальный союзник на нашей стороне** (соответчик / соистец / третье лицо на нашей стороне по `case.yaml.parties[]`; напр. отзыв АУ при защите СРО) (E.9) | `add-opponent` (`source: ally`, пристинная копия, **без** опп-анализа) |
| `own-work` | **собственная аналитика/наработка юриста** — памятка, справка, черновик позиции нашей команды (не от стороны спора) (E.9) | `intake` (`source: own-work`, без пристинной копии) |
| `unclear` | сторону не определить (голый скан без реквизитов; документ третьего лица без явной привязки) | спросить Сюзерена |

### Поведение

1. **Свои файлы** (класс = владелец текущего скилла) → обрабатываются штатно.
2. **Чужие файлы** (класс ≠ владелец) → **не обрабатывать**; в Preview показать отдельным списком и **предложить**: «N файлов похожи на документы {оппонента / суда / клиента} — оформить их через `{нужный скилл}` сейчас?»
   - **Да** → сначала доделать **свою** часть (свои файлы → apply → «На удаление/»), затем **передать управление** нужному скиллу, ограниченному этими файлами (область = список файлов, см. ниже). К моменту передачи во «Входящие» остаются только чужие файлы.
   - **Нет** → чужие файлы **оставить во «Входящие»** + сообщить «оформите через `{нужный скилл}`». Ничего чужого не трогать, оригиналы не двигать.
3. **`unclear`** → спросить Сюзерена, к какому источнику отнести (или отложить файл до выяснения).

Симметрично: `intake` / `add-evidence` предлагают `add-opponent` для opponent/court; `add-opponent` предлагает `intake` / `add-evidence` для client. Крайний случай — **вся пачка чужая** (запустили `intake` на чисто-оппонентской пачке): своих 0 → Preview «клиентских документов нет; все N похожи на оппонента — оформить через `add-opponent`?»; при согласии полный handoff, текущий скилл сам ничего не пишет.

### Вторая ось: принадлежность документа делу (F.19)

**Зачем.** Триаж выше классифицирует файл по **отношению отправителя к сторонам** — то есть
отвечает на вопрос «чей это документ». Вопрос «а **этого ли дела** документ» не задаётся вовсе:
ни `case.number`, ни ИНН, ни предмет спора в сверку не входят. Поэтому документ из **соседнего
дела**, подписанный тем же клиентом, проходит как совершенно легитимный `client`.

Боевые случаи по обе стороны: в одном деле агент поймал 16 чужих документов (дело ФСИН, номер
отличался одной цифрой), в другом — не поймал; а в третьем, наоборот, **выбросил как чужие** две
аналитические справки, которые оказались ключевым материалом — именно они вскрыли ошибку по
подсудности. Отсюда формулировка правила: **флаг и вопрос, никогда не молчаливый отсев.**

**Что сверяется** — по уже извлечённому тексту, отдельного чтения не требует:

| Сигнал | Источник в карточке | Как читать |
|---|---|---|
| № дела в шапке/тексте | `case.number` | другой номер — сильнейший сигнал; отличие в одну цифру это **не** совпадение, а типовой случай |
| ИНН / ОГРН | `parties[].inn`, `.ogrn` | реквизит, которого нет ни у одной стороны дела |
| Наименования сторон | `parties[].name`, `.short_name` | ни одна сторона дела в документе не упомянута |
| Суд | `case.court` | другой суд при наличии № дела |
| Машинный | `composite_suspected` / `composite_reasons` | множественные ИНН в одном PDF (см. ниже) |

**Срабатывание — только по положительному противоречию.** Флаг поднимается, когда в документе
**есть реквизит, прямо противоречащий карточке**. **Отсутствие реквизитов — не сигнал:** у памятки,
справки, черновика, фотографии шапки с реквизитами не бывает по природе, и это норма, а не «чужое».
Ровно на этом сгорели две аналитические справки. Документы `source: own-work` (собственная
аналитика юриста) под сверку принадлежности **не попадают вовсе**.

**Поведение:**

1. Противоречий нет → штатная обработка, ничего не пишем.
2. Противоречие есть → файл **не отбраковывается и не двигается**. В Preview — отдельный блок:
   «⚠ N файлов, возможно, из другого дела: {файл} — в тексте № А40-…, в карточке дела А33-…» и
   вопрос Сюзерену: **обработать всё равно · оставить во «Входящие» · это документ другого дела**.
   При «обработать» — обрабатываем штатно и оставляем след: строка в EXTRACTION NOTES зеркала
   («реквизиты другого дела: {что}; приобщено по решению Сюзерена от {дата}»).
3. Ответа нет (неинтерактивный прогон) → файл остаётся во «Входящие» с пометкой. Это уже
   действующий консервативный дефолт: «На удаление/» наполняется **только** успешно обработанными
   файлами. Отдельного маршрута «отбраковать содержательно чужой файл» в конвенциях нет —
   и заводить его не нужно, нужен только сигнал.

**Машинный сигнал `composite_suspected` — замкнуть цепочку.** `extract_text.py` собирает ИНН из
PDF, но самостоятельным триггером они не являются (лишь вспомогательная причина при уже сработавшем
«повтор заголовка-якоря»), а сам флаг ведёт к предложению **split**, не к сверке принадлежности.
Поэтому: при `composite_suspected: true` каждая часть — после split или после отказа от него —
проходит сверку принадлежности **отдельно**; именно там всплывает «чужой платёж на 2-й странице».
Флаг обязаны обрабатывать **все три** приёмника, а не только `intake`.

**Образец поведения уже есть** — E.6.1 «плательщик ≠ клиент» в `intake`: флаг в Preview + строка в
EXTRACTION NOTES, без `needs_manual_review` и без блокировки. F.19 устроен так же: это флаг
**происхождения документа**, а не качества извлечения и не правовая оценка относимости
(та — `legal-review` / `study-evidence`).

**Кто обязан выполнять:** `intake`, `add-evidence`, `add-opponent` — вместе с триажем источника,
перед Preview.

### Область (scope) — опция

Приёмник принимает необязательную область из `$ARGUMENTS`:
- **подпапка** «Входящие документы/{подпапка}/» → только файлы под ней;
- **список файлов** → только они (этим же механизмом идёт handoff: скилл A передаёт скиллу B список чужих файлов);
- **не задано** → вся «Входящие документы/» + триаж (дефолт).

Даже при заданной области триаж всё равно прогоняется (защита от «в подпапке от-клиента случайно лежит отзыв»), но по умолчанию файлы там считаются своими.

**Низкий риск ложных срабатываний:** на первом `intake` «Входящие» — обычно всё клиентское (иск, договоры), оппонент ещё не ответил; стороны в `case.yaml` уже заданы `init-case`. Триаж «выстреливает» позже — когда приходят документы оппонента/суда.

## Папка «На удаление/»

Корзина для файлов, подлежащих удалению. Создаётся при `init-case`.

**Зачем:** `rm` на маунте Cowork недостоверен — возвращает rc=0 без фактического удаления либо `Operation not permitted`. Вместо удаления все ненужные файлы **перемещаются** (`mv`) в эту папку.

Правила:
- Все команды плагина, которым нужно «удалить» файл, **перемещают его в `На удаление/`** через `mv` вместо удаления
- Структура внутри — плоская, при совпадении имён добавляется суффикс `(2)`, `(3)`
- Пользователь периодически очищает эту папку вручную (на своей стороне, вне Cowork)
- Агент **не удаляет** файлы из «На удаление/» — только кладёт туда

Техническая реализация «перемещения»:
```bash
# Переместить в «На удаление/» (mv на маунте работает надёжно)
mv "Входящие документы/файл.pdf" "На удаление/файл.pdf"
```
`mv` заменяет прежнюю технику `cp` + обнуление (`: >`): обнуление оставляло 0-байтные «пустышки» в рабочих папках, тогда как `mv` переносит файл начисто. Подробнее — раздел «Cowork-first robustness» → операционные следствия.

### Каталоги — тот же маршрут (F.16)

Всё описанное выше написано про **файлы**; для каталога маршрута не существовало даже на уровне
конвенции. Он такой же:

```bash
mv "Материалы от клиента/Экспертиза" "На удаление/Экспертиза"
```

- Переносится **только фактически пустой** каталог — либо содержащий исключительно системный
  мусор (`.DS_Store`, `Thumbs.db`, `desktop.ini`). Каталог с содержимым не переносится
  **никогда**, ни целиком, ни рекурсивно: одно `mv` папки с материалами унесёт документы дела
  целиком и незаметно.
- Совпало имя в «На удаление/» → суффикс `(2)`, `(3)`, как у файлов.
- `rmdir` не используем по той же причине, что и `rm`: код возврата на маунте недостоверен.

## Уборка опустевших папок (F.16)

**Что происходит без правила.** `intake` обрабатывает «Входящие документы/» рекурсивно, но уводит
в «На удаление/» **только файлы** — вложенные папки остаются пустыми. Так набегают боевые «5 пустых
папок из 19»: отработанные подпапки «Входящих», опустевшие подпапки «Материалов», слоты, которые
так и не наполнились.

**Хозяин уборки — `update-index`** (решение Сюзерена 2026-07-19). Он единственный и так сканирует
всю ФС дела и уже умеет переносить в «На удаление/»; «каждый скилл за собой» продублировал бы
правило в четырёх местах, и оно разъехалось бы на первой же правке.

**Правила:**

1. **Кандидат — только фактически пустой каталог** (с оговоркой про системный мусор выше).
2. **Перенос — только с подтверждением Сюзерена**, отдельным блоком Preview. Пустая папка часто
   бывает **заготовкой под будущие материалы** («Экспертиза/» заведена заранее, документы ещё не
   пришли) — молча уносить её нельзя.
3. **Не трогаем никогда:** корень дела; штатные папки `init-case` («Входящие документы/»,
   «На удаление/», «Материалы от клиента/» верхнего уровня); «На подачу/»; `Архив/`; всё
   внутри `.vassal/`.
4. **`.vassal/` живёт по своим правилам.** Унаследованную пустую `.vassal/positions/` `init-case`
   намеренно **игнорирует**, а не убирает — противоречия с настоящим правилом нет: оно про рабочие
   папки дела, которые видит юрист. Служебные временные артефакты процесса убираются отдельным
   постусловием ingest-скиллов («Уборка временных артефактов скилла»).
5. Пустые каталоги, оставшиеся следом текущего прогона (подпапка «Входящих», опустевшая после
   `intake`), предлагаются к уборке при ближайшем `update-index` — отдельного вызова после каждого
   приёма не требуется.

## Папка «На подачу/»

Staging-зона для комплектов документов, готовых к подаче в суд. Создаётся скиллом `build-submission` лениво (не в `init-case`). **Контейнер:** каждая подача — отдельный датированный подкаталог `{ГГГГ-ММ-ДД} {Сторона} - {действие}/` (как процессуальные папки), внутри — нумерованный комплект.

Правила:
- **Самоописывающие имена файлов:** `NN Наименование от ГГГГ-ММ-ДД Nл.ext` (`00` = сам документ, `01..NN` = приложения в порядке перечня; `Nл` — листаж из зеркала). Отдельный файл-опись не создаётся — папка с такими именами и есть опись. Детали — `skills/build-submission/SKILL.md`.
- **Staging, не архив:** держит готовые-но-не-поданные комплекты. Канонический экземпляр поданного остаётся в деле (продукт в корне + `intake` входящего судебного акта). После подачи подкаталог отработан → Сюзерен чистит вручную (как «На удаление/»); агент сам из «На подачу/» не удаляет.
- **В игнор-списках сканирования** (Phase 0, `update-index`) — копии в комплекте не должны всплывать как «новые файлы» или дубли индекса.
- Машинно-читаемый манифест каждой подачи — `.vassal/submissions/{ГГГГ-ММ-ДД}-{действие}.md` (источник истины о составе: `main_doc` + `refs:[doc-NNN]` + результат кросс-проверок «заявлено vs вложено»).

## Таксономия типов документов

Значения поля `type` в index.yaml:

**Договорные:** договор, дополнительное-соглашение, приложение-к-договору, спецификация, акт, накладная, счёт, счёт-фактура

**Переписка:** претензия, ответ-на-претензию, уведомление, письмо, требование

**Процессуальные:** исковое-заявление, отзыв-на-иск, ходатайство, заявление, возражение, пояснения, дополнение-к-позиции, апелляционная-жалоба, кассационная-жалоба, мировое-соглашение, ходатайство-об-утверждении-мирового, заявление-об-отказе-от-иска, заявление-о-признании-иска

**Судебные:** определение, решение, постановление, протокол-заседания

**Платёжные:** платёжное-поручение, выписка, справка-из-банка

**Корпоративные (F.18):** протокол-общего-собрания, решение-единственного-участника, бюллетень-для-голосования, реестр-акционеров, выписка-из-реестра-акционеров, список-участников-общества

**Прочие:** доверенность, выписка-из-егрюл, устав, свидетельство, заключение-эксперта, иной-документ

> **Почему группа заведена отдельно (F.18).** Категория дела «корпоративный спор» поддержана
> (`case-schema.yaml`), а специфичных для неё классов документов в таксономии не было вовсе — из-за
> чего не работала привязка защиты к классу (см. «Решающие документы: вторая голова»). Соседние
> значения означают **другое** и не годятся как замена: `выписка` в группе «Платёжные» — банковская,
> `протокол-заседания` в «Судебных» — судебного заседания, а не общего собрания участников.

## Источники документов

Значения поля `source` в index.yaml:
- `client` — получено от нашего клиента
- `opponent` — получено от процессуального оппонента
- `court` — получено из суда
- `public` — из публичных источников

## Пользовательская конвенция имён (E.9, зона действия уточнена в F.14)

У Сюзерена может быть собственный стандарт имён — например `Тип_о чём_ДДММГГГГ_на Nл.docx`. Он задаётся в **user `CLAUDE.md`** и **переопределяет** дефолты плагина, но **не везде**:

| Зона | Дефолт плагина | Пользовательская конвенция |
|---|---|---|
| **Входящие документы сторон** | `ГГГГ-ММ-ДД Отправитель Описание.расш` (см. `intake` → «Формат имени файла») | **применяется** |
| **Финальный `.docx`** — то, что уходит Сюзерену и в суд | `{имя исходного .md}.docx` | **применяется** (F.14) |
| Продукты плагина в `.md` (аналитика, позиции, подаваемые тексты) | `ГГГГ-ММ-ДД {Тип продукта}.md` | **не применяется**: на этих именах держатся автодетект типа артефакта, архивация (F.12) и обратные ссылки |
| Служебная зона `.vassal/` | шаблоны из «Продукты плагина» | **не применяется** |
| Комплект внутри «На подачу/» | `NN Наименование от ГГГГ-ММ-ДД Nл.ext` | **не применяется**: самоописывающие имена там и есть опись комплекта |

Дата в имени — ISO `ГГГГ-ММ-ДД`, если пользовательская конвенция не диктует иное.

**Кто обязан её прочитать — раньше не читал никто (F.14).** Правило было **декларацией без потребителя**: `CLAUDE.md` упоминался во всём плагине ровно один раз — в самом этом правиле, и ни один скилл не содержал шага «прочитать пользовательскую конвенцию». То есть боль Сюзерена («мой стандарт — `Тип_о чём_ДДММГГГГ_на Nл`») не была закрыта вообще ничем. Обязаны читать:

- `intake` / `add-evidence` / `add-opponent` — на шаге формирования имени входящего файла;
- `format-doc` — в Фазе 0, перед выбором имени выхода (см. [skills/format-doc/SKILL.md](../skills/format-doc/SKILL.md) → «Имя и каталог выхода»).

**Конвенции нет, `CLAUDE.md` отсутствует или не читается** → тихо работать по дефолту: не спрашивать, не предупреждать, не падать.

## Решающие документы: вторая голова (F.18)

**Проблема.** Приём читает документ Haiku-субагентом — и он же оценивает качество собственного
чтения (`quality`, `needs_manual_review`, пер-полевой confidence). Петля самооценки замкнута:
уверенно и неверно прочитанная цифра флага не поднимает. Внутридокументная контрольная сумма
«разбивка = итог» (`shared/ocr.md` §3.1 п.3) спасает платёжку и расчёт, но в выписке из реестра
акционеров или в бюллетене такой пары нет вовсе. Боевой случай: доля прочитана как «100 %,
единственный акционер» вместо 15 % — переворачивало конструкцию корпоративного спора.

**Решение (развилка F.18, решение Сюзерена 2026-07-19):** класс документа как **автоматический
пол**, ручная пометка — как **потолок** для нетипичных документов. В обоих случаях суть одна:
**критичные поля сверяют две независимые головы, а не одна себя.**

### Что считается решающим документом

**1. По классу** (автоматически). Закрытый список:

`реестр-акционеров` · `выписка-из-реестра-акционеров` · `бюллетень-для-голосования` ·
`протокол-общего-собрания` · `решение-единственного-участника` · `список-участников-общества` ·
`выписка-из-егрюл` · `заключение-эксперта`

Критерий включения в список (по нему список и расширяется): **цифра документа сама определяет
исход, а внутридокументной контрольной суммы «разбивка + итог» в нём нет.** Платёжка и расчёт
неустойки в список не входят именно потому, что там контрольная сумма есть и работает.

**2. По пометке Сюзерена** (вручную). Любой документ, помеченный решающим:
- аргументом при запуске приёма (`решающие: <файл>, <файл>`), либо
- ответом на вопрос скилла в Preview («есть ли в пакете документы, на цифрах которых держится
  позиция?»).

Пометка сохраняется в записи индекса (`decisive: true`, `decisive_reason: manual | class`) —
чтобы её видели повторный прогон и нижестоящие скиллы, а не только текущая сессия.

### Что делает приём

Протокол чтения (какая голова что получает, как сверяется, что пишется в зеркало) — целиком в
[`shared/ocr.md` §3.2](ocr.md); третья, немодельная нога — `--spot-check` там же §6. Ключевое
условие независимости: **вторая голова не получает транскрипцию первой**, а сверку выполняет
оркестратор сопоставлением значений — не вопросом модели «согласна ли ты».

**Вторая голова — только там, где цифру прочитала модель.** Документ с текстовым слоем
(`pdf-text` / `docx-parse` / `text-read`) проверяется **машинной** сверкой: значение в зеркале
обязано буквально встречаться в тексте, извлечённом программно. Гонять по нему Opus значит
заменить точную проверку ещё одним модельным чтением — то есть ослабить её. Разбивка по методам
и гибридный случай — в `ocr.md` §3.2.

### Поведение — флаг, не блок

Расхождение приём не останавливает: документ индексируется, помечено **поле** (не документ),
Сюзерен видит строку в Preview и в EXTRACTION NOTES с **обоими** прочтениями. Ограничение
наступает дальше по конвейеру: `needs_manual_review` не даёт цитировать этот реквизит дословно
в подаваемом документе (verify-before-assert правило 4). То есть не «нельзя работать», а
«нельзя утверждать непроверенное».

**Чего правило не делает:** не оценивает правовое значение документа (это `legal-review` /
`build-position`) и не решает, какое из двух прочтений верное — это решает Сюзерен по оригиналу.

**Зона действия:** `intake`, `add-evidence`, `add-opponent`, `update-index` (при пересоздании
зеркала решающего документа второе чтение прогоняется заново — иначе `verified_fields` устареет
молча).

## Принцип Preview → Apply

Все команды, изменяющие файлы или данные дела, работают в два шага:
1. **Preview** — показать план изменений Сюзерену
2. **Apply** — выполнить только после подтверждения

Касается: intake, add-evidence, add-opponent, update-index (при удалении), обновлений case.yaml.

**Версионирование продуктов с пересчётом:** для аналитических продуктов (`legal-review`, `build-position`) при повторном запуске создаётся **новый файл с новой датой**, старый сохраняется. Это даёт хронологию мысли по делу. Перезапись запрещена.

> **«Перезапись запрещена» — три разные политики, не одна (F.14).** Формулировка встречается в трёх местах и означает в них **разное**; смешение даёт боевое «три редакции × три файла = девять».
>
> | Политика | Где действует | Что происходит при повторе |
> |---|---|---|
> | **Новый датированный файл** | датированные продукты: аналитика, подаваемые `.md`, проекты | пишется новый файл с новой датой; предыдущий снимок того же типа уезжает в `Архив/` (см. «Актуальное состояние продукта и папка `Архив/`») |
> | **`_v2` при занятом целевом** | `.docx` любого продукта | целевой файл **заблокирован** (открыт в Word / OneDrive-лок) → пишем `{имя} _v2.docx`. Это реакция на **техническую невозможность записи**, а не способ версионирования: при свободном целевом `.docx` пишется штатно под своим именем |
> | **Штатная перезапись** | недатированные живые артефакты: `Таблица документов.xlsx`, `.vassal/analysis/evidence-dossier.md`, `judge-profile.md`, `retractions.md` | файл один и всегда актуален; перезапись (или аппенд) — штатный режим, версий не бывает |
>
> `_v2` появляется **не от правки текста**, а только от занятого файла — правка текста порождает новую дату, а не `_v2`.
> **Эскалация `_v2` (её не было нигде):** занят и `_v2` → `_v3`, `_v4` и далее по возрастанию; на `_v9` — остановиться и сказать Сюзерену «закройте открытые копии документа», а не плодить дальше.

**Коллизия имён в один день.** Единое правило для всего плагина (F.14) — суффикс зависит от того, **кто порождает имя**:

| Что | Суффикс | Почему |
|---|---|---|
| **Продукты плагина** и **процессуальные папки** | `-{ЧЧММ}` после даты: `2026-04-25-1430 Обновлённая позиция.md` | имя порождает прогон плагина: время известно точно и задаёт осмысленный порядок |
| **Файлы документов сторон**, «На удаление/», `Архив/` | `(2)`, `(3)` | имя задаётся содержанием документа, а времени в самом документе может не быть вовсе |

Прежняя оговорка для продуктов («`-{ЧЧММ}` **или** `(2)`, если время не важно») снята: она оставляла выбор исполнителю и прямо противоречила запрету `(2)` для процессуальных папок.

**Кросс-дельные накопительные файлы (judge-profile и т.п.)** именуются без даты — они аппенд-only по своей природе (см. раздел «Постусловия» для аналитических скиллов).

**Глобальная (кросс-дельная) память.** Часть скиллов (`analyze-hearing`, `draft-judgment`, `add-opponent`, `prepare-hearing`, `build-position`, `appeal`, `cassation`) дополнительно работает с глобальной памятью в `$VASSAL_GLOBAL_DIR/` (профиль судьи, профиль оппонента -- агрегируются по всем делам). Это **отдельное хранилище** вне текущего дела, со своим набором правил именования, накопления и постусловий -- см. раздел «Глобальная память (кросс-дельная)» ниже.

## Актуальное состояние продукта и папка `Архив/` (F.12)

**Проблема.** Одиннадцать скиллов кладут датированный снимок в корень дела **при каждом запуске**. Боевые цифры одного дела за одну сессию: 15 файлов в корне, из них 9 — версии одного заявления. Юрист не может определить, какой файл актуален, а плагин ему в этом никак не помогает.

**Решение (Сюзерен, 2026-07-19 и 2026-07-21).** В корне дела остаётся **последняя версия каждого типа артефакта**; предыдущие датированные снимки уезжают в подпапку `Архив/`. Файлы **не удаляются и не переписываются** — меняется только место, история сохраняется полностью. Правило «перезапись запрещена» не нарушается.

### Что считается «актуальным состоянием» — по типу артефакта

Актуальность считается **по типу артефакта**, а не по скиллу-производителю и не «последний продукт вообще». Это не вопрос вкуса:

- один скилл производит **несколько типов за запуск** (`settlement` — до трёх, `analyze-hearing` — три), и «один свежий продукт на скилл» пришлось бы разводить вручную;
- **более ранний подаваемый документ штатно нужен более позднему скиллу**: `cassation` читает нашу апелляционную жалобу, `cassation` при `target='ruling_settlement'` — текст мирового соглашения, `appeal` — проект решения (нейтральный прогноз). Это **конструкция обжалования**, а не редкий случай. «Последний продукт вообще» сломал бы вход того самого скилла, ради которого архивируем.

**Закрытый список типов.** Глоб якорится по **концу** имени (`* Мировое соглашение.md` не матчит `* Мировое соглашение — анализ и проект.md`). Колонка «В индексе» — см. следующий подраздел:

| Тип артефакта | Что остаётся в корне | Производитель | В индексе |
|---|---|---|---|
| Досье по доказательствам | `* Досье по доказательствам.md` | `study-evidence` | — |
| Предварительный анализ | `* Предварительный анализ документов.md` | `legal-review` | — |
| **Позиция** | `* позиция.md` — **все варианты `{тип}` («Начальная», «Обновлённая») это один тип** | `build-position` | — |

**Исключение по имени `.docx` у `analyze-hearing`.** Отчёт клиенту печатается как `{ГГГГ-ММ-ДД} Клиент Отчет о судебном заседании.docx` — шаблон имени **не совпадает** с его же `.md` (`{ГГГГ-ММ-ДД} Клиенту - краткая сводка по заседанию.md`), потому что это унаследованная ветка `arbitrum-docx`, не `format-doc`. Для архивации это **один тип**: оба файла — снимок одного артефакта и едут вместе. Правило «пара по общему имени» здесь не сработает — пару задаёт **тип**, а не совпадение имён.

**Два места, где список намеренно расходится с таблицей «Продукты плагина»:**

1. **`build-position`:** `{тип}` в имени («Начальная» / «Обновлённая») — это **часть версии, а не типа**. Все `* позиция.md` — один тип, в корне остаётся последняя.
2. **`draft-judgment`:** `{режим}` — наоборот, **часть типа**. «В пользу клиента» и «нейтральный прогноз» — методологически разные ветки, и `appeal` читает именно нейтральный прогноз, **явно отвергая** второй. Два типа, каждый держит в корне свою последнюю версию.

### Кто и когда архивирует — гибрид

**Решение Сюзерена 2026-07-21.** Два уровня, дешёвый и точный плюс сетка безопасности:

1. **Производитель при apply** — перед записью нового снимка уводит в `Архив/` **предыдущий снимок своего типа**. Ровно одно `mv` (пара `.md` + `.docx` — два). Тип он знает точно: это его собственный продукт, искать и угадывать не нужно.
2. **`update-index` при плановой сверке** — находит в корне более одного снимка одного типа и предлагает увести лишние (Preview → Apply, с подтверждением). Это закрывает историю, накопившуюся до правила, и следы оборванных прогонов.
3. **Служебная зона `.vassal/` не архивируется никогда.** Там датированность несёт **рабочую нагрузку**: шесть мест берут «последний по дате» глобом, `backfill-global` читает **все** `opponent-*.md` подряд. Мотив «чистота корня для юриста» к `.vassal/` неприменим — конвенция прямо выводит её из-под уборки, и юристу она не показывается.

Почему не «каждый скилл сам» и не «только `update-index`»: первое дало бы 11 копий правила, которое разъедется на первой правке (ровно то, что отвергли в F.16); второе оставило бы корень замусоренным между плановыми сверками.

### Механика

- Перемещение — **`mv`**, как в «На удаление/» (`rm` на маунте недостоверен).
- `Архив/` создаётся **лениво** (`mkdir -p`) при первой архивации; `init-case` её не создаёт.
- Структура внутри — **плоская**. Коллизия имени → `(2)`, `(3)` (это уже не продукт-в-работе, а сложенная история — см. таблицу суффиксов).
- **Пара `.md` + `.docx` едет вместе.** У `prepare-hearing`, `argument-map`, `draft-judgment` и ручного `/format-doc` продукт — два файла с общим именем. Увести `.md`, оставив `.docx`, **нельзя**: в корне останется осиротевший `.docx` без источника, и юрист прочитает как актуальный именно его. Архивируются **оба**, включая `_v2`/`_v3`-версии, если они появлялись.
- **`Архив/` — это не «На удаление/».** Файлы там живые: это история дела, а не мусор. Агент из `Архив/` ничего не удаляет и не переносит дальше; Сюзерен её не чистит по расписанию.
- **Ничего не архивируется, если архивировать нечего** — в том числе при идемпотентном повторе (см. «Идемпотентность»).

### Что `Архив/` меняет в сканировании и ссылках

- **`Архив/` — в игнор-списках сканирования** (Phase 0 и `update-index`, шаг 1), по образцу «На подачу/». Без этого каждый архивный снимок всплыл бы при первой же сверке как «новый файл».
- **Резолв обратных ссылок — с падением в `Архив/`.** Девять полей записывают ссылку **голым именем файла, без папки** (`supersedes`, `related_summary`, `related_document`, `related_docx`, `based_on_position`, `position_summary`, `prior_appeal`, `main_doc`). Правило резолва: **сначала от корня дела, не нашли — искать в `Архив/`**; нашли там — работать штатно, переписывать старые артефакты не нужно. Так переезд не рвёт ни одну существующую ссылку, и миграция не требуется.
### Продукты плагина и `index.yaml` — правило, которого не было

Правила «какие продукты попадают в индекс» **не существовало нигде** — ни в конвенциях, ни в `index-schema.yaml`. Вместо него — россыпь частных решений: `appeal` и `cassation` свой продукт в индекс заводят, `build-position`, `legal-review`, `study-evidence`, `argument-map`, `draft-judgment`, `analyze-hearing` — нет. Отсюда два боевых следствия: одинаковые по статусу файлы в корне ведут себя по-разному, а **позиция в корне при каждой сверке попадает в `new_files`** — Phase 0 поднимает ложный рассинхрон, а `update-index` предлагает прогнать по собственной аналитике плагина OCR и завести ей `doc-NNN` как документу стороны.

**Правило (F.12) — по назначению артефакта, не по скиллу:**

| Что | В индексе | Почему |
|---|---|---|
| **Подаваемые процессуальные документы** — жалобы, отзывы, ходатайства, заявления, мировое, замечания на протокол | **да** | это документы **дела**: они уходят в суд и становятся его материалами; `build-submission` ссылается на них (`main_doc`, `filing_status`), на них ссылаются двойные ссылки |
| **Аналитические продукты** — досье, предварительный анализ, позиция, карта доводов, проект решения, сводный по примирению, сводка клиенту | **нет** | это наша мысль о деле, а не его материалы. Доказательством не являются, `[doc-NNN]`-источником не выступают, OCR им не нужен |

Колонка «В индексе» в таблице типов выше — та же граница поимённо. Правило **закрепляет уже сложившееся поведение**, а не меняет его: `appeal`/`cassation` действовали верно, прочие тоже — не хватало самой границы.

**Следствия для сканирования:**
- Файлы аналитических типов в корне — **в игнор-списке** Phase 0 и `update-index` (наравне с `Таблица документов.xlsx`, который туда попал по той же причине). Ложный «новый файл» на собственном продукте больше не возникает.
- Архивный переезд **подаваемого** документа (тот в индексе есть) `update-index` подхватывает штатной автосвязкой переименований по `content_hash` — запись не осиротеет.

### Контракт чтения (обязателен для всех читателей)

Архивация меняет то, **что лежит в корне**, — а значит, меняет контракт для читателей. Три правила:

1. **Нужно актуальное состояние типа** → бери файл **из корня**: по построению он там ровно один. Это относится и к «чужому» типу: `cassation` берёт из корня `* Апелляционная жалоба.md`, `appeal` — `* Проект решения суда (нейтральный прогноз).md`.
2. **Нужна история или эволюция** → иди в **машинный слой `.vassal/`**, он не архивируется и остаётся на месте. Для позиции это `.vassal/analysis/position-{дата}-{секция}.md`. **Глоб по корню за историей запрещён:** после архивации он вернёт одну последнюю версию и молча выдаст её за всю эволюцию мысли — то есть соврёт, не упав.
3. **В корне не нашлось** → посмотри в `Архив/` (Сюзерен мог перенести файл вручную) и **скажи об этом** в отчёте, а не работай молча без документа.

**Стык с `revise-position`.** Этот скилл — не производитель снимков, а **мутатор** корневого продукта: он дописывает баннер «⚠ ОТОЗВАНО» в начало **последней `* позиция.md` в корне**. Архивация ему не мешает, а помогает: в корне остаётся ровно один файл этого типа, и «последняя» перестаёт быть догадкой. Важно другое — **баннер не переезжает вместе с мыслью**: когда `build-position` положит следующую позицию, файл с баннером уедет в `Архив/`, а новый снимок баннера не унаследует. Отозванное из него исключается не баннером, а **read-хуком по `.vassal/analysis/retractions.md`** (раздел «Леджер отзывов позиции») — леджер живёт в служебной зоне, не архивируется и остаётся единственным несущим механизмом. Баннер — вспомогательная пометка для юриста в текущем файле, и полагаться на него как на носитель отзыва нельзя.

## Идемпотентность (что значит «повторный прогон безопасен»)

**Определение.** Скилл идемпотентен, если **повторный прогон на неизменившемся входе не порождает нового состояния**: ни дублирующих записей в индексе, ни лишних файлов, ни повторно инкрементированных счётчиков. Это свойство **результата**, а не побайтового равенства выхода.

До сих пор определение жило только в `ARCHITECTURE.md`, а в плагине фактически сосуществуют **три** режима. Все три законны, но применяются в разных местах, и путать их нельзя:

| Режим | Кто | Что делает повторный прогон |
|---|---|---|
| **Пересборка** | `build-submission`, `catalog`, `update-index`, `format-doc` | собирает тот же артефакт заново поверх прежнего; выход зависит только от входа |
| **Пропуск сделанного** | `intake`, `add-evidence`, `add-opponent` | сверяет `content_hash`: уже принятый файл пропускается, `next_id` не жжётся, дубль записи не заводится |
| **Новый датированный снимок** | 11 производителей продуктов | пишет снимок с новой датой (или `-{ЧЧММ}` в ту же дату), предыдущий уводит в `Архив/` |

**Инвариант, общий для трёх режимов:** повторный прогон **не теряет** сделанного и **не удваивает** его.

Для третьего режима отсюда следует правило, которого не было: **если вход не изменился и новый снимок содержательно совпал бы с предыдущим — новый файл не создаётся, и архивация не выполняется.** Датированный снимок фиксирует **изменение мысли**, а не факт запуска скилла; прогон «на всякий случай» не обязан оставлять след в корне. Расхождение есть → новый снимок пишется штатно, предыдущий уезжает в `Архив/`.

> **`.docx` сравнивается по содержимому, а не по байтам (F.29).** `.docx` — это zip, и `python-docx` проставляет в записях архива **текущее время**. Поэтому `sha256` двух прогонов на одном входе **не совпадает**, хотя `document.xml`, `styles.xml`, `numbering.xml` побайтово идентичны. Проверять идемпотентность `.docx` хэшем файла — гарантированная ложная тревога (на неё уже попадались при триаже). Сравнивать нужно **распакованные части архива**.

## Двухуровневое сохранение для аналитических скиллов

**Принцип:** дорогая Opus-аналитика (правовой разбор, позиции, blue/red team, стресс-тест, подбор практики ВС РФ) сохраняется в **двух представлениях одновременно**: «человечном» сводном файле для Сюзерена и наборе машинно-читаемых файлов для других скиллов. Это устраняет два антипаттерна: (а) эфемерность дорогой работы (потеря между запусками); (б) парсинг «человечного» сводного `.md` соседним скиллом.

**Уровень a) Для Сюзерена -- сводный `.md` в корне дела.**

Имя -- по шаблону скилла из таблицы «Продукты плагина» (`{ГГГГ-ММ-ДД} Предварительный анализ документов.md` и т.п.). Содержит весь анализ в человечной форме: разделы, таблицы, аудируемые выводы. Юрист читает только этот файл -- он самодостаточен.

**Уровень b) Для агента -- машинно-читаемые файлы в `.vassal/{категория}/`.**

Каждый аналитический блок сохраняется отдельным файлом со стандартным frontmatter:

```yaml
---
type: <тип артефакта, напр. position-section / prep-analysis / cassation-prep>
section: <название блока, если применимо>   # для многосекционных скиллов
date: ГГГГ-ММ-ДД
case: "{номер дела}"
related_summary: "{путь к сводному файлу для Сюзерена}"   # обратная ссылка
supersedes: null | "{предыдущий файл этой же секции}"
refs: ["doc-NNN", ...]   # doc-id всех источников
not_applicable: false | "<причина>"   # если блок не имеет смысла в данном контексте
---
```

Содержимое -- блок из сводного, в аудируемом формате, с двойными ссылками на источники.

**Когда какой паттерн применять:**

| Скилл | Сводный файл | Файлы для агента | Расположение |
|---|---|---|---|
| `study-evidence` | `{дата} Досье по доказательствам.md` (снимок прозы досье) | `evidence-dossier.md` — **живое каноническое, не датируется**, дельта по `content_hash` (без supersedes-цепочки) | `.vassal/analysis/` |
| `legal-review` | `{дата} Предварительный анализ документов.md` | `qualification.md`, `deadlines.md`, `pretrial.md`, `jurisdiction.md`, `completeness.md`, `questions-to-client.md`, `answers.md` | `.vassal/analysis/` |
| `build-position` | `{дата} {тип} позиция.md` | `position-{дата}-{evidence-base, strengths, weaknesses, opponent-forecast, risks, strategy}.md` | `.vassal/analysis/` |
| `prepare-hearing` | `{дата} {тип процдокумента}.md` (текст документа) | `{дата}-prep.md` (Blue/Red team, парирование, стресс-тест, финальная структура) | `.vassal/hearings/` |
| `cassation` | `{дата} Кассационная жалоба.md` (текст жалобы) | `cassation-prep-{дата}.md` (сравнительный разбор актов, кандидаты в основания, фильтр непереоценки, практика ВС, ранжирование, стресс-тест) | `.vassal/analysis/` |
| `settlement` | `{дата} Мировое соглашение — анализ и проект.md` (или варианты для `withdrawal` / `admission`) + подаваемые `.md` документов (мировое / ходатайство / заявление); `.docx` — на `build-submission` через `format-doc` (мировое вне охвата) | `settlement-{дата}-{batna, zone-of-agreement, opponent-forecast, risks, terms-draft}.md` | `.vassal/analysis/` |
| `argument-map` | `{дата} Карта доводов.md` (+ `.docx`) — **чистая** для суда, tag-free, выводится из рабочей **вычитанием** столбца «оценка узла» | `argument-map-{дата}-working.md` — **рабочая**: полная таблица + оценка силы/слабости узла, `[doc-NNN]` (богаче сводной; чистая = рабочая минус оценка) | корень / `.vassal/analysis/` |

**Правила консистентности:**

1. **Содержательная согласованность.** Каждое утверждение в сводном `.md` имеет корреспондирующий блок хотя бы в одном из машинно-читаемых файлов; и наоборот, ничего значимого не существует только в служебной зоне.
2. **Двойные ссылки везде.** В обоих представлениях источники -- по правилу «Двойные ссылки» (`Название документа от ДД.ММ.ГГГГ [doc-NNN]`). Юрист в сводном файле читает имя; соседний скилл в машинно-читаемом -- ходит по `[doc-NNN]`.
3. **Цепочка `supersedes`.** При повторном запуске:
   - Сводный получает `supersedes: <путь к предыдущему сводному>` во frontmatter.
   - Каждый машинно-читаемый файл получает `supersedes: <путь к предыдущему файлу той же секции>`.
   - Старые файлы **не удаляются** -- это история мысли по делу.
4. **`not_applicable` вместо пропуска.** Если по контексту дела какой-то блок неприменим (например, у ответчика без встречного иска evidence-base почти пустой) -- файл всё равно создаётся со фронтматтером `not_applicable: <причина>` и одной строкой в теле. Это сохраняет цепочку и даёт явный аудиторский след «почему пусто».
5. **Постусловия.** Категория 2 «Аналитические скиллы» в разделе «Постусловия скиллов» ниже формализует, что должно быть правдой после `apply` -- в том числе обязательное создание сводного и всех заявленных машинно-читаемых файлов.

**Зачем именно так:**
- `prepare-hearing` напрямую читает `.vassal/analysis/position-{последняя-дата}-{секция}.md` без парсинга человечной позиции -- структура у него под контролем frontmatter.
- При повторной кассации (СКЭС) -- читается `cassation-prep-*.md` целиком, фазы 2-3 не повторяются.
- `analyze-hearing` после заседания читает `{дата}-prep.md` для сравнения «что готовили» vs «что фактически произошло».
- При сбое сессии -- работа Opus сохранена и доступна следующему запуску.

## Леджер отзывов позиции (revise-position)

**Принцип:** `.vassal/` -- многофайловый слой истины **без понятия «текущего среза»**. Когда правовая позиция правится по ходу дела (отвергнут довод, поправлена ссылка на Пленум, убрана сущность), финальный документ выходит верным, но служебный слой остаётся со **старыми выводами** -- и следующий скилл, читая его как истину, воскрешает уже исправленную ошибку (типичный провал: `build-position` грузит **весь** `analysis/` скопом → тянет осевший отозванный вывод). Скилл `revise-position` ([skills/revise-position/SKILL.md](../skills/revise-position/SKILL.md)) замыкает эту петлю через **леджер отзывов**.

### Файл

`.vassal/analysis/retractions.md` -- единый живой **append-only** файл (как `judge-profile.md`: не датируется, без supersedes-цепочки). Одна запись = один отзыв: что отозвано, тип (правовой вывод / практика / факт / сущность), причина, чем заменено, затронутые артефакты, способ распространения. Полная схема и пример -- в [skills/revise-position/SKILL.md](../skills/revise-position/SKILL.md) → «Формат леджера».

### Read-хук (единый для потребителей)

Скиллы, читающие служебный слой как источник истины, в фазе загрузки контекста **обязаны** применить фильтр отозванного:

> **Хук `revise-position`:** перед тем как принять `.vassal/analysis/*`, prep-артефакты и `index.yaml` за истину, прочитай `.vassal/analysis/retractions.md` (если есть). Любой вывод / факт / сущность / практику, помеченную отозванной, **исключи** из построения -- **даже если** она присутствует в загруженном analysis-файле (тот отражает состояние ДО правки). При наличии замены -- используй новую формулировку из леджера. Если отозванное всё же нужно упомянуть -- только с явной пометкой «отозвано {дата}, причина {…}», не как действующий довод.

Хук -- несущая часть механизма: отозванное фильтруется **независимо** от того, в каком файле оно осело и резолвит ли читатель supersedes-цепочку.

### Кто чтит леджер

`build-position`, `prepare-hearing`, `appeal`, `cassation`, `settlement` -- в фазе загрузки контекста (ссылаются на этот раздел). Прочие скиллы, читающие `.vassal/analysis/` как вход для рассуждения (`legal-review`, `draft-judgment` при повторном прогоне), применяют тот же фильтр, если леджер присутствует.

### Границы

`revise-position` отзывает **выводы**; факты/сущности в `index.yaml`/зеркалах он только **флагует** и передаёт `update-index` (зеркала -- verbatim-отражение документов, не переписываются -- стык с E.8). Кросс-дельная память (`judge-profile.md`, `$VASSAL_GLOBAL_DIR/`) -- append-only, не редактируется; просочившееся отозванное только флагуется Сюзерену. Полная переработка позиции -- повторный `build-position`, не `revise-position` (тот работает точечной дельтой).

## Глобальная память (кросс-дельная)

**Принцип:** некоторые наблюдения ценны не только для текущего дела, но и для всех будущих дел того же юриста: профиль судьи (его стиль, предпочтения, триггеры), паттерны конкретного оппонента (типовые доводы в отзывах, тактика, представители). Эти наблюдения накапливаются в **глобальной памяти**, единой для всех дел Сюзерена, и читаются скиллами **до** анализа -- модель сразу знает, что у этого судьи / оппонента уже наблюдалось в прошлых делах.

Без глобальной памяти возникает антипаттерн «изоляция кросс-дельной ценности»: 5 дел у судьи Иванова → 5 пустых стартовых профилей; тот же оппонент в третьем деле подряд → модель снова с нуля анализирует «нового» оппонента, паттерны которого мы уже видели дважды.

### Расположение

**Базовый путь:** `~/.vassal-global/` (по умолчанию).

**Переопределение:** переменная окружения `VASSAL_GLOBAL_DIR`. Если задана -- используется её значение, иначе -- `~/.vassal-global/`.

Зачем переопределение: типичные сценарии -- хранение глобальной памяти на синхронизируемом диске (Яндекс.Диск / Dropbox / OneDrive) для кросс-машинного синка между рабочей и поездочной машинами; либо изоляция глобальной памяти разных юристов команды на одной рабочей станции.

**Структура папки:**

```
$VASSAL_GLOBAL_DIR/                              # по умолчанию ~/.vassal-global/
├── judges/
│   ├── {ФИО-slug}--{court-slug}.md             # один файл на пару (судья × суд)
│   └── ...
├── counterparties/
│   ├── inn-{ИНН}.md                            # для юрлиц с ИНН -- ИНН как ключ
│   ├── noinn-{slug-name}.md                    # fallback для физлиц / без ИНН
│   └── ...
└── README.md                                    # опционально, заметки Сюзерена
```

**Важно:** глобальная папка живёт **вне** репозитория плагина и **вне** папки конкретного дела. Скиллы создают её при первом обращении (`mkdir -p`), если не существует.

`templates/{категория}/` -- предусмотрено архитектурно, но в этап 6 не входит (наполняется вручную, см. план в FINAL-REPORT.md этап 7).

### Правила слагов

Имена файлов формируются по детерминированному правилу:

1. Кириллица сохраняется (без транслитерации) -- `Иванов`, `Арбитражный`.
2. Пробелы → дефис: `Арбитражный суд` → `Арбитражный-суд`.
3. Точки удаляются: `И. И.` → `И-И`.
4. Кавычки `«»"'` удаляются: `ООО «Ромашка»` → `ООО-Ромашка`.
5. Запятые, слэши, спецсимволы → дефис.
6. Подряд идущие дефисы схлопываются в один.
7. Между двумя слаг-блоками в имени файла -- двойной дефис `--` (визуальный разделитель).

Примеры:
- Судья: `Иванов И. И.` × `Арбитражный суд Красноярского края` → `Иванов-И-И--Арбитражный-суд-Красноярского-края.md`
- Оппонент с ИНН: `inn-7707083893.md` (короткое имя в frontmatter).
- Оппонент без ИНН: `noinn-Иванов-Иван-Иванович.md`.

### Двойная запись и обратные ссылки

Когда скилл наблюдает паттерн (по судье или оппоненту), он пишет **в два места одновременно**:

1. **Локальный файл** -- в `.vassal/` текущего дела (`judge-profile.md`, `opponent-filing-*.md`, `opponent-hearing-*.md`). Содержит наблюдения только из этого дела, привязан к конкретным заседаниям/документам с двойными ссылками `[doc-NNN]`.
2. **Глобальный файл** -- в `$VASSAL_GLOBAL_DIR/`. Содержит **агрегированные** наблюдения по всем делам, каждое наблюдение помечено источником `(дело {номер}, {дата})`.

В локальном файле во frontmatter -- обратная ссылка на глобальный:

```yaml
---
type: judge-profile
judge: "Иванов И. И."
court: "Арбитражный суд Красноярского края"
shared_profile: "judges/Иванов-И-И--Арбитражный-суд-Красноярского-края.md"
# путь относительно $VASSAL_GLOBAL_DIR -- скилл резолвит при чтении
hearings_analyzed: 2          # в этом деле
last_updated: 2026-05-10
---
```

В глобальном файле -- список дел, на которых он построен:

```yaml
---
type: judge-profile-global
judge: "Иванов И. И."
court: "Арбитражный суд Красноярского края"
slug: "Иванов-И-И--Арбитражный-суд-Красноярского-края"
cases:
  - "А33-12345/2026"
  - "А33-67890/2026"
  - "А33-11111/2025"
hearings_total: 8                       # суммарно по всем делам
written_decisions_total: 3              # суммарно
last_updated: 2026-05-10
last_case: "А33-67890/2026"
---
```

### Правило накопления

При каждом обновлении (двойная запись после `analyze-hearing`, `draft-judgment`, `add-opponent`):

- В **локальный** файл -- наблюдения этого запуска, с двойными ссылками на документы текущего дела.
- В **глобальный** файл:
  - Каждое новое наблюдение дописывается **аппенд-only** в соответствующий раздел с обязательным маркером `(дело {номер}, заседание {дата})` или `(дело {номер}, документ {краткое имя})`.
  - Старые наблюдения **никогда не удаляются и не редактируются** (даже если они противоречат новым -- противоречие добавляется как «уточнение» с новой датой; разрешать конфликты -- задача Сюзерена при чтении, не агента при записи).
  - Список `cases:` пополняется (без дублей по номеру дела).
  - Счётчики `hearings_total`, `written_decisions_total`, `filings_analyzed`, `hearings_analyzed` инкрементируются ровно на число добавленных в этом запуске.
  - `last_updated` и `last_case` обновляются.

**Бэкфилл накопленной локальной памяти.** Для дел, чья локальная аналитика (`.vassal/hearings/judge-profile.md`, `.vassal/analysis/opponent-*.md`) накапливалась до этапа 6.1 (двойная запись в глобальную) или иначе не попала в глобальный профиль -- разовый перенос выполняется через служебный скилл `/vassal-litigator:backfill-global` ([skills/backfill-global/SKILL.md](../skills/backfill-global/SKILL.md)). Скилл с Opus-семантической дедупликацией добавляет новые наблюдения в глобальные файлы с маркерами `(дело {номер}, ...)` и пишет опциональное поле `backfilled_cases:` во frontmatter -- его читает только сам `backfill-global` для идемпотентности повторных запусков; другие скиллы это поле игнорируют.

### Чтение глобальной памяти

Скиллы, у которых есть зона релевантности глобальной памяти (`prepare-hearing`, `build-position`, `appeal`, `cassation`, `analyze-hearing`, `draft-judgment`):

1. **В фазе загрузки контекста** -- разрезолвить `$VASSAL_GLOBAL_DIR` (с fallback на `~/.vassal-global/`).
2. По `case.judge` собрать ожидаемое имя файла судьи в `judges/` (по правилам слагов выше). Если файл существует -- загрузить **до** локального `judge-profile.md`. Если нет -- работать без глобального профиля, не падать.
3. По `case.parties` для оппонента (роль ≠ роли нашего клиента) -- собрать имя файла в `counterparties/`. Сначала пробовать `inn-{ИНН}.md` (если ИНН есть в `case.parties[].inn`), потом `noinn-{slug-name}.md`. Если файл существует -- загрузить.
4. Глобальные файлы имеют **приоритет в смысле «ранее увиденного»** -- модель учитывает их паттерны как фон, локальные наблюдения этого дела -- как foreground.

### Конфиденциальность

Глобальная память -- **производная аналитика**, не копия документов:

- ✅ Можно: паттерны судьи, типовые формулировки оппонента, статистика «в N делах из M ходатайствовал по ст. 333 ГК», ФИО представителей, ИНН/ОГРН (это публичные данные).
- ❌ Нельзя: тексты документов клиентов, конкретные суммы по конкретным делам клиентов, персональные данные третьих лиц без юридической необходимости (контрагенты клиента -- да, физлица -- осторожно).

Глобальная папка, как и `.vassal/` дела, лежит **локально на машине Сюзерена**. Если используется кросс-машинный синк через облако -- ответственность за приватность канала на Сюзерене.

### Постусловия (для скиллов, пишущих в глобальную память)

После `apply` скилл обязан проверить (в дополнение к локальным постусловиям своей категории):

- Глобальный файл создан или обновлён по правильному пути (резолв `$VASSAL_GLOBAL_DIR` выполнен).
- Папка `judges/` или `counterparties/` создана при необходимости (`mkdir -p`).
- Содержимое **аппенд-only**: счётчики увеличены ровно на число добавленных наблюдений; список `cases:` -- без дублей; `last_updated` обновлён.
- Локальный файл (если есть) содержит во frontmatter `shared_profile:` -- путь к глобальному относительно `$VASSAL_GLOBAL_DIR`.
- При сбое записи в глобальный файл (ФС недоступна, нет прав) -- скилл **не падает целиком**, а: (а) фиксирует локальный файл; (б) предупреждает Сюзерена по шаблону «Глобальная память недоступна: {причина}; локальный профиль сохранён; глобальный синк выполнить позже»; (в) пишет факт в `.vassal/history.md`.

## Notion-слой (опциональная одностороння синхронизация)

**Принцип:** Notion -- **зеркало**, не источник правды. Скилл `notion-sync` ([skills/notion-sync/SKILL.md](../skills/notion-sync/SKILL.md)) выполняет односторонний push метаданных дела (`case.yaml`), глобального профиля судьи (`$VASSAL_GLOBAL_DIR/judges/`) и (опционально, этап 6.2b) глобальных профилей оппонентов (`$VASSAL_GLOBAL_DIR/counterparties/`) в Notion-базы `Cases`, `Judges`, `Counterparties`. Это даёт юристу единый дашборд по всем делам и кросс-дельную видимость (которая локально лежит в глобальной памяти, но в Notion удобнее просматривать).

Notion-слой -- **опциональный**. Плагин полностью работоспособен без него. Если конфиг `~/.vassal/notion-config.yaml` отсутствует -- авто-хуки в `init-case`, `analyze-hearing`, `appeal`, `cassation` не предлагают синк, ручная команда `/vassal-litigator:sync-notion` явно сообщает о ненастроенности.

### Что синхронизируется

| Данные | В Notion? | Почему |
|---|---|---|
| Метаданные дела (номер, стороны, суд, наш клиент, стадия, следующее заседание) | ✅ | Дашборд |
| Профиль судьи (стиль, паттерны, склонности, кол-во дел) | ✅ | Кросс-дельная память + дашборд |
| Профили оппонентов (`$VASSAL_GLOBAL_DIR/counterparties/`) -- сжатые поля «Типовые доводы», «Тактика», «Представители» | ✅ (опционально, этап 6.2b) | Кросс-дельная память + дашборд; активируется, если `notion.databases.counterparties` задана в конфиге |
| Тексты документов / md-зеркала | ❌ | Конфиденциальность + объём |
| Позиции (`*позиция.md`) | ❌ | Стратегия -- самое чувствительное |
| `.vassal/analysis/*` | ❌ | Оценки рисков, слабостей |
| Транскрипции заседаний | ❌ | Чувствительно |

Полная матрица -- в [NOTION-INTEGRATION-PROPOSAL.md](../NOTION-INTEGRATION-PROPOSAL.md) §3.

### Направление синхронизации

**Push (автоматически по запросу):**
- Скилл `notion-sync` ИЛИ опциональные хуки в `init-case`, `analyze-hearing`, `appeal`, `cassation` (хуки **не блокирующие** -- скилл-инициатор завершается успешно даже если Сюзерен отказался от синка или синк упал).
- Конфликты разрешаются просто: при upsert поля из локальной правды **перезаписывают** Notion-запись, **кроме** `fields_manual_only` из конфига (например, `Статус: won/lost` -- ручное поле юриста).

**Pull (вручную, по запросу) -- зона расширения, не MVP:**
- При следующем `prepare-hearing` плагин может предложить: «По судье Иванову в Notion есть свежие заметки от 15.04 -- подтянуть?». В MVP не реализовано.

**Обратный авто-синк не делается** -- конфликтует с local-first архитектурой. См. [NOTION-INTEGRATION-PROPOSAL.md](../NOTION-INTEGRATION-PROPOSAL.md) §4.

### Конфигурация

Файл: `$VASSAL_CONFIG_DIR/notion-config.yaml` (один на пользователя, не на дело).

**Расположение:**
- По умолчанию: `~/.vassal/notion-config.yaml`.
- Переопределение: переменная окружения `VASSAL_CONFIG_DIR`. Если задана -- используется её значение, иначе -- `~/.vassal/`.

Сценарии переопределения -- те же, что у `$VASSAL_GLOBAL_DIR` (см. раздел «Глобальная память»):
- Хранение в облачном диске для кросс-машинного синка между рабочей и поездочной машинами (важно: на разных Windows-машинах `~` резолвится в разные пути из-за разных имён пользователя; env var с явным OneDrive/Dropbox-путём решает это).
- Изоляция конфигов разных юристов команды.

Логически `$VASSAL_CONFIG_DIR` и `$VASSAL_GLOBAL_DIR` парные -- обычно ставятся в **одну OneDrive-/Dropbox-папку**, как два соседних подкаталога. Можно и порознь, если нужно (например, конфиг -- локально, а память -- на облаке).

**На Windows для кросс-машинного синка** рекомендуется `REG_EXPAND_SZ` со встроенной переменной `%OneDrive%` -- одно значение работает на всех машинах одного юзера, Windows подставит профиль. Точная команда -- в [scripts/notion-init.md](../scripts/notion-init.md) → §3.1. Это ключевая деталь: `setx` создаёт `REG_SZ` без раскрытия `%VAR%`, поэтому `setx` для кросс-машинной конфигурации не подходит -- нужен `reg add /t REG_EXPAND_SZ`.

Шаблон конфига -- [scripts/notion-config.example.yaml](../scripts/notion-config.example.yaml). Bootstrap (создание Notion-баз и заполнение конфига) -- разовая операция по инструкции [scripts/notion-init.md](../scripts/notion-init.md).

Токен Notion -- через MCP-auth, в плагине не хранится.

### Идемпотентность и dedup

- **Cases**: dedup по `case.number`. Дело без номера -- временный ключ `temp-{slug}` (миграция при появлении номера -- зона расширения).
- **Judges**: dedup по `slug` глобального профиля (или `ФИО+Суд` если глобального профиля нет).
- **Counterparties** (если активна): dedup по `slug` (`inn-{ИНН}` или `noinn-{slug-name}` -- тот же ключ, что в файле локальной памяти). Fallback'и: ИНН, TITLE `Организация`. Теневой дубль (`inn-*` + `noinn-*` одновременно в локальной памяти) синкается **только в каноническую запись**, см. [skills/add-opponent/SKILL.md](../skills/add-opponent/SKILL.md) → «Дедуп оппонента: inn-/noinn- теневой дубль».
- При двух последовательных запусках на одно дело -- update, не дубль.

### Опция `--private-case`

Если в `case.yaml` есть поле `case.private: true` (зарезервировано на будущее) -- `notion-sync` **не синкает** это дело и явно сообщает Сюзерену. В MVP поле не используется, но скилл его уважает. Сценарий: дела особо чувствительных клиентов, где даже метаданные не должны уходить в облако.

### Постусловия

- `~/.vassal/notion-config.yaml` прочитан и валиден ИЛИ скилл вышел с явным предупреждением (без изменений).
- Notion MCP проверен на доступность (через короткий probe-запрос) ИЛИ зафиксировано в `.vassal/notion-sync.log` как недоступный.
- При успешном синке: запись в `Cases` создана/обновлена ровно одна; запись в `Judges` -- ровно одна (если `case.judge` не null); записи в `Counterparties` -- по одной на каждого оппонента из `case.parties` (если `notion.databases.counterparties` активна и оппоненты есть); relation `Cases.Судья → Judges` и `Cases.Оппонент → Counterparties` установлены; поля из `fields_manual_only` не перезаписаны.
- `.vassal/notion-sync.log` обновлён (timestamp + что синкалось + статус OK/PARTIAL/FAIL).
- `.vassal/history.md` обновлён.

## Постусловия скиллов

После успешного `apply` каждый скилл должен убедиться, что его выходные артефакты соответствуют контракту. Без явных постусловий скилл не может проверить себя — возможна молчаливая порча состояния (записи в индексе без файлов, файлы без зеркал, рассогласованный `next_id`, невалидный YAML).

В каждом `SKILL.md` обязательна секция **«Постусловия»** перед завершением `apply`. Чек-лист зависит от категории скилла.

### Категория 1: ingest-скиллы (`intake`, `add-evidence`, `add-opponent`)

- `index.yaml` — валидный YAML, соответствует [shared/index-schema.yaml](index-schema.yaml) v3.
- Для каждой новой записи:
  - физический файл по пути `file:` существует;
  - md-зеркало по пути `mirror:` существует и валидно (frontmatter + текст);
  - `content_hash` вычислен и записан;
  - `source` соответствует скиллу (intake/add-evidence → `client`, add-opponent → `opponent`).
- `next_id` инкрементирован ровно на число добавленных документов; `next_bundle_id` — на число добавленных бандлов.
- **Сохранение оригинала по режиму `raw_pristine`:** для `source ∈ {opponent, court}` (или keep-pristine) — `.vassal/raw/{скилл}-{ГГГГ-ММ-ДД}/` содержит пристинные копии (бит-в-бит), запись `raw_pristine: true`. Для `source = client` — байтовой копии нет; сохранение оригинала = манифест (`origin` + `content_hash` в записи индекса) + рабочая копия в «Материалы». См. «Cowork-first robustness» → операционные следствия.
- Все обработанные файлы из «Входящие документы/» перемещены в «На удаление/» (через `mv`, см. раздел «Папка „На удаление/"»).
- Если в `Входящих` остались файлы — каждому в отчёте указана причина (нечитаемый, защищён паролем, требует ручного решения).
- **Решающие документы (F.18):** для каждого документа решающего класса или помеченного Сюзереном проставлены `decisive` / `decisive_reason`; критичные поля либо прошли второе чтение (`verified_fields` заполнен вердиктами), либо явно зафиксировано, что вторая нога **не отработала** (пустой `verified_fields` + строка в EXTRACTION NOTES и в отчёте). «Не проверено» не выдаётся за «проверено и чисто». Расхождение чтений → поле в `low_confidence_fields` + `needs_manual_review: true`, **оба** прочтения в зеркале.
- **Принадлежность делу (F.19):** сверка выполнена для каждого файла; при положительном противоречии (чужой № дела / ИНН / стороны) файл показан отдельным блоком Preview и решение Сюзерена зафиксировано (обработан со строкой в EXTRACTION NOTES ЛИБО оставлен во «Входящие»). **Ни один файл не отбракован молча.**
- Запись в `.vassal/history.md` зафиксирована.
- **Уборка временных артефактов скилла:** служебные файлы процесса (`intake_*.json`, `*_manifest.py`, `__pycache__/`, `.write_test` и т.п.) убраны из `.vassal/` (через `mv` в «На удаление/», т.к. часть не удаляется `rm`). В `.vassal/` остаются только штатные артефакты (`case.yaml`, `index.yaml`, `mirrors/`, `analysis/`, `hearings/`, `submissions/`, `history.md`, `raw/`). **`submissions/` в этом перечне отсутствовала** (F.12) — по букве прежней редакции ingest-скилл был вправе унести манифесты подач в «На удаление/»; папка штатная, создаётся лениво скиллом `build-submission`.
- Если есть бандлы: `bundles[].main_doc` и `members` ссылаются на существующие `doc-NNN`; в каждом `doc-NNN` бандла заполнены `bundle_id`, `parent_id`, `role_in_bundle`.

### Категория 2: аналитические скиллы (`legal-review`, `build-position`, `prepare-hearing`, `analyze-hearing`, `settlement`, `study-evidence`, `argument-map`)

> `study-evidence` -- частичное исключение из общих правил категории: машинно-читаемый артефакт -- **единый живой файл** `.vassal/analysis/evidence-dossier.md` (дельта по `content_hash`, **без supersedes-цепочки и без датирования**); датированный снимок для Сюзерена (`{дата} Досье по доказательствам.md`) создаётся, как у прочих. `case.yaml` скилл **не пишет** (чистый читатель -- пункт про обновление полей ownership к нему неприменим). Кэш и инвалидация -- в [skills/study-evidence/SKILL.md](../skills/study-evidence/SKILL.md).

> `argument-map` -- тоже **чистый читатель** (`case.yaml` не пишет, зон ownership нет). Особенность двухуровневого сохранения инвертирована: машинно-читаемый файл (`.vassal/analysis/argument-map-{дата}-working.md`) **богаче** сводного -- в нём столбец «оценка узла» (сила/слабость) и `[doc-NNN]`; сводный для Сюзерена (`{дата} Карта доводов.md`, чистая для суда) **выводится из него вычитанием** этого столбца и подчисткой формулировок, tag-free. Требование: чистая версия не собирается заново, только вычитанием из рабочей (слабые места не должны просочиться в судебную версию); практика — либо резолвится в коннектор CasusLegal / локальную папку «Практика*», либо помечена «сверить вручную». Детали -- [skills/argument-map/SKILL.md](../skills/argument-map/SKILL.md).

> `settlement` -- гибрид категорий 2 и 3: на нём действуют постусловия обеих категорий. По категории 2 -- блок «зона компромисса» и стресс-тест трёх рисков сохраняются машинно-читаемыми файлами; по категории 3 -- финальные проекты документов (мировое / ходатайство об утверждении / заявление об отказе от иска / заявление о признании иска) создаются как **подаваемые `.md`**, а `.docx` печатается позже на `build-submission` через `format-doc` (мировое соглашение -- двусторонний документ, вне охвата `format-doc`: прежний путь). Подробности -- ниже в категории 3 и в `skills/settlement/SKILL.md` → «Постусловия».

- Все заявленные в SKILL.md выходные файлы в `.vassal/analysis/` (или `.vassal/hearings/`) созданы. Если какой-то блок пропущен — `not_applicable: <причина>` во frontmatter и одна строка в теле (не молчаливый skip; см. раздел «Двухуровневое сохранение для аналитических скиллов» правило 4).
- **Двухуровневое сохранение соблюдено**: сводный файл для Сюзерена в корне дела + комплект машинно-читаемых файлов в служебной зоне (см. таблицу в одноимённом разделе). Сводный и детальные согласованы между собой; источники в обоих местах -- двойные ссылки.
- `case.yaml` остался валидным YAML; обновлены **только** поля, входящие в зону ownership скилла (см. раздел «Ownership полей case.yaml»).
- Все выводы оформлены по разделу «Аудируемость выводов» — все поля заполнены, источники указаны в формате двойной ссылки (см. раздел «Двойные ссылки»).
- Если обновлялся `index.yaml` (например, проставлены `tags`, `role_in_bundle`) — снят backup перед apply (см. ingest-скиллы).
- Аппенд-only файлы (`questions-to-client.md`, `answers.md`, кросс-дельные `judge-profile.md`) — действительно дописаны, а не перезаписаны.
- При повторном запуске -- `supersedes`-цепочка корректна как у сводного, так и у каждого машинно-читаемого файла; старые версии не удалены.
- **Архивация предыдущего снимка (F.12):** в корне дела остался **ровно один** файл этого типа артефакта — свежий; предыдущий снимок того же типа перемещён (`mv`) в `Архив/` **вместе с парным `.docx`**, если он был. Машинно-читаемые файлы в `.vassal/` **не тронуты** — служебная зона не архивируется. Правило и закрытый список типов -- «Актуальное состояние продукта и папка `Архив/`».
- **Идемпотентный повтор:** если вход не изменился и новый снимок содержательно совпал бы с предыдущим -- новый файл **не создан**, архивация не выполнялась, и это сказано Сюзерену («содержательных изменений нет, снимок не создавался»), а не выдано за успешную перегенерацию.
- Запись в `.vassal/history.md` зафиксирована -- с именами сводного и всех машинно-читаемых файлов; при архивации -- что уехало в `Архив/`.

### Категория 3: document-producing скиллы (`prepare-hearing` (документ), `draft-judgment`, `appeal`, `cassation`, `settlement`)

- **Подаваемый `.md`** выходного документа создан в корне дела по шаблону из «Продукты плагина» (tag-free, по якорному контракту `format-doc`).
- **`.docx` — late-binding** (см. «Где печатается `.docx`»): `prepare-hearing` печатает `.docx` через `format-doc` (host) ИЛИ `.md`-fallback (нет `python-docx`) + предупреждение. `appeal` / `cassation` / `settlement` **`.docx` здесь не создают** — подаваемый `.md` готов, `.docx` печатается на `build-submission`. `draft-judgment` и мировое соглашение — вне охвата `format-doc` (arbitrum-docx опц. / `.md`).
- **Версионирование и архивация (F.12) — раньше категория 3 об этом молчала.** В корне дела остался **ровно один** файл этого типа артефакта; предыдущий снимок того же типа перемещён (`mv`) в `Архив/` вместе с парным `.docx`, если он был. Тип берётся из закрытого списка -- «Актуальное состояние продукта и папка `Архив/`». **Снимки чужих типов не тронуты:** `cassation` не архивирует апелляционную жалобу, `appeal` не архивирует проект решения — они нужны как штатный вход соседним скиллам.
- **Идемпотентный повтор:** содержательно неизменившийся документ **не порождает** нового снимка (см. «Идемпотентность»); Сюзерену сказано, что изменений нет.
- Приложения к документу перечислены **в самом документе** + связаны с записями `index.yaml` через двойные ссылки.
- Соответствующее поле в `case.yaml` обновлено (`appeal.filed_date`, `cassation.filed_date`, `settlement.draft_date | filed_date | confirmed_date | in_progress`, `status: pending_appeal | pending_cassation | pending_settlement | settled | withdrawn`).
- Для `settlement`: проверена совместимость `mode × stage` по правилам [case-schema.yaml](case-schema.yaml) (`admission` -- только `stage='1inst'`; `withdrawal` -- кроме `enforcement`; запрещённые комбинации блокируются ещё в фазе 0 SKILL).
- Для `settlement`: при `mode='agreement'` сохранены **отдельные** подаваемые `.md`: текст мирового соглашения (двусторонний, подписи обеих сторон, ст. 140 АПК — вне охвата `format-doc`) **и отдельно** ходатайство об утверждении (по умолчанию одностороннее от нашего клиента); состав документов отражён в `history.md`. `.docx` печатается на `build-submission` (ходатайство — через `format-doc`; мировое — прежним путём).
- **Если в скилле использован Opus-субагент для red team / стресс-теста / подбора практики** — его аналитика сохранена машинно-читаемым артефактом по правилу «Двухуровневое сохранение для аналитических скиллов»: `.vassal/hearings/{ГГГГ-ММ-ДД}-prep.md` для `prepare-hearing`, `.vassal/analysis/cassation-prep-{ГГГГ-ММ-ДД}.md` для `cassation`. Для `appeal` и `draft-judgment` -- по аналогичному паттерну (если внедрено в SKILL.md).
- Запись в `.vassal/history.md` зафиксирована: имя подаваемого `.md`, prep-артефакта; для `prepare-hearing` — также `.docx` (или fallback) и состояние движка `format-doc`; для `appeal`/`cassation`/`settlement` — пометка «`.docx` откладывается до `build-submission`».

### Категория 4: служебные и сборочные (`update-index`, `catalog`, `backfill-global`, `revise-position`, `build-submission`)

- **`revise-position`:** `.vassal/analysis/retractions.md` -- валидный frontmatter; запись **дописана** (прежние не тронуты), `entries` инкрементирован на 1, `last_updated` обновлён. Если регенерировались секции позиции -- `supersedes`-цепочка корректна, старые файлы не удалены (как в `build-position`). Для типов факт/сущность `index.yaml`/зеркала **не отредактированы молча** -- факт флага зафиксирован в леджере и озвучен Сюзерену; зеркала (`.vassal/mirrors/`) и кросс-дельная память не тронуты. Если правился баннер сводной позиции -- тело позиции не перезаписано. `.vassal/history.md` дополнен записью с формулировкой отзыва и перечнем затронутых артефактов.
- **`update-index`:** перед apply снят backup `.vassal/index.yaml.bak.{timestamp}` (ротация 5). После apply — все ingest-постусловия (см. категорию 1) + проверено обратное отношение «зеркало → запись» (нет orphan mirrors). **Уборка пустых папок (F.16):** предложенные каталоги перенесены в «На удаление/» **только** по подтверждению Сюзерена и **только** фактически пустые; штатные папки `init-case`, «На подачу/», `Архив/` и внутренности `.vassal/` не тронуты (см. «Уборка опустевших папок»). **Архивация как сетка безопасности (F.12):** после сверки в корне не осталось более одного снимка одного типа — лишние предложены к переезду в `Архив/` и перенесены **только** по подтверждению Сюзерена, парами `.md` + `.docx`; служебная зона `.vassal/` не тронута.
- **`build-submission` (F.20):** корень дела разрезолвлен в **абсолютный** путь до первой операции с ФС (правило 4 «Cowork-first robustness»: рабочая директория между вызовами bash не сохраняется). Подкаталог комплекта **фактически** лежит под `{CASE_ROOT}/На подачу/` — проверяется по реальному пути созданного каталога, а **не** сверкой поля `folder` манифеста с самим собой: `folder` пишет этот же скилл по тому же шаблону, поэтому такая «проверка» успешна всегда, в том числе когда папка легла не туда. Полный чек-лист комплекта — [skills/build-submission/SKILL.md](../skills/build-submission/SKILL.md) → Фаза 6.
- **`catalog`:** `Таблица документов.xlsx` создана с колонкой `ID` (doc-id) для двойной ссылки. Все записи `index.yaml` присутствуют в таблице.
- **`backfill-global`:** перед записью каждого целевого глобального файла снят backup `{глобальный путь}.bak.{timestamp}` (ротация 5); при успехе backup удалён, при сбое -- восстановлен. После apply -- все постусловия раздела «Глобальная память» (для пишущих в глобальную): `cases:` без дублей; счётчики инкрементированы ровно на число `new_bullets` (merged не инкрементируют); `backfilled_cases:` обновлено; аппенд-only не нарушен (ни один существующий bullet не удалён, merged-bullets имеют объединённый маркер). Локальный `judge-profile.md` обработанных дел имеет `shared_profile:` во фронтматтере. Соседний (не-канонический) файл при теневом дубле НЕ редактировался. `.vassal/history.md` каждого обработанного дела дополнен записью «backfill-global» со счётчиками.

## Двойные ссылки

**Принцип:** ссылка на документ дела должна быть читаема **и** для человека (юриста), **и** для агента (других скиллов).

**Формат:** `Название документа от ДД.ММ.ГГГГ [doc-NNN]`

Примеры:
- `Договор поставки №47 от 01.06.2025 [doc-042]`
- `Претензия ООО «Ромашка» от 15.08.2025 [doc-088]`
- `Решение Арбитражного суда Красноярского края от 20.03.2026 [doc-201]`

**Где обязательны:**
- Аудируемые выводы (поле `**Источники:**`).
- Сводные аналитические файлы для Сюзерена (`Предварительный анализ документов.md`, позиции).
- Файлы в `.vassal/analysis/*.md`.
- Колонка `ID` в `Таблица документов.xlsx` (от `catalog`).
- **Рабочий перечень приложений** в prep/analysis-артефактах генераторов (`prepare-hearing` §6 prep, `cassation` §7 `cassation-prep`, `appeal` `appeal-prep`, `settlement` `settlement-*-appendices`): каждый пункт — `- NN. Наименование от ДД.ММ.ГГГГ [doc-NNN]`. По нему `build-submission` точно резолвит приложение в файл (E.4.2); нет тега — уход на эвристику с флагом. В **подаваемом** документе перечень остаётся tag-free (см. «Где не нужно»).

**Где не нужно:**
- Имена файлов на ФС (там и так есть имя документа, doc-id хранится в индексе).
- Md-зеркала (`.vassal/mirrors/*.md`) — они и есть документ, frontmatter содержит `id`.
- **Подаваемые процессуальные документы** (`.md`/`.docx` в суд: жалобы, ходатайства, отзывы, мировое и т.п.) — теги `[doc-NNN]` в них **недопустимы**. Двойные ссылки живут в prep-артефакте и в `.vassal/analysis/`, а в filable-тексте — чистые человекочитаемые ссылки на доказательства («приложение №3», «Договор поставки №47 от 01.06.2025»). Разводи рабочий текст (с тегами) и подаваемый (без тегов).

**Зачем:**
- Юрист читает «Договор поставки №47 от 01.06.2025», игнорируя `[doc-042]` визуально.
- Агенты других скиллов парсят `[doc-NNN]` и идут точно по индексу — без fuzzy-матчинга по имени, который ломается при переименованиях, дубликатах с суффиксом `(2)`, опечатках.

**Миграция старых артефактов:** существующие аналитические файлы (без doc-id в источниках) остаются как есть — переписывать историю не нужно. Новые версии при перегенерации добавят `[doc-NNN]` автоматически.

## Дедупликация по `content_hash`

**Поле:** `content_hash: "sha256:<hex>"` в каждой записи `index.yaml` (см. [index-schema.yaml](index-schema.yaml)).

**Когда вычисляется:** при ingest файла (intake / add-evidence / add-opponent), до создания зеркала. Хэш считается от **исходного бинарного содержимого** файла во «Входящие документы/» (он же оригинал на момент приёма), не от md-зеркала. Для `source ∈ {opponent, court}` тот же байтовый оригинал дополнительно сохраняется пристинно в `.vassal/raw/`.

**Проверка дублей перед добавлением:**
1. Скилл вычисляет `content_hash` для каждого файла в пакете.
2. Сверяет с существующими `content_hash` в `index.yaml`.
3. При совпадении — **не создавать новую запись `doc-NNN`**, а:
   - Для `intake`/`add-evidence` (наш клиент): пропустить файл, отметить в preview как «дубль уже обработанного `doc-NNN` — пропускаем».
   - Для `add-opponent`: добавить копию в существующую запись через поле `duplicate_copies` (см. схему `index-schema.yaml`). Это юридически значимо — отмечается, что оппонент представил тот же документ.

**Использование при детекции изменений (`update-index`):**
1. Скилл считает `content_hash` каждого файла на диске.
2. Сравнивает с `content_hash` в индексе.
3. Если хэши не совпадают → файл изменился → пересоздать зеркало, обновить `last_verified` и `mirror_stale: false`, новый хэш записать.

**Использование при автосвязке переименований:**
- Если детектирована «осиротевшая запись» (файл по `file:` отсутствует) **и** «новый файл без записи» с **тем же `content_hash`** — это переименование. Связать автоматически (обновить `file:` в существующей записи), без вопроса Сюзерену.

**Хэши не зависят от имени, времени, метаданных файла — только от содержимого.** Это даёт стабильность относительно переименований, повторных пересылок, копирований.

**Мягкий дедуп (одинаковый контент, разный хэш).** Внутренний таймстамп/метаданные иногда меняют `content_hash` при идентичном содержании (два экспорта одного отчёта). Точный хэш-дедуп их не поймает. Поэтому при ingest: если `content_hash` различается, но **размер и нормализованный текст** (без пробелов/регистра/служебных меток) совпадают с уже имеющейся записью — пометь как **возможный дубль** и спроси Сюзерена в preview, не объединяй автоматически.

## Ownership полей `case.yaml`

Чтобы скиллы не перезаписывали друг другу значения и не возникала «гонка обновлений», каждое поле `case.yaml` имеет **owner-скиллы** — те, кому разрешено его писать. Все остальные читают, но не пишут.

Матрица фиксируется в [case-schema.yaml](case-schema.yaml) v6 в виде комментариев `# writes: <скиллы>` и `# reads: <скиллы>` рядом с каждым полем (или блоком).

Сводно по основным группам:

| Блок | Writes | Reads |
|---|---|---|
| `case.{number, court, judge, category, subject, our_client, representative}` | `init-case` | все |
| `case.judge`, `case.next_hearing`, `case.next_hearing_source` | `init-case`, `analyze-hearing` | все |
| `case.parties` (структура) | `init-case` | все |
| `case.parties` (уточнение реквизитов) | `legal-review` | — |
| `case.amounts.{claim, court_fee}` | `init-case`, `build-position` | `prepare-hearing`, `appeal`, `cassation` |
| `case.qualification` | `legal-review`, `build-position` (только `applicable_norms`) | `build-position`, `prepare-hearing`, `appeal`, `cassation` |
| `case.jurisdiction` | `legal-review`; **`confirmed_by_user` — дополнительно `prepare-hearing`** (фиксация явного подтверждения форума Сюзереном, F.9) | `build-position`, `prepare-hearing`, `appeal`, `cassation` |
| `case.pretrial` | `legal-review` | `prepare-hearing`, `appeal` |
| `case.settlement.*` | `settlement` (основные поля), `analyze-hearing` (`confirmed_date`, если суд утвердил/принял прямо в заседании) | `prepare-hearing` (хук в фазе 2 п.13), `cassation` (если `confirmed_date != null` и обжалуется по ст. 141 АПК) |
| `case.appeal.*` | `appeal` (расчётные), `analyze-hearing` (`hearing_date`, `ruling_date`), `init-case` (фактические поля при постапелляционном входе — `origin: intake`) | `cassation` |
| `case.cassation.*` | `cassation` (расчётные), `analyze-hearing` (`hearing_date`, `ruling_date`), `init-case` (фактические поля при посткассационном входе — `origin: intake`) | — |
| `case.status` | `init-case`, `appeal`, `cassation`, `analyze-hearing`, `settlement` | все |
| `case.timeline` (append-only) | `init-case`, `legal-review`, `analyze-hearing`, `appeal`, `cassation`, `settlement` | все |
| `case.filing_date` | `init-case` | все |
| `case.production_type` (+ `_basis`, `_set_by`, `_set_date`) | `init-case`, `legal-review` | `build-position`, `prepare-hearing`, `appeal` |
| `case.bankruptcy.*` | `init-case` (структура, известные даты), `legal-review` (`registry_close_date`, `procedure`, даты публикации) | `build-position`, `prepare-hearing`, `appeal`, `cassation`, `legal-review` |
| `case.parties[].role_detail` | `init-case` (нач.), `legal-review` (уточнение при смене процедуры) | все |

**Правило:** если скилл не указан в `writes:` для поля — он **не имеет права это поле обновлять**. Если по логике задачи нужно — это сигнал к расширению матрицы (правка conventions + comments в case-schema.yaml), не к молчаливой перезаписи.

При отсутствии файла Notion-функционал безопасно отключается (хуки не предлагают синк, ручная команда явно сообщает о ненастроенности). Путь конфигурируется -- см. раздел «Notion-слой» → «Конфигурация» |

Внешние зависимости могут оказаться недоступны: плагин не установлен, версия несовместима, упал процесс. Скилл **не имеет права тихо упасть** — это особенно опасно для `appeal`/`cassation` (жёсткие процессуальные сроки) и `analyze-hearing` (5 дней на замечания на протокол).

### Где печатается `.docx` (late-binding, две точки)

Оформление в `.docx` происходит **не на каждом шаге**, а в **двух точках**:

1. **`prepare-hearing`** — документ к заседанию (юрист берёт его на заседание, читает заранее).
2. **`build-submission`** — сборка комплекта на подачу: `.docx` печатается из **финальной подаваемой** версии `.md` в момент сборки.

Скиллы-генераторы `appeal` / `cassation` / `settlement` (и `analyze-hearing` → замечания на протокол) выдают **подаваемый `.md`**, а `.docx` печатается позже — на подаче, из последней версии текста. Правки в `.md` дёшевы; `.docx` рождается один раз и **не может отстать** от правок — это конструктивно исключает подачу устаревшего документа (закрывает E.2 / E.4). Ручной запуск `/format-doc` по любому `.md` доступен всегда (например, показать черновик до подачи). Документы вне охвата `format-doc` (мировое соглашение, проект решения, отчёт клиенту) — прежним путём (arbitrum-docx опц. / `.md`).

**Особый случай — `argument-map` (карта доводов).** Печатает свой `.docx` (тип `карта-доводов`, альбомная таблица) **в момент генерации**, не на подаче. Это не противоречит late-binding: карта — **аналитическая таблица-помощник, не подаваемый процессуальный документ** (её нет в комплекте `build-submission`), поэтому риска «подать устаревший `.docx`» нет. Чистая версия печатается сразу, чтобы юрист взял её на заседание; при правках просто перегенерируется.

### Единый паттерн «feature detection + fallback»

Применяется во всех скиллах, использующих внешние зависимости.

**1. Feature detection в начале шага оформления:**
- Для Python-зависимости (**основной путь `.docx`**): попытка импорта `python3 -c "import docx"` в pre-flight (это делает `format-doc`, Фаза 0).
- Для плагина (опц. альтернатива): проверить, что `arbitrum-docx/SKILL.md` доступен, — только если `format-doc` не применим (документ вне охвата) или Сюзерен предпочёл его.
- Для системной утилиты: `which tesseract` / `tesseract --version` с обработкой ненулевого exit code.

**2. При недоступности — graceful degradation:**
- Сохранить **минимально достаточный** артефакт в целевом пути:
  - `.docx`: основной путь — **`format-doc`** (`python-docx`). Нет `python-docx` → создать только `.md` в том же месте + предупреждение. `arbitrum-docx` — опциональная альтернатива, если установлен и предпочтён (или документ вне охвата `format-doc`: мировое, проект решения, отчёт клиенту).
  - Вместо `.xlsx` через xlsx-скилл → создать markdown-таблицу `Таблица документов.md`.
  - OCR: основной путь — **vision** (Read tool по PNG, см. [shared/ocr.md](ocr.md)), не tesseract. Если и vision недоступен (страница не материализуется даже после ретрая) → `needs_manual_review: true` + флаг Сюзерену. Tesseract-спот-сверка опциональна и при отсутствии `rus.traineddata` тихо пропускается (vision-результат остаётся в силе).

**3. Явное предупреждение Сюзерену:**

Шаблон сообщения:
```
ВНИМАНИЕ. Внешняя зависимость недоступна: {имя зависимости}
Сделано: {что именно создано в fallback-режиме, путь}
Что нужно от Сюзерена: {оформите вручную по своему шаблону / установите зависимость и перезапустите / ...}
Срок (если процессуальный): осталось N дней до {дедлайн}
```

**4. Запись в `.vassal/history.md`:** обязательно зафиксировать, что артефакт создан в fallback-режиме (для последующего аудита).

**5. Что НЕ делать:**
- Тихо пропускать создание `.docx` и считать задачу выполненной.
- Импровизировать самодельный рендер в обход `format-doc` (единственная санкционированная нога `.docx` — `scripts/format_doc.py`; при её недоступности fallback — `.md`, не «сверстаю сам»).
- Перепрыгивать на другой формат без предупреждения (например, сохранить `.txt` вместо `.docx`).

## OCR-модуль (извлечение текста)

Единый модуль извлечения текста из документов — **[shared/ocr.md](ocr.md)** (контракт +
агентский протокол) + детерминированная Python-нога [scripts/extract_text.py](../scripts/extract_text.py).
Скиллы, создающие зеркала (`intake`, `add-evidence`, `add-opponent`, `update-index`),
извлекают текст **только по этому протоколу** — прозу OCR-пайплайна не дублируют.

Кратко (полностью — в `shared/ocr.md`):
- **Vision — основной путь OCR** (Read tool по отрендеренным PNG). Системного рус. tesseract в Cowork нет;
  tesseract работает по вендоренному `rus.traineddata` и служит **спот-сверкой критичного поля** —
  второй ногой, независимой от нейросети (`ocr.md` §6; вход «PDF + страница», вердикт машинный).
- **Решающий документ → вторая, независимая голова** (F.18, `ocr.md` §3.2): критичные поля
  перечитывает Opus **без** транскрипции первого чтения, сверяет оркестратор, расхождение → оба
  прочтения в зеркало + `needs_manual_review`. См. раздел «Решающие документы: вторая голова».
- **Кэш по `content_hash`** — vision выполняется один раз на содержимое; зеркало и есть кэш
  (`vision_done` + `content_hash` во frontmatter). Повтор переиспускает зеркало; re-vision — только при смене хэша.
- **Детект мусорного текстового слоя** (mojibake / тонкий OCR поверх скана) → авто-переход на vision,
  а не молчаливый возврат мусора.
- **Структурный режим** для длинных сканов (полнотекст головы + скелет; нельзя цитировать дословно).
- **Пер-полевой confidence** для критичных реквизитов (ИНН/суммы/даты) → `needs_manual_review` + флаг
  гранулярно (один сомнительный реквизит не зануляет весь документ). **Текстовый слой ≠ «скан на сверку»:**
  `method ∈ {pdf-text, docx-parse, text-read}` без scan/garbage-страниц и low-conf полей → `needs_manual_review: false` (E.6.4, `ocr.md` §7).
- **Детект составного пакета** (E.6.2): `extract_text.py` отдаёт `composite_suspected` + `composite_reasons`
  (повтор заголовка-якоря по страницам, множественные ИНН) — скилл приёма предлагает split в preview, не индексирует склейку как один `doc-NNN`.
  Флаг обрабатывают **все три** приёмника (F.19; раньше — только `intake`), и каждая часть после split проходит сверку принадлежности делу отдельно.
- Рендер — через pymupdf в `outputs/` песочницы (не в синкаемые папки), с guard обрезки.

## Проверка консистентности ФС ↔ индекс (Phase 0)

**Зачем:** аналитические скиллы (`study-evidence`, `legal-review`, `build-position`, `prepare-hearing`, `analyze-hearing`, `draft-judgment`, `appeal`, `cassation`) читают `index.yaml` и md-зеркала, но между запусками между ФС и индексом мог накопиться рассинхрон: юрист положил файл мимо `intake`, переименовал зеркало вручную, переложил документ. Без проверки -- скилл анализирует устаревшие данные и формулирует выводы на неполной картине дела.

**Кто обязан выполнять:** все аналитические скиллы, перед началом своей Phase 1 (загрузка контекста).

### Алгоритм Phase 0

1. **Быстрая сверка ФС ↔ индекс** (без полного скана через `update-index`):
   - Прочитай `.vassal/index.yaml` -- получи список путей `file:` для всех записей.
   - Просканируй ключевые папки дела: `Материалы от клиента/` (рекурсивно), все `{ГГГГ-ММ-ДД} *` (рекурсивно), корень дела.
   - Игнорируй (**единый список**, дословно тот же в `update-index` шаг 1 — расхождение по `*.bak.*` снято в F.12):
     - папки: `.vassal/`, `На удаление/`, `Входящие документы/`, `На подачу/`, `Архив/`;
     - служебное: `*.bak.*`, `.DS_Store`, `Thumbs.db`, `desktop.ini`;
     - **аналитические продукты плагина в корне** — строки со знаком «—» в колонке «В индексе» таблицы типов («Актуальное состояние продукта и папка `Архив/`»), включая `Таблица документов.xlsx`. Они в индекс не заводятся by-design, поэтому «новыми файлами» не являются.
   - Сверь множества: `files_on_disk` vs `files_in_index`.

2. **Классификация рассинхрона:**
   - `new_files`: файлы на диске без записи в `index.yaml`.
   - `orphan_records`: записи `index.yaml` без файла на диске, **кроме записей, чей `file:` лежит под игнор-папкой** (`На подачу/`, `На удаление/`, `Входящие документы/`, `Архив/`, `.vassal/` -- см. шаг 1). Их файлы не попадают в `files_on_disk` by-design (папка проигнорирована при скане), поэтому осиротевшими они **не** считаются -- иначе ложный орфан «указывает в „На подачу/“» при живом файле (находка E.4). Для `Архив/` это тот же случай: продукт, уехавший туда по правилу архивации (F.12), — живой файл, а не пропажа.
   - (Устаревшие зеркала отдельно не проверяются здесь -- это работа `update-index`.)

3. **Решение:**
   - **Если рассинхрона нет** (`new_files == 0 and orphan_records == 0`) -- молча перейти к Phase 1. Никаких сообщений Сюзерену.
   - **Если рассинхрон есть** -- предупредить Сюзерена:
     ```
     ВНИМАНИЕ. Рассинхрон ФС ↔ индекс:
       Новые файлы на диске (нет в индексе): N -- {краткий список первых 3-5}
       Осиротевшие записи (нет файла): M -- {краткий список первых 3-5}

     Рекомендация: запустить update-index перед анализом, чтобы анализ работал на актуальных данных.

     Варианты:
     1. Запустить update-index сейчас (рекомендуется)
     2. Продолжить анализ на текущем индексе (риск: новые файлы не учтутся, ссылки на осиротевшие записи будут битыми)
     3. Прервать
     ```
   - Дождаться выбора Сюзерена.
   - Если выбран п.1 -- передать управление `update-index` (либо инструкцией Сюзерену запустить `/vassal-litigator:update-index`, либо явным вызовом скилла), после завершения -- вернуться в текущий скилл и заново начать Phase 0 (она должна пройти чисто).
   - Если выбран п.2 -- зафиксировать в `.vassal/history.md` и в выходном артефакте: «Анализ выполнен на устаревшем индексе ({N} новых файлов, {M} осиротевших не учтены)». Это часть аудируемости.
   - Если выбран п.3 -- завершить.

### Что НЕ делает Phase 0

- Не пересоздаёт зеркала, не вычисляет хэши -- это полная работа `update-index`.
- Не пишет в `index.yaml` ни в каком случае -- только читает.
- Не сравнивает `mtime` / `content_hash` для устаревших зеркал -- этим занимается `update-index`.

Phase 0 -- быстрая проверка «есть ли смысл доверять текущему индексу как полному снимку дела». Полная сверка -- задача `update-index`.

## Cowork-first robustness (закалка под среду)

**Принцип.** Плагин не предполагает чистую, постоянную, рутируемую Linux-машину. Реальная среда Cowork — эфемерная песочница без root, с дефицитным общим диском, ленивым маунтом синкаемой папки (OneDrive) и без доступа к российским правовым базам. Скиллы обязаны быть **недоверчивыми к среде**: проверять фактический результат операции, а не считать, что записалось / прочиталось / установилось / удалилось. Большинство сбоев среды (см. раздел «Известные ограничения Cowork») безопасны, если скилл их детектирует и обходит, и опасны, если действует вслепую.

### 5 правил

1. **Ничему не верить молча (read-back).** После записи критичного файла (`case.yaml`, `index.yaml`, `history.md`, md-зеркала) — перечитать его **тем же каналом** (файловый инструмент) и проверить: размер > 0, контент парсится (для YAML — `yaml.safe_load`), присутствует ожидаемый хвостовой фрагмент. Перед массовыми операциями (копирование пакета, рендер сканов) — проверить свободное место (`df`). Молчаливое усечение на полном диске и обрезанное чтение при рассинхроне маунта так превращаются из тихой порчи в детектируемый отказ.

2. **Один авторитетный канал.** Пишем и верифицируем через **файловый инструмент** (Read/Write/Edit). Чтение свежезаписанного файла через bash-маунт — **совещательное**, не авторитетное: при рассинхроне OneDrive bash какое-то время отдаёт устаревшую/обрезанную копию. На «обрыв» (`unexpected end of stream`), «не видит папку» или cloud-only-файл — **ретрай с паузой** и повторное чтение, а не вывод «контент битый». Cloud-only файлы: сначала Read (материализует файл), потом bash. В скриптах перечисление файлов — через `find`, не через shell-glob (glob ненадёжно раскрывает облачные плейсхолдеры).

3. **Без sudo / apt.** Песочница работает с флагом «no new privileges»: `sudo`/`apt` недоступны. Скрипты не должны их вызывать (а если вызывают опционально — каждая такая команда защищена `|| true`, без `set -e`-обрыва). Python-зависимости ставятся первыми и независимо. Системные пакеты, требующие root (рус. tesseract), не предполагаются — основной путь OCR — vision (см. раздел «OCR-модуль» выше и [shared/ocr.md](ocr.md)).

4. **Абсолютные пути; тяжёлые медиа — порциями; темп — в песочницу.** Рабочая директория между вызовами bash не сохраняется — пути всегда абсолютные. Сканы рендерятся **постранично с downscale** (ориентир ~1200–1700 px по ширине), иначе срыв по таймауту. Временные файлы (PNG-рендеры и пр.) пишутся в `outputs/` песочницы, **не** в синкаемые папки дела (`.vassal/raw/`, корень) — иначе мусор уходит в OneDrive и не вычищается.

5. **Валидация состояния после каждой фазы.** YAML-файлы дела валидируются (`yaml.safe_load`) **после каждой фазы apply**, а не только в конце скилла — порча `case.yaml` множественными мелкими правками ловится сразу, а не на финале.

### Операционные следствия (декларация; реализация — в составе соответствующих изменений схемы/скиллов)

- **Уборка через `mv`.** «Удаление» файла — это `mv` в «На удаление/», а не `cp` + обнуление (`: >`). На маунте `mv` работает надёжно, а `cp`+truncate плодит 0-байтные «пустышки» в рабочих папках. Это заменяет технику из раздела «Папка „На удаление/"» (сам раздел приводится в соответствие в составе доработки уборки). Возвращаемый код `rm` недостоверен (rc=0 без фактического удаления) — на `rm` не полагаемся.
- **`.docx` версионируется, не перезаписывается.** Открытый в Word / синкаемый `.docx` нельзя детерминированно перезаписать (EACCES / Operation not permitted). Поэтому процессуальные `.docx` сохраняются новой версией (`… _v2.docx`), а не перезаписью; при занятом целевом файле — явное предупреждение Сюзерену, не молчаливый сбой. Согласуется с правилом версионирования продуктов («перезапись запрещена»).
- **`raw/` — манифест, не побайтовые копии.** Оригиналы Сюзерена всегда сохраняются локально и синхронизируются в OneDrive независимо от плагина, поэтому `.vassal/raw/` хранит **манифест** (исходное имя, дата получения, пакет приёма, `content_hash`, source, указатель на рабочую копию), а не дубль файла. Пристинная побайтовая копия удерживается только для `source ∈ {opponent, court}` или при явном флаге keep-pristine (chain of custody). Формат закрепляется в `index-schema.yaml`; постусловия ingest-скиллов приводятся в соответствие в составе этой доработки.
- **Сопоставление имён — по нормализованному виду (E.6.5).** Любой матчинг имени файла (резолв «план ↔ файл на диске», дедуп, манифест, привязка приложений) — по **нормализованному** имени, не по байтовому совпадению. Экзотические юникод-пробелы из банк-клиентов и гос-выгрузок (NBSP `U+00A0`, thin `U+2009`, medium-math `U+205F`, narrow-nbsp `U+202F`, figure `U+2007`, word-joiner `U+2060`) молча ломают точный матч → `AssertionError` / «файл не найден» и обрыв apply. Нормализация: все пробельные → обычный пробел, схлопнуть повторы, `strip` (ориентир: `re.sub(r"[\s     ⁠]+", " ", name).strip()`). Тот же NBSP молча ломает `str.replace()` при программной правке Word-текста — там сравнивать по нормализованным/безпробельным якорям и **верифицировать результат чтением** (не полагаться на «заменилось»).

## verify-before-assert (сверка факта до утверждения)

**Принцип.** Аналитические и документные скиллы не имеют права формулировать вывод, довод или текст процессуального документа на **предположении** о содержании документа. Любой опорный **факт, цитата, число, сумма, состав приложений** сверяется по md-зеркалу или оригиналу **до** того, как попадёт в анализ или в подаваемый документ. Это прямое следствие боевых прогонов, где доводы строились на непрочитанных документах (рухнувшая линия защиты, выдуманный платёж, цитата практики с несуществующим выводом) — и спасала только ручная сверка.

### Правила

1. **Сначала сверить, потом утверждать.** Перед использованием факта/цитаты/суммы — открыть зеркало/оригинал и подтвердить. Цитируемая судебная практика должна резолвиться в **локальный** источник: md-зеркало/индекс дела ИЛИ **папку практики в корне дела** («Практика*» и т.п.) — скилл обязан проиндексировать и прочитать такие папки в Фазе 1 (загрузка контекста). Web (vsrf.ru/arbitr.ru) — best-effort, когда доступен; в Cowork РФ-базы часто недоступны (см. «Известные ограничения»), поэтому неподтверждённая локально ссылка — не вывод.
2. **Непроверяемое — флаг-задача, не вывод.** Если факт нельзя сверить по материалам — он оформляется как явная пометка «факт не проверен по материалам — сверить до подачи», а не подаётся как установленный. Это расширяет поле **«Недостающие данные»** раздела «Аудируемость выводов».
3. **Развести «по праву» и «по факту».** В стресс-тесте и аналитике различать **уязвимость по праву** (проверяемую рассуждением — выдаётся как вывод) и **уязвимость по факту** (требующую сверки с материалами — выдаётся как задача на проверку, а не как готовый риск). Иначе стресс-тест плодит ложные риски на догадках.
4. **`needs_manual_review` блокирует.** Зеркало с `needs_manual_review: true` (низкое качество извлечения, ручная сборка без OCR) **нельзя** использовать как источник дословных формулировок/реквизитов в подаваемом документе до OCR-сверки. Допустимо для ориентировки, не для цитирования.
5. **Сверка полноты.** Число и реквизиты единиц, заявленных в описи/расчёте (платёжки, приложения), сверяются с фактически извлечёнными из файла-доказательства; перечень приложений — с реально вложенными документами; суммы — пересчётом (сумма единиц = заявленный итог). Расхождение → `needs_manual_review` + явный флаг Сюзерену, а не молчаливый перенос заявленного числа.
6. **Норма из документа-рассуждения — гипотеза, а не источник (F.8).** Правила 1–5 охраняют **факты** (что написано в документе). Ссылка на **норму права**, взятая из документа, который сам о праве рассуждает, не покрывалась ничем: она не «факт из зеркала» и не «судебная практика» — и проходила в артефакты без единой проверки.

   **Что считается документом-рассуждением:** претензия, чужой иск / отзыв / жалоба, досье или справка куратора, аналитическая записка, письмо с правовой позицией, заключение — **любой документ, который сам рассуждает о праве**, независимо от источника (`client`, `opponent`, `own-work`, `ally`). Не относятся: текст закона, судебный акт, B.3-верифицированный reference, выдача коннектора.

   **Правило.** Ссылка на статью / пункт, пришедшая из такого документа, — **гипотеза до сверки с первоисточником** (текст закона / B.3-reference / коннектор / web-whitelist). Сверяется **содержание нормы, а не наличие номера**: номер бывает верным при полностью перевранном содержании. Не сверено → «норма {X} взята из {документ} — не сверена с текстом закона», а не готовый довод.

   **Боевые случаи, которые правило ловит:** «п. 11 ст. 25.1» из документа клиента разошёлся по всем артефактам двух дел; несуществующее определение КС попало в иск; абз. 2 п. 4 ст. 20.4 ФЗ-127 подан как «управляющий обязан возместить убытки от пополнения компфонда» — норма обязывает возместить **членам саморегулируемой организации**, а не самой СРО (номер верен, содержание переврано). Отчёт 10.07 формулирует корень: «клиентский документ я по умолчанию считал источником, а не гипотезой».

**Зона действия:** `study-evidence`, `legal-review`, `build-position`, `prepare-hearing`, `appeal`, `cassation`, `build-submission`, `settlement`, `draft-judgment`, `analyze-hearing`; правило 6 дополнительно помечается на приёме (`intake` / `add-evidence` / `add-opponent` — строка в EXTRACTION NOTES зеркала). Реализуется как обязательные шаги в соответствующих SKILL.md (в составе доработки этих скиллов).

## Статус вывода о компетенции (F.9)

Вывод о подсудности / компетенции отличается от прочих аналитических выводов: скиллы ниже по конвейеру принимают его как данность и на нём строят документ, а цена ошибки — переписанный иск с пересчётом пошлины (боевой случай: два дела подряд). Поэтому уверенность по этому выводу — **не поле отчётности, а управляющий сигнал**.

**Машиночитаемый статус** пишет `legal-review` в `case.jurisdiction` (см. `shared/case-schema.yaml`): `confidence` (`высокая | средняя | низкая`), `special_norm_checked` (прогонялся ли шаг 0 — профильный закон), `special_norm` (что найдено), `confirmed_by_user`.

**Правило (решение Сюзерена 2026-07-19, F.9):**

| Ситуация | Поведение |
|---|---|
| `confidence: высокая` | Обычный ход |
| Ниже высокой **+ первичная подача** (иск / заявление по существу / заявление об обеспечительных мерах — то есть мы **выбираем** форум) | **Блок**: не переходить к apply, пока Сюзерен явно не подтвердит форум. Подтверждение фиксируется в `case.jurisdiction.confirmed_by_user: true` |
| Ниже высокой **+ документ в идущем деле** (отзыв, ходатайство, пояснения — форум уже определён судом) | **Флаг**, не блок: громкая пометка в preview + предложение заявить о неподсудности отдельным доводом, если основания есть |
| `special_norm_checked: false` | Шаг 0 не прогонялся — вывод о компетенции считается **неполным** независимо от заявленной уверенности |

Почему не блок на всё: там, где суд уже принял дело, останавливать подготовку отзыва бессмысленно — вопрос компетенции превращается из «куда подавать» в «какой довод заявить», и это работа, а не препятствие.

**Зона действия:** `legal-review` (пишет статус), `prepare-hearing` (читает в фазе загрузки контекста). Расширяемо на `appeal` / `cassation` / `settlement` при потребности.

## Дисциплина качества анализа (E.7)

Поверх verify-before-assert — конкретные заточки самопроверки для аналитических скиллов (боевые промахи, которые preview-перед-apply ловил, но лучше не допускать). Все внешние сверки — **best-effort с флагом, не блок** (E.7 [Q1]): в Cowork РФ-базы/веб часто недоступны, поэтому недоступность сверки → **пометка «сверить»**, а не остановка анализа.

1. **Метаданные дела дрейфуют (№ / судья / стадия).** № дела перенумеровывается (в бою `2-3945/2025 → 2-502/2026`), судья меняется (Тутукина → Гореева), стадия уходит вперёд. При анализе — сверить `case.number` / `case.judge` / стадию по **КАД** (kad.arbitr.ru) / **sudrf.ru** (web best-effort). Недоступно → пометка «№/судья/стадия — сверить по КАД перед подачей», не блок. Owner проверки — `legal-review`.
2. **Дословная сверка пункта Пленума / Обзора.** Цитируя конкретный пункт («п. X ППВС / Обзора № Y»), сверь **дословный текст пункта**, а не только номер — номер может быть верным, а содержание перепутано (боевой промах: п. 47 ППВС № 50 процитирован как про запрет выезда — реально это ст. 67 ФЗ-229). Источник дословного текста: **B.3-верифицированный reference-файл** ИЛИ коннектор (CasusLegal / vasrf для практики ВС) / web-whitelist (consultant / garant / vsrf.ru / pravo.gov.ru). Не сверено дословно → «пункт {X} ППВС № {Y} не сверён дословно — проверить текст», не подавать как установленную позицию Пленума.
3. **Не достраивать неподанные ходатайства (E.7 [Q2]).** Процессуальное ходатайство / довод, которого сторона не заявляла и нет во вводной / материалах, — **не готовый довод, а гипотеза**: помечать «гипотеза — подтвердить у Сюзерена». Опасные «резервные» (восстановление срока, зачёт, признание части и т.п.) — с явным предупреждением о риске (напр. заявить восстановление срока = **признать** пропуск). Стратегия вправе предлагать ходатайства (в этом её ценность), но не выдавать выдуманное за решённое.
4. **Повышенный стандарт осмотрительности.** Для **профессионального участника** (профучастник торгов, лицо, для которого сделка — обычная деятельность) применяй повышенный стандарт: дефекты / основания недействительности, очевидные профессионалу при должной осмотрительности, влияют на начало течения давности и на оценку добросовестности. Не занижать довод о давности, презюмируя «обычную» осмотрительность там, где сторона — профессионал (боевой промах: недооценён довод о давности для профучастника торгов).
5. **Стабильный `case_id` коннектора рядом с цитатой практики.** Цитата ВС / ВАС / КС, взятая из коннектора (CasusLegal / vasrf), сопровождается **стабильным `case_id` коннектора** (в reference — рядом с реквизитами; в аналитике — в источниках), чтобы повторная сверка шла по id, а не переформулированным тематическим запросом (тот отдаёт другой набор). Ретрофит существующих reference — в процессе **B.3** (следующая полугодовая сверка); новые цитаты — сразу с `case_id`.

**Зона действия:** `legal-review` (метаданные — п.1; Пленум — п.2), `build-position` (Пленум — п.2; ходатайства — п.3; осмотрительность — п.4; case_id — п.5). Расширяемо на `prepare-hearing` / `appeal` / `cassation`. Реализуется точечными шагами в SKILL.md.

## Чтение трекера задач (Asana/Notion) — опциональный источник истории (E.16)

Трекер задач Сюзерена (Asana / Notion) хранит **историю работы по делу и по фигурантам** (АУ, оппонент): прежние отказы, определения, заметки, задачи. Скилл может прочитать её как **дополнительный источник** — но трекер это **личные заметки, не авторитетный источник права/факта**.

**Механизм (по образцу feature-detection `notion-sync`):**
1. **Проба коннектора** — короткий запрос (Asana MCP `search_tasks` / Notion `notion-search`). Недоступен / не авторизован → **тихий skip**, отметка в `.vassal/`-логе, **не блокировать** (в Cowork-сессии без интерактивной auth это норма, а не ошибка).
2. **Запрос** — по `case.number` (№ дела) + ФИО/наименованиям сторон из `case.parties[]` + ФИО АУ (`parties[]` с ролью «Арбитражный управляющий»). Конфиг (workspace/project) — только для **сужения области**, не обязателен для базового поиска. Запуск **штатный** при доступном коннекторе (E.16 [Q1]).
3. **Оба коннектора независимо гейтятся** — есть только один → работает он; нет обоих → шаг тихо пропускается.

**verify-before-assert для находок (E.16 [Q2], критично).** Находка трекера («два прежних отказа по нашему АУ», «определение по смежному спору») — **лид, а не установленный факт**. Ссылка на судебный акт / определение из трекера **обязана резолвиться в реальный документ в материалах дела** до попадания в подаваемый документ. Скилл: черновит раздел от лида, но помечает «**найдено в трекере: {что}** — подтянуть определение/решение в дело (`add-evidence` / `add-opponent`) и сверить перед цитированием»; в суд цитата идёт только с подтверждённым локальным источником. Это то же правило, что «непроверяемое — флаг-задача, не вывод» (verify-before-assert правило 2).

**Зона действия:** `prepare-hearing` (E.16, штатный шаг перед анализом). Расширяемо на `legal-review` / `build-position` при потребности. **Связь:** это «B.16 наоборот» — тот же коннектор на **чтение** истории; B.16 (пост-MVP) — на **запись** задачи-заседания.

## Известные ограничения Cowork (среда — не лечится плагином)

Эти сбои — свойства песочницы/харнесса, не дефекты плагина. Плагин их **не чинит**, но и **не падает** от них: при таком симптоме — обход по таблице. Перечень — для того, чтобы скилл (и Сюзерен) опознавал симптом и не тратил время на «починку» неисправимого.

| Симптом | Что это | Обход |
|---|---|---|
| `Failed to create bridge sockets` | bash-песочница временно недоступна | не сажать критичный путь только на bash; ретрай; при доступном файловом инструменте работать им |
| Файловый инструмент: `outside connected folders` на `.vassal/`, `outputs/`, части папок дела | непостоянство видимости маунта | работа с состоянием через shell по VM-пути; ретрай с паузой |
| Рассинхрон OneDrive: bash видит устаревшую/обрезанную копию | задержка синхронизации маунта | авторитетный канал — файловый инструмент; ретрай-пауза (см. правило 2) |
| `pdftoppm failed … unsafe location` у файлового Read | растеризатор Read и bash расходятся | ручной рендер в PNG (`pdftoppm`/`pdftocairo`) → Read изображения |
| `/tmp` и пути вне подключённых папок невидимы Read | песочница | темп-файлы — в `outputs/` или подключённую папку (см. правило 4) |
| `rm` → rc=0 без удаления / `Operation not permitted` | bindfs на маунте | уборка через `mv` в «На удаление/» (см. операционные следствия) |
| Диск `/sessions` заполнен → молчаливое усечение записи | общий 10 ГБ том, не чистится изнутри | `df` + read-back (правило 1); чистка — на стороне хоста Сюзереном |
| sudrf.ru: кириллица → `�` | карточки в cp1251, web_fetch декодит как UTF-8 | принудительный декод cp1251 (рендер-движок/Chrome) или добор реквизитов из документов дела |
| Notion-коннектор отдаёт HTML вместо JSON | истёкшая авторизация коннектора | переавторизация; до неё Notion-функции пропускаются (хуки не блокируют) |
| Asana/Notion MCP не авторизован (headless/cron-сессия без интерактивной auth) | коннектор подключается на уровне сессии, не бандлится плагином | чтение трекера (E.16) тихо пропускается — feature-detect + skip, не блок; норма для Cowork без auth |
| AskUserQuestion: `permission stream closed` | сбой харнесса | повторить вопрос; не считать зависанием |
| Форма уточнений всплывает на каждый скилл | хук харнесса | извлекать контекст из материалов до формы (см. доработку elicitation) |
| Сброс счётчика ID задач посреди сессии | харнесс | трассировку прогресса дублировать в `history.md` |
| Потеря контекста диалога между сессиями | харнесс | плагин пишет ВСЁ значимое в `.vassal/`; `history.md` фиксирует не только сделанное, но и **«на чём остановились / открытые решения»**, чтобы следующая сессия продолжила без пользователя |
