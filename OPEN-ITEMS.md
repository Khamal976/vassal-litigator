### A.5. OneDrive conflict copies при параллельной работе ❌ **Принято как ограничение**

**Что сейчас:** если на двух машинах одновременно запустить скиллы, пишущие в один и тот же глобальный файл (например, `judges/Иванов-И-И--АС-N.md`), OneDrive создаст `... (kholv's conflicted copy ...).md`.

**Что задокументировано:** этап 6.1, раздел ограничений -- «не работать параллельно, дать OneDrive 1-2 мин на синк при переключении».

**Возможные fix'ы (отвергнуты):**
- Lock-файл соседом -- race-condition-prone, может застрять.
- Централизованный lock-сервер -- overkill для однопользовательского сценария.

**Решение:** оставить как есть, документация уже есть. Если столкнёшься с реальным конфликтом, разрешать мёрдж руками (аппенд-only логика этому помогает -- ничего не перезаписано, просто две параллельные ветки наблюдений).

Поля: получатель (УФК), ИНН/КПП получателя, банк, БИК, счёт, КБК (зависит от инстанции и кода суда), ОКТМО, статус плательщика («08»/«20» по Приказу Минфина № 58н, с 01.04.2026 -- filing-fees.md §5), назначение платежа («Госпошлина за рассмотрение апелляционной жалобы по делу № … в …»), сумма (округление до рубля -- п. 7 ППВС № 39), сведения о плательщике (п. 7 ППВС № 39 -- допустима уплата представителем/третьим лицом с указанием плательщика).

**Архитектурное решение (черновое):**
- Сумма -- переиспользовать логику filing-fees.md (инстанция × категория × сторона физ/юр), не дублировать.
- Реквизиты -- отдельный шаг с graceful fallback (паттерн ГИР БО, B.7): сайт суда недоступен / калькулятор не парсится -> вывести чек-лист полей для ручного заполнения, не падать.
- Кэш реквизитов суда -- кандидат на глобальную память `$VASSAL_GLOBAL_DIR/courts/{суд}.md` (реквизиты + КБК + дата сверки), переиспользование между делами в одном суде, с предупреждением «реквизиты могли измениться -- сверь на дату подачи» (filing-fees.md §7 п. 5).
- Вывод документа -- кандидаты: (а) через arbitrum-docx как Тип 1 .docx (см. B.2); (б) заполнение готового шаблона платёжного поручения; (в) PDF (есть PDF-tools MCP); (г) просто структурированный блок реквизитов для копипаста в банк-клиент. Решить на этапе детальной структуры.

**Применение:** `appeal` (платёжка под АЖ, пп. 19), `cassation` (под КЖ, пп. 20/21 -- с ветвлением 1-я кассация vs ВС РФ), `legal-review` / `init-case` (под иск 1 инст. -- расчёт по цене иска, пп. 1/2/4). Хук -- в фазе подготовки соответствующего документа («жалоба готова -> нужна платёжка»).

### B.18. Дедуп глобального профиля судьи при стиле «папка-на-обособленный-спор» ⏳ **Находка WS-1c (аудит №2), 2026-06-15**

Семантический дедуп есть только в разовом `backfill-global` (Opus), не в потоковой двойной записи.

**Следствие:** завышение счётчиков заседаний/решений судьи и дублирующиеся наблюдения при стиле «папка-на-спор» + общие заседания. Аналитика судьи валидна по существу, но статистика искажается.

**Что делать (на approve):** в правило двойной записи глобальной памяти добавить дедуп при записи по ключу `(судья, маркер наблюдения)` / `(судья, дата заседания)` -- перед аппендом проверять наличие наблюдения с тем же маркером; при совпадении не дублировать (или пометить «подтверждено из N папок» без инкремента счётчика). Затрагивает `shared/conventions.md` (правило накопления) + `analyze-hearing` (точка записи). Объём небольшой. Альтернатива -- периодически прогонять семантический дедуп `backfill-global`.
