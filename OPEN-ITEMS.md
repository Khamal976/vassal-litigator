**Решение:** оставить как есть, документация уже есть. Если столкнёшься с реальным конфликтом, разрешать мёрдж руками (аппенд-only логика этому помогает -- ничего не перезаписано, просто две параллельные ветки наблюдений).

### B.18. Дедуп глобального профиля судьи при стиле «папка-на-обособленный-спор» ⏳ **Находка WS-1c (аудит №2), 2026-06-15**

Семантический дедуп есть только в разовом `backfill-global` (Opus), не в потоковой двойной записи.

**Следствие:** завышение счётчиков заседаний/решений судьи и дублирующиеся наблюдения при стиле «папка-на-спор» + общие заседания. Аналитика судьи валидна по существу, но статистика искажается.

**Что делать (на approve):** в правило двойной записи глобальной памяти добавить дедуп при записи по ключу `(судья, маркер наблюдения)` / `(судья, дата заседания)` -- перед аппендом проверять наличие наблюдения с тем же маркером; при совпадении не дублировать (или пометить «подтверждено из N папок» без инкремента счётчика). Затрагивает `shared/conventions.md` (правило накопления) + `analyze-hearing` (точка записи). Объём небольшой. Альтернатива -- периодически прогонять семантический дедуп `backfill-global`.

#### F.1. 🔴 CRLF в собранном `.plugin` убивает `setup.sh`, а с ним всю работу с PDF ✅

**Где:** отсутствующий `.gitattributes`, `scripts/setup.sh`, `scripts/build-plugin.ps1`.

**Что:** `core.autocrlf=true` + нет `.gitattributes` → в git блоб чистый (63 LF, 0 CR), в рабочем дереве 63 CRLF; `build-plugin.ps1` пакует **рабочее дерево** → в `dist/vassal-litigator-0.22.0.plugin` `setup.sh` лежит с CRLF. В bash `\`+CR+LF — не продолжение строки: стр. 17 выполняется с лишним аргументом `\r` (`pip` падает на `Invalid requirement: '\r'`), стр. 18 начинается с `||` → syntax error, `exit 2`. Ошибка съедена `2>/dev/null`; стр. 19–63 (fallback, tesseract, libreoffice, блок статуса) **не выполняются вовсе**. Итог: **pymupdf не установлен**, а он единственный путь к PDF — `extract_text.py:272-278` при `ImportError` отдаёт `method: none`, и рендер PNG для vision тоже на `fitz` (`:458-460`), т.е. задокументированный fallback сам требует отсутствующий пакет. Маскируется на машине разработчика: `bash -n` в Git Bash даёт `rc=0`, MSYS2 вырезает CR при чтении.

**Что делать:** `.gitattributes` (`*.sh text eol=lf`, `*.py`, `*.md`) → `git add --renormalize .`; страховка — нормализация переводов строк при упаковке в `build-plugin.ps1`.

**Источник:** выведено при триаже; в отчётах видно только следствие («pymupdf стабильно не ставился» — 15.07, 16.07 ×2).

**Закрыто 2026-07-19.** Три уровня защиты:
1. **`.gitattributes`** (новый файл): `* text=auto eol=lf` + явные `*.sh|*.py|*.md|*.yaml|*.json → eol=lf`; `*.ps1 → eol=crlf` (Windows-only сборка); бинарные ассеты (`*.traineddata`, `*.docx`, `*.xlsx`, `*.pdf`, `*.png`, `*.plugin`) помечены `binary`. Любой свежий клон/checkout получает LF.
2. **Рабочее дерево приведено к LF** — 101 отслеживаемый текстовый файл. Блобы в git уже были чистыми (проверено `git cat-file`), поэтому реального изменения содержимого нет: `git diff` показывает только правку OPEN-ITEMS.
3. **`build-plugin.ps1`** — страховка на случай копии репозитория с иными настройками autocrlf: побайтовая нормализация `*.sh` в staging + **жёсткий гейт** (CR в любом shell-скрипте → сборка падает) + **проверка целостности бинарных ассетов** (размер в staging = размер в источнике).

**Верификация (сквозная).** Дефект воспроизведён строго: реальный фрагмент строк 17–19 с CR → `bash -n` rc=2, `syntax error near unexpected token '||'`; он же без CR → rc=0. Сборка из CRLF-исходника печатает `normalized CRLF -> LF: setup.sh`, в артефакте `setup.sh` CR=0 / LF=63, `bash -n` артефактной версии rc=0, `rus.traineddata` 3 861 738 байт байт-в-байт.

⚠️ **Методическая заметка (пригодится при любой проверке переносов строк на этой машине).** Git Bash/MSYS2 **вырезает CR при чтении файлов** — `cat file | bash -n`, `sed`, а также пайп `python … | bash -n` дают ложное rc=0 на заведомо битом файле. Достоверный способ — подавать байты напрямую: `subprocess.run(["bash","-n"], input=data)`. Первые прогоны этой проверки дали ложноотрицательный результат именно из-за маскировки.

⚠️ **Инцидент при работе (записан как урок).** Второй проход нормализации рабочего дерева не сверялся с `git check-attr` и прошёлся побайтовой заменой по **всем** отслеживаемым файлам, включая `scripts/tessdata/rus.traineddata` — из бинарника пропало 83 байта. Восстановлено `git checkout` (sha256 сходится с блобом). Отсюда и появилась проверка целостности бинарных ассетов в `build-plugin.ps1` (п. 3). **Правило:** массовые побайтовые правки — только по whitelist расширений или по `git check-attr`, никогда «по всем tracked-файлам».

⚠️ **Кириллица в `.ps1`.** Windows PowerShell 5.1 читает `.ps1` без BOM в системной кодировке — комментарии и строки на русском ломают парсер (`Unexpected token`). `build-plugin.ps1` ведётся **на английском ASCII**; это уже отмечено в самом файле применительно к `Get-Content -Raw`.

#### F.2. 🔴 `pymupdf` — жёсткая зависимость без fallback ✅ (рендер-ветка ждёт прогона в Cowork)

#### F.20. 🟡 `build-submission` не проверяет, куда легла папка ✅

**Что:** манифест проверяется явно (`SKILL.md:155`), а что подкаталог лежит именно в контейнере «На подачу/» — нет: префикс задан инструкцией на apply (`:107`), но постусловием не верифицируется. Сверка «упомянуто в тексте, но нет в приложениях» — **есть** (`:76`), вопреки рекомендации отчёта 16.07.

**Уточнено разведкой 2026-07-19 — проблема глубже, чем «забытая проверка»:**
1. **Постусловие `:155` сверяет строку с самой собой.** Оно проверяет, что каталог из поля `folder` манифеста существует, — но `folder` записывает сам же скилл на `:132` по тому же шаблону. Фактически собранный путь с задекларированным не сопоставляется.
2. **Корень риска — относительные пути при неустойчивом CWD.** Все пути в `:107` / `:113-114` / `:132` относительные, а `conventions.md:803` (Cowork-first, правило 4) прямо требует: «Рабочая директория между вызовами bash не сохраняется — пути всегда абсолютные». Поиск по скиллу на `pwd|абсолютн|корень дела|cwd` = 0. Вот откуда берётся «папка легла не туда» — не из отсутствия проверки, а из отсутствия якоря.
3. **`build-submission` не отнесён ни к одной категории постусловий** в `conventions.md` → «Постусловия скиллов» (кат. 1 — ingest, кат. 2 — аналитические, кат. 3 — document-producing, кат. 4 — служебные). Структурный пробел: скилл, физически собирающий комплект на подачу, вне общей рамки самопроверки.

**Закрыто 2026-07-19 (v0.25.0).** Лечится корень, а не симптом:

1. **Якорь `CASE_ROOT`** — Фаза 1 шаг 2, **до первой операции с ФС**: `CASE_ROOT="$(cd "$(dirname .vassal/case.yaml)/.." && pwd)"`. Дальше все пути строятся от него; относительные в скилле не используются. К якорю приведены и соседние места, где путь уезжал бы так же: вызов `format_doc.py`, `--outdir` для `soffice`, rollback Фазы 5.5.
2. **Фактический путь вместо задекларированного** — `mkdir -p "$SUB" && SUB_REAL="$(cd "$SUB" && pwd)"`. В постусловие и в поле `folder` манифеста идёт `SUB_REAL`, а не шаблон.
3. **Постусловие сверяет факт:** реальный путь собранного подкаталога начинается с `$CASE_ROOT/На подачу/`, файлы лежат именно там. В тексте постусловия прямо сказано, **почему** прежняя проверка не была проверкой: `folder` пишет тот же скилл по тому же шаблону, поэтому она успешна всегда — в том числе когда папка легла не туда.
4. **Категория заведена:** кат. 4 переименована в «служебные и **сборочные**» и включила `build-submission` — с собственным пунктом про якорь и сверку факта.

В манифесте `folder` хранится **относительно корня дела** (как `file:` в `index.yaml`) — путь должен пережить перенос папки дела на другую машину; абсолютным он только проверяется.

#### F.16. 🟡 Никто не убирает пустые папки ✅

**Что:** правила нет ни одного (`grep` по «пуст.*папк|rmdir|empty dir» = 0). Пустые «Входящие документы/», подпапки «Материалов», отработанные слоты остаются. Уборка — `mv` в «На удаление/», не `rm` (на маунте `rm` недостоверен).

**Уточнено разведкой 2026-07-19:**
1. **Вся механика «На удаление/» написана про файлы.** `conventions.md:98-115` — «все команды, которым нужно „удалить" **файл**», техника `mv "…/файл.pdf"`; про каталоги ни слова. То есть маршрута для папки не существует даже на уровне конвенции — не «забыли вызвать», а «нечего вызывать».
2. **`intake:128` фиксирует расхождение прямым текстом:** «Если в `Входящие документы/` были вложенные папки — обрабатывай рекурсивно, но только обработанные **файлы**» → файлы уезжают, каталоги остаются. Это и есть боевые «5 пустых папок из 19».
3. **Прецедент уже есть, и он в другую сторону:** `init-case:84` — унаследованная `.vassal/positions/` «**игнорируется**, а не убирается». Решение по F.16 задаёт общий тон: убираем или игнорируем.
4. **Единственное существующее постусловие про уборку** — `conventions.md:540` (только кат. 1, ingest): «служебные файлы процесса (`intake_*.json`, `__pycache__/` и т.п.) убраны из `.vassal/` через `mv`». В нём уже фигурирует **каталог** (`__pycache__/`), но что делать с опустевшим каталогом-источником, не сказано. Симметричных пунктов в кат. 2/3/4 нет.
5. **Естественный хозяин уборки виден из кода:** `update-index` — единственный скилл, который и так сканирует всю ФС дела и уже умеет переносить в «На удаление/».

**Закрыто 2026-07-19 (v0.25.0).** Развилка решена как **`update-index` + подтверждение**.

1. **Маршрут для каталога описан** — новый подраздел «Каталоги — тот же маршрут» в «Папке „На удаление/"». Ключевая оговорка: переносится **только фактически пустой** каталог (либо содержащий один системный мусор). Каталог с содержимым — **никогда**, ни целиком, ни рекурсивно: одно `mv` папки с материалами унесло бы документы дела целиком и незаметно. `rmdir` не используем по той же причине, что и `rm`.
2. **Правило уборки** — новый раздел «Уборка опустевших папок»: хозяин `update-index`; перенос **только с подтверждением** и по каждой папке отдельно (пустая папка часто оказывается заготовкой под будущие материалы); закрытый список неприкасаемых (корень, штатные папки `init-case`, «На подачу/», `Архив/`, всё внутри `.vassal/`).
3. **Реализация в скилле:** шаг 1 собирает пустые каталоги (область шире сканирования записей — включает подпапки «Входящих», опустевшие после `intake`), появился **пятый список** результатов и блок Preview, шаг 15.1 переносит через `mv` с **перепроверкой пустоты между preview и apply**, постусловие 23.1 фиксирует границы.
4. **Прецедент `init-case:84` не отменён, а примирён:** `.vassal/` живёт по своим правилам и под уборку не попадает — правило про рабочие папки дела, которые видит юрист. Служебные временные артефакты убираются отдельным постусловием ingest-скиллов.
5. **Состояние «Сюзерен сказал оставить» нигде не хранится** — оставленная папка будет предложена снова при следующем `update-index`. Это осознанный выбор: навязчивость дешевле молча унесённого слота. В граничных случаях описан способ снять вопрос совсем (положить файл-заглушку).

**Закрыто 2026-07-19 (v0.25.0).** Развилка решена как **«третий сегмент — тип документа»**, суффикс времени — запасной при полном совпадении.

1. **Критерий заведён ровно там, где стоял вопрос** (шаг 6): таблица из пяти пар признаков (одна просительная часть vs своя у каждого; перечислен в приложениях vs не назван нигде; адресован суду самостоятельно; исходящий №; сквозная нумерация листов). **Правило разрешения: перечень приложений основного документа — главный признак.** Признаки противоречат или перечня нет → **спросить в Preview**, не угадывать; образец такого поведения в скилле уже был (документы от нескольких оппонентов).
2. **Несколько актов одной датой** → папка на **каждый**, различаются типом документа. Правило продублировано в конвенции («Именование процессуальных папок») — там же, где живёт формат.
3. **Коллизия имён** (та же дата + сторона + тип; сюда же попадает повторный прогон) → суффикс **`-{ЧЧММ}`** после даты, время из документа, иначе — время приёма. `(2)` для процессуальных папок явно отвергнут: не говорит о содержимом и даёт случайный порядок.
4. **Расхождение терминов снято определением, а не переименованием:** `{действие}` = **тип процессуального документа** (или назначение папки, если документов несколько — «к судебному заседанию»). Так сохранены три места из четырёх, где термин уже использовался (конвенция, `add-evidence`, «Продукты плагина» / «На подачу/»), и исправлено единственное расходящееся — шаг 7 `add-opponent`.
5. **Секция «Идемпотентность» добавлена** — с разбором именно того случая, который упирался в коллизию: папка уже существует (совпало по хэшам → пропуск; новые файлы к тому же документу → доносим; другой акт того же типа и даты → `-{ЧЧММ}`), плюс пристинные копии, глобальный профиль (не инкрементировать `filings_analyzed` дважды) и кэш второго чтения из F.18.

#### F.15. ✅ Приём разложенной вручную папки (2026-07-21, v0.26.0)

**Что:** `conventions.md` → «Папка „Входящие документы/"» — «берут файлы **только** отсюда». Область сужается подпапкой внутри «Входящих» или явным списком файлов; работа по уже организованной вручную папке дела не поддержана. Реакция на пустую папку у трёх скиллов разная: `intake` разово предлагает посмотреть наружу, `add-evidence` советует положить файлы, `add-opponent` просто завершается. **Уточнено разведкой 2026-07-21 — механизм готов, не хватает входа:**

1. **`update-index` технически умеет всё, что нужно** для приёма разложенной вручную папки: рекурсивный обход `Материалы от клиента/`, процессуальных папок `{ГГГГ-ММ-ДД} *` и корня; распознавание типа, даты и сторон; OCR по протоколу `ocr.md`; зеркала; `content_hash`; вторая голова для решающих документов (F.18 — там прямо оговорено «найденный вручную файл может быть решающим ровно так же, как принятый через `intake`»); backup и rollback. Ключевое: он индексирует файл **по тому пути, где тот лежит**, и **ничего не переименовывает** — то есть ровно то поведение, которого ждёт юрист от уже разложенной папки.
2. **Не хватает только входа.** Предусловия `update-index` требуют существующих `.vassal/index.yaml` и `case.yaml`, а его же граничный случай описывает сценарий «структура перенесена с другого диска **без `.vassal/`**» — то есть **скилл не проходит собственные предусловия в случае, который сам и описывает**.
3. **Кольцо разорвано с обеих сторон.** `init-case:35` детектирует «дело ведётся вручную» и обрывается на «переспросить, прежде чем создавать структуру» — **без меню вариантов и без дефолта**, тогда как у соседнего шага 1 меню из трёх опций и дефолт «отмена» есть. Слово `update-index` не встречается в `init-case` **ни разу**; обратная ссылка есть только в `commands/update-index.md` («нет индекса → предложи `init-case`»), то есть отправляет туда, откуда пришли.
4. **Реакция на пустую «Входящие» — три разных поведения**, и общая конвенция («сообщает и завершается») точно описывает только `add-opponent`. `intake` — **единственная в плагине точка приёма файлов не из «Входящие документы/»**: он смотрит в корень дела и в принесённые папки и предлагает обработать найденное. `add-evidence` смотрит не на диск, а в `history.md` — объясняет, куда делись файлы, но маршрута не даёт. Расхождение нигде не оговорено.
