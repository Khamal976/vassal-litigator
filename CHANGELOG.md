## [vassal-litigator] 0.32.0 — G.3: Excel как объект анализа + попутные дефекты среды -- 2026-07-30

Первый пункт **§G** (новые направления). Решения Сюзерена: хозяин анализа — `study-evidence`; плагин `data` привлекается **точечно** поверх своего кода (вариант Б); приём читает **только структуру**; профилей четыре.

### Приём научился читать таблицы

Было: `.xlsx` падал в ветку «неизвестный формат» — пустой текст и `needs_vision: false`, то есть таблицу не читали ни программно, ни глазами, и зеркало выходило пустым **молча**. Хуже, чем у `.doc`/`.rtf`, где хотя бы есть подсказка «используй Read tool».

Стало: `method: table-structure` — структурная сводка в зеркало (листы, шапки **с номерами строк файла**, первые строки, итоговые строки, диапазон дат, **скрытые листы**). Номер строки для таблицы играет роль «л. 4» для бумажного документа: без него цифру нельзя предъявить. Анализ приём не делает — канон отдаёт кросс-документную сверку `study-evidence`.

Отдельно ловится **классическая ловушка выгрузок из 1С и банковских систем**: файл сохранён без кэша вычисленных значений, в Excel суммы видны, а в файле их нет — программное чтение вернёт нули **молча**. Нога сравнивает два прохода по одним координатам и требует пересохранить файл.

### `scripts/analyze_table.py` — аналитическая нога, четыре профиля

- **`debt-calc`** — арифметика построчно, перекрытие периодов (двойной счёт дней), выпадение строки из конвенции счёта дней, итог против суммы строк. Формулу **не навязывает**: подбирает из шести моделей ту, что сходится с данными, иначе честно сообщает «не проверено». Знаменатель — по году каждой строки (365/366), как требует канон F.10.
- **`statement`** — главное здесь **непрерывность остатка**: изъятие операций из середины выписки по датам не видно, а по сальдо видно. На тесте — скрытые 2 000 000 ₽ с указанием строк. Плюс обороты, дубли, дробление платежей, крупнейшие получатели.
- **`registry`** — очереди, **доля голоса без финансовых санкций** (они голосов не дают), дубли ИНН, отсутствие нашего требования как ошибка. Способ расчёта базы печатается в сообщении: вычитать неустойку можно только если колонка суммы её включает.
- **`payments`** — периоды подозрительности гл. III.1 от **даты принятия заявления** (при нескольких заявлениях — первого, п. 7 ППВАС № 35). Периоды вложены, поэтому профиль называет **самый лёгкий применимый состав** и отдаёт кумулятивные суммы. Флаг «± 5 дней от границы»: там один день решает квалификацию. Без анкера считать **отказывается**.

Проверяется одной командой без внешних файлов: `python scripts/analyze_table.py --selftest` — девять сценариев плюс состояние всех зависимостей.

### Встройка в `study-evidence`

Фаза 1.3 (группа таблиц + подтверждение профиля), 2 часть Б (вызов ноги вместо чтения; расписано, что делать с каждым отказом), 3 (**кросс-документная сверка, которая раньше была невыполнима**: требование «сумма платёжек = цена иска» по выписке на 340 листов физически не проверялось, и досье честно писало «дословно не цитируется»), 4 (свой чек-лист зарытого). ### Правило F.10 поднято в канон

Существовало тремя копиями, и они разошлись: в `draft-claim` не было ни источника ставки, ни правила о дате её введения, ни разбивки периода, ни флага при недоступности. ## [vassal-litigator] 0.31.0 — ПЛАН-ДОБИВ блок 4: F.22, каталог образцов (`index-samples`) -- 2026-07-29

Закрывает **блок 4 ПЛАН-ДОБИВа** и **F.22**. Этим **ПЛАН-ДОБИВ выполнен целиком** — все пять блоков.

### Каталог образцов — третья сущность глобальной памяти

Тот же вопрос всплывает в делах годами, а документ по нему уже написан — в другом деле, полгода назад, и найти его можно только памятью Сюзерена. Каталог отвечает на «а не делали ли мы это раньше и где оно лежит», **не втягивая чужую фактуру в текущее дело**.

`$VASSAL_GLOBAL_DIR/samples/{категория-slug}.yaml` — первая сущность памяти, индексирующая **документы**, а не субъектов (до неё были только профили судей и оппонентов).

**Форма — указатель, не копия** (решение Сюзерена 2026-07-21). Запись: номер дела · путь **относительно корня дела** · тип по таксономии · дата · `origin` (`own` / `court`) · производитель · `relation_type` и `applicable_norms[]` из карточки · исход, если известен. Отвергнуты хранение текстов (цена ошибки — чужая сумма или контрагент в поданном документе; тот же класс риска, что вскрыл F.19) и скелет-«рыба» (полезнее, но отдельная функция со своей проверкой вычистки).

**Шардирование по `case.category`** выбрано не ради размера файла, а чтобы **сохранить действующий способ обращения к глобальной памяти**: читатель собирает имя файла детерминированно из карточки своего дела — ровно как собирает имя профиля судьи из ФИО и суда. Разведка показала, что перечисления папки и поиска по ней в плагине нет **нигде**; каталог их и не вводит.

**Абсолютные пути в память не пишутся никогда** (решение Сюзерена): полный путь по факту несёт фамилию клиента и суть спора (типовой вид — `D:/Дела/А33-12345 — оспаривание сделки с Петровым`), а папка едина по всем клиентам и часто синхронизируется облаком. Корень дела резолвится **в момент обращения**, поиском по номеру от родителя текущего дела, и обратно в память не записывается.

**Охват** (решение Сюзерена): подаваемое + аналитика (позиция, карта доводов, проект решения, досье) + **судебные акты**. Акты — самый ценный ориентир: по ним видно, что суд принял, а что отклонил, и конфиденциальности клиента они не затрагивают (публикуются в КАД). **Документы оппонентов не заводятся** — их паттерны ведёт глобальный профиль оппонента.

### `index-samples` — 24-й скилл

Служебный скилл разового наполнения. Механику обхода дел берёт у `backfill-global` (сбор корней с лимитом глубины 4, дедуп по `case_root`, «папка на обособленный спор» — не дубль, Preview → Apply, бэкапы с сохранением только при сбое).

**Skip-критерии переписаны, и это главное отличие:** критерии `backfill-global` («нет профиля судьи», «нет аналитики оппонента») выбросили бы ровно те дела, которые каталогу нужнее всего — с готовыми документами и без разбора заседаний. Здесь дело пропускается, только если карточка невалидна либо в индексе нет ни одной подходящей записи.

Читает по делу **только два файла** — `case.yaml` и `index.yaml`. Тексты документов и зеркала не открываются вовсе; единственное исключение — сопоставление имён файлов в корне для аналитики, которой нет в индексе (позиция, карта доводов и проект решения по таблице F.12 в индекс не заводятся), и содержимое всё равно не читается.

Идемпотентность — по паре `case` + `file`. Обновляется **только** `outcome` (исход становится известен позже документа); расхождение в остальных полях показывается Сюзерену, а не переписывается молча. Переименованный файл даёт битый указатель — скилл его не чинит и не снимает: для этого отдельный режим `--check`, и снятие подтверждает человек (файл мог уехать в `Архив/`, а не пропасть).

### Инкрементальное наполнение — без новой точки

Второй путь пополнения — сами производители, и точка привязки у трёх классов **разная**:

- **подаваемые документы** — в момент, когда производитель заводит продукт в `index.yaml`. Отдельной точки не потребовалось: этот шаг стандартизирован у всех в v0.30.0, когда чинилось «`draft-claim` и `enforcement-adjustment` не оставляют следа»;
- **аналитика** — своё постусловие категории 2, при сохранении сводного продукта. К индексу её привязать нельзя: позиция, карта доводов, проект решения и досье по правилу F.12 в `index.yaml` **не заводятся**;
- **судебные акты** — постусловие ingest-скиллов (категория 1), при приёме документа с `source: court`.

### Чтение — лид, а не материал

Восемь потребителей (`build-position`, `prepare-hearing`, `draft-claim`, `enforcement-adjustment`, `appeal`, `cassation`, `settlement`, `argument-map`) в фазе загрузки контекста собирают имя своего шарда и ищут пересечение по `applicable_norms[]`; при пустых нормах — по `relation_type` + типу документа. Находка подаётся строкой «по этим же нормам в деле {номер} был {тип} от {дата} — открыть?». **Автооткрытия нет, чтения текста найденного документа нет.**

### Три правила подняты в канон

1. **Закрытый список полей записи** — в разделе «Конфиденциальность».
2. **Абсолютный путь к папке дела в глобальную память не пишется никогда.**
3. **Автоматическое копирование текста между делами запрещено.** Прежде этот запрет существовал только как проектное решение в трекере — в `shared/conventions.md` его не было вовсе, то есть сослаться было не на что.

Отдельно записано, что **каталог не отменяет сверку принадлежности делу (F.19)**: переработанный образец понесёт реквизиты другого дела, и вторая ось триажа обязана сработать штатно.

### Состязательная проверка — 6 блокеров, и главный был концептуальным

Реализация ушла на независимую проверку до коммита. Найдено 6 блокеров; три самых важных стоят того, чтобы их назвать:

- **Инкрементального пути не существовало.** Он был записан **постусловием, а не шагом алгоритма** — а постусловие это проверка: без шага оно проверяет пустоту. Ни у одного из 15 производителей записи в каталог не было. Исправлено по-настоящему: явный шаг заведён в 16 файлах — у подаваемых рядом с регистрацией в индексе, у аналитики при сохранении сводного продукта, у приёмников для судебных актов.
- **Утверждение «шаг регистрации в индексе есть у каждого производителя» ложно** — и записано было уверенно, в четырёх местах. Канон на строке 624 сам перечисляет пятерых, кто в индекс не заводит (`build-position`, `legal-review`, `study-evidence`, `argument-map`, `draft-judgment`): их продукты аналитические. Именно поэтому привязок оказалось три, а не одна.
- **Фильтр отбора по `source: own-work` терял 6 продуктов из 15**, включая обе жалобы и всё примирение: `settlement` ставит своим подаваемым `source: client`, `appeal` и `cassation` источник не задают вовсе. Отбор переведён на таблицу артефактов F.12 — как и предписывает канон.

Плюс: обезличивание адресата-физлица работало только в разовом скилле и не было в инкрементальном пути; ключ идемпотентности сменён на `case` + **имя файла без директории**, иначе архивация документа заводила бы вторую запись на тот же образец; задана таблица конверсии `outcome` (словари карточки и каталога не совпадают ни одним значением); режим `--check` получил собственную фазу и перестал требовать путь, которого у него нет.

**Отдельно снято обещание, которое не выполнялось.** Канон утверждал, что переработанный образец поймает сверка принадлежности делу (F.19). Не поймает: документы `source: own-work` под эту сверку **не попадают вовсе** — карв-аут, введённый после боевого случая с выброшенными аналитическими справками. Автоматической защиты здесь нет, и единственный настоящий барьер — запрет копирования. Записано прямо, вместо ложной ссылки на страховку.

Три дефекта нашлись раньше проверки, самостоятельно: адресат-физлицо в имени файла (и одновременное противоречие канону, который контрагентов-юрлиц разрешает); неоднозначный слаг категории — писатель и читатель получали бы разные имена, и каталог тихо распался бы на два файла; отсутствие типа для аналитики в таксономии.

### A.6 — переоценка выполнена

Обещана в постановке блока. **F.22 его не закрывает:** каталог даёт указатель, A.6 требует хранилища **текста** и в нынешней формулировке («библиотека переиспользуемых доводов») упирается в прямой запрет «тексты документов клиентов». Схлопнуть их можно ровно одним способом — редуцировать A.6 до курируемых человеком **пометок поверх записей каталога** (флаг «удачная формулировка» + якорь на документ, без копии); тогда и `templates/` не нужна. Развилка для Сюзерена, в бэклоге A.6 остаётся открытым с этой оценкой.

## [vassal-litigator] 0.30.0 — Смежные дефекты перед блоком 4 + добор блока 3 -- 2026-07-29

Два захода в одном релизе, оба — следствие того, что **субагентов вернули в работу**. Разведка перед F.22 нашла семь дефектов вне реестра; независимая состязательная проверка блока 3 нашла ещё пять, включая **критическую правовую ошибку, которую сам блок 3 записал как достижение**.

### Заход 1 — смежные дефекты (разведка перед F.22)

Семь находок, ни одной из них в трекере не было. Каждая проверена по первоисточнику до правки.

- **F.26 доехал только до писателей.** Восемь скиллов-читателей (`appeal`, `cassation`, `notion-sync`, `build-position`, `analyze-hearing`, `prepare-hearing`, `argument-map`, `settlement`) резолвили `$VASSAL_GLOBAL_DIR` формулировкой, которую канон запрещает **дословно** («а не «разрезолви `$VASSAL_GLOBAL_DIR`» на глаз»). На Windows это молчаливый уход в пустой fallback при верно заданной переменной — скилл работает с нуля по накопленным профилям и не сообщает об этом.
- **Счётчики глобальной памяти: две несовместимые семантики.** `backfill-global` инкрементировал по числу bullet'ов, `analyze-hearing` — по числу заседаний, а детектор задвоения сверял со вторым. Забэкфилленное заседание с восемью наблюдениями давало `hearings_total += 8`, после чего плагин предлагал «поправить» верные данные. Введено правило **«Счётчики считают события, а не наблюдения»**; счёт идёт по уникальным маркерам новых **и слитых** наблюдений (слияние межделовое и часто приносит маркер события, которого в файле не было), с явным исключением под санкционированный повтор B.18a. Старые профили намеренно не мигрируются — расхождение доберёт детектор.

### Заход 2 — добор блока 3 (то, чего он не получил)

Блок 3 делался с отключёнными субагентами: разведка, верификация и «состязательная проверка» шли одной головой. Прогнаны две независимые — правовой слой и конструкция порознь.

#### Правовой слой: критическая ошибка в проде

**«Для изменения способа исполнения — п. 35 ППВС № 50, планка ниже, триггер „очевидные затруднения"»** — записано в справочник, скилл, схему, канон, `ARCHITECTURE` и в CHANGELOG 0.29.0 как один из двух дефектов, «переставивших конструкцию скилла». **Неверно.** П. 35 стоит под заголовком «Окончание и прекращение исполнительного производства» и начинается словами «Окончание исполнительного производства &lt;…&gt; в связи с фактическим исполнением»; стандарта для изменения способа он не содержит. Оборот «очевидными затруднениями» в его абз. 4 — описание ситуаций, на которые распространяется то же правило о допустимости обращения, а не тест.

Действующий тест ВС выводит **прямо из нормы**: изменение способа «допускается только при наличии обстоятельств, затрудняющих исполнение решения суда, либо свидетельствующих о невозможности исполнить решение суда тем способом, который указан в судебном акте» (Определение СКЭС от 04.07.2024 № 307-ЭС24-2577), плюс три ограничителя, которых у отсрочки нет: без изменения существа решения, в пределах заявленных требований, соразмерно первоначальному исполнению (п. 20 Обзора ВС по делам о защите прав потребителей от 18.10.2023). **Планка не ниже — она с дополнительными требованиями.** Практическое последствие прежней ошибки: скилл велел по `method_change` **не доказывать** имущественное положение и опираться на пониженный стандарт.

Остальное по правовому слою:

- **Снят ложноотрицательный флаг по КС № 37-П.** Ч. 1 ст. 358 КАС названа и в предмете рассмотрения, и в резолютивной части, признана не соответствующей Конституции; законодателем не исполнено (норма не менялась с 05.04.2016), предписание КС действует. Новый §4.6 с маршрутом для случая «должник — госорган без лицевого счёта».
- **Новый §4.5 — п. 64 ППВС № 50:** изменение способа через обращение взыскания на долю в ООО. Самый частый случай в арбитраже, в справочнике отсутствовал. Свой круг заявителей (только взыскатель и пристав) и свой узкий предмет доказывания — отсутствие у должника иного имущества, подтверждаемое актом пристава.
- **Новый §4.7 — исполнительский сбор.** У режима не было правового теста вообще: ч. 2.1 ст. 324 АПК, названная стандартом, — процедурная норма. Внесены пп. 74–75 ППВС № 50 (предел уменьшения — не более четверти; для субъекта предпринимательской деятельности освобождение только по непреодолимой силе), расхождение п. 74 с ч. 7 ст. 112 ФЗ-229 (закон называет имущественное положение, Пленум — нет), формула ч. 6 ст. 112 «**с иском**» и её процессуальные последствия (п. 6 ч. 1 ст. 40, ч. 8 ст. 112).
- **П. 25 перестал завышаться.** «Возможность исполнения по истечении срока отсрочки» — пункт **открытого** перечня («в частности, могут относиться»), а не обязательный элемент теста; обязательный элемент один — неустранимость обстоятельств. Возражение «не доказан обязательный элемент» бьётся текстом пункта.
- **Судебная неустойка за период отсрочки не начисляется** — п. 34 ППВС № 7 от 24.03.2016, действующее разъяснение, приведено целиком (период считается **с момента возникновения обстоятельств**, а не с даты определения). Прежняя оговорка «не подтверждено разъяснением ВС» сохранена только для договорных пеней и ст. 395 ГК.
- Мелкое: ч. 2 ст. 37 ФЗ-229 приведена целиком (вторая половина про **меры принудительного исполнения** и решает — арест и списание относятся к ним); ст. 434 ГПК больше не обрывается на середине (её последнее предложение отсылает к ст. 203 — нормы не параллельны); ст. 37 ФЗ-229 про отложение — должнику этот путь не открыт; формула «действительно исключительный характер» годится как авторитет только по 24-КГ15-3, в трёх других актах это пересказ довода нижестоящих судов, который ВС **отверг**; пошлина — «за каждое **самостоятельное требование**» (два требования = 20 000 ₽).

⚠️ **Заявление блока 3 о «сплошном механическом сканировании 88 пунктов» не подтвердилось** — пропущены пп. 64, 74, 75, ровно те, что обслуживают подвиды скилла. Вывод для метода: «просканировано сплошь» — утверждение о процессе, само требующее проверки результатом.

#### Конструкция: три блокера

- **Генерация текста не ветвилась по режиму.** Ветвление было в фазах квалификации и red team, а в фазе, где рождается документ, — одна структура, заявления. В `objection` скилл выдал бы документ с просительной частью «предоставить рассрочку». Теперь три структуры, у каждой своя просительная часть; фазы доказательственной базы и графика помечены «только `request`».
- **Ветка ГПК не была замкнута:** скилл говорил «готовим частную жалобу», но продукта не было, печать шла типом `заявление`, а маршрут вёл в `appeal`/`cassation`, где обжалование таких определений **вне охвата MVP**. Частная жалоба стала полноценным продуктом этого скилла — своё имя файла, `--type жалоба`, своя структура, срок 15 дней (ст. 332 ГПК), строка в таблице F.12.
- **`granted_until` / `schedule` писались дважды с разным смыслом** — сначала запрошенное, потом присуждённое. Карточка показывала отсрочку до определения суда, и от неё пересчитывался срок предъявления исполнительного листа.

#### Схема case.yaml v7 → v8

- Разведены **`requested_until` / `requested_schedule`** (что просим) и `granted_until` / `schedule` (что суд дал).

### `draft-claim` — новый скилл (22-й)

Плагин распознавал претензию как входящий документ в восьми местах, но написать её не мог. Разведка кода **впервые за четыре захода не переставила диагноз**: обвязка действительно была на месте (тип в `TYPE_MAP`, спецификация стиля, поля схемы), отсутствовал только генератор.

## [vassal-litigator] 0.26.0 — Волна 4 §F: файловая гигиена (F.12, F.14, F.15) -- 2026-07-21

Закрывает **волну 4 §F** — последнюю в фазе 3. Адресная разведка кода (урок волны 3, применённый к самой волне 4) снова переставила диагноз: **во всех трёх живых пунктах** проблема оказалась не там, где записана.

**Пять развилок согласованы Сюзереном** (AskUserQuestion, 2026-07-21). Четыре плановые: актуальное состояние считается **по типу артефакта**; архивирует **гибрид** (производитель + `update-index` как сетка безопасности); пользовательский стандарт имён применяется через **параметр имени выхода** `format-doc`; маршрут «принять уже разложенную вручную папку» — **достроить**. Пятая вскрылась при состязательной проверке — **зона действия пользовательской конвенции имён** — и разрешилась не тем, чем ставилась. Сюзерен выбрал «только корень дела», а затем уточнил результат конкретными именами: в корне его устраивает `2026-05-08 Отзыв на иск.docx` (это **дефолт плагина**), в комплекте — `00 Отзыв ООО Ромашка на иск 2026-05-08 8л.docx`. То есть стандарт `Тип_о чём_ДДММГГГГ_на Nл.docx` был **описанием нехватки, а не требованием сменить схему имён**: у слота `00` не было ни стороны-подателя, ни даты (два отзыва по одному делу различались в архиве подач только содержимым). Формат дат отдельно оговорён как **ISO, единый по комплекту** — то есть прямо против `ДДММГГГГ` из исходной формулировки. Внедрять шаблон не потребовалось; потребовались два поля.

**F.12 — это контракт чтения, а не перемещение файлов.** Правило «в корне остаётся последнее» выглядело как уборка, а оказалось изменением того, что читатели найдут на диске. Пять скиллов грузили «все позиции» глобом по корню (`build-position`, `draft-judgment`, `appeal`, `cassation`, `add-opponent`) и после архивации молча деградировали бы до одной версии — **соврали бы, не упав**. Опаснее другое: `cassation` штатно грузит **нашу апелляционную жалобу**, а при `target='ruling_settlement'` — **текст мирового соглашения**; оба по определению старше кассации и при подходе «в корне только самое свежее» уехали бы в `Архив/` первыми, сломав вход того самого скилла, ради которого архивация затевалась. Это не редкий случай, а конструкция обжалования — отсюда и решение считать актуальность **по типу артефакта**. Заведён закрытый список типов с двумя намеренными расхождениями с таблицей «Продукты плагина»: у `build-position` `{тип}` («Начальная» / «Обновлённая») — часть **версии**, у `draft-judgment` `{режим}` — часть **типа** (`appeal` читает именно нейтральный прогноз, явно отвергая проект «в пользу клиента»). Производителей оказалось **11, не 10** (забыт `format-doc`), а `analyze-hearing` кладёт в корень **три** артефакта против одного в таблице.

**Правила «продукты плагина в индексе» не существовало вовсе — найдено при работе.** Ни в конвенциях, ни в `index-schema.yaml`; вместо него — россыпь частных решений: `appeal` и `cassation` свой продукт индексируют, `build-position` / `legal-review` / `study-evidence` / `argument-map` / `draft-judgment` / `analyze-hearing` — нет. Следствие: **позиция в корне при каждой сверке попадала в `new_files`** — Phase 0 поднимала ложный рассинхрон, а `update-index` предлагал прогнать по собственной аналитике плагина OCR и присвоить ей `doc-NNN` как документу стороны. Граница проведена по **назначению артефакта**: подаваемые процессуальные документы индексируются (это материалы дела, на них ссылается `build-submission`), аналитические — нет (это наша мысль о деле, не доказательство). Правило **закрепляет сложившееся поведение**, а не меняет его.

**F.14 — заявленного конфликта не существует, а настоящая боль не была закрыта ничем.** «Плагин требует одно, `format-doc` другое» — не расхождение: граница «документы сторон ↔ продукты плагина» прописана явно и дважды. Реальных расхождений четыре, и они другие: три несогласованных правила суффикса коллизии; **три разные политики под одним словом «перезапись запрещена»** (новый датированный файл / `_v2` при занятом целевом / штатная перезапись живых артефактов) — их смешение и давало боевое «три редакции × три файла = девять», хотя `_v2` возникает **не от правки текста, а только от заблокированного файла**; постусловие `format-doc` «имя `.docx` = имя `.md`», **нарушавшееся по построению** на пути `build-submission`; и `_v2` без правила эскалации. ## [vassal-litigator] 0.25.0 — Волна 3 §F: достоверность приёма и самопроверки (F.16–F.20) -- 2026-07-19

Закрывает **волну 3 §F**. Адресная разведка кода перед работой изменила диагноз **трёх пунктов из пяти**: это оказались не «забытые шаги», а **отсутствующие механизмы**. Отсюда и характер правок — не «добавить проверку», а «завести то, чему нечем было сработать».

**Четыре развилки согласованы Сюзереном** (AskUserQuestion, 2026-07-19): триггер второй головы — **класс документа + ручная пометка**; мёртвую спот-сверку — **оживить**; хозяин уборки пустых папок — **`update-index` с подтверждением**; несколько актов одной датой разводятся **типом документа**.

**F.18 — петля самооценки разомкнута.** Правил эскалации «Haiku → Opus» в плагине не было **ни одного**: все 26 назначений модели статические, по фазе скилла. При этом все три ступени защиты исполнял **тот же Haiku**, что делал транскрипцию, — включая заполнение `quality` и `needs_manual_review`. Уверенно и неверно прочитанная цифра флага не поднимала, а контрольная сумма «разбивка = итог» тут не спасает: в выписке из реестра акционеров и в бюллетене такой пары нет. Что сделано: (1) в таксономию заведена группа **«Корпоративные»** — без классов документов привязка защиты к классу была невозможна в принципе (соседние значения означают другое: `выписка` — банковская, `протокол-заседания` — судебного); (2) появилось понятие **решающего документа** (закрытый список классов + пометка Сюзерена) и **единственное в плагине правило эскалации**, включающееся свойством документа, а не фазой; (3) критичные поля перечитывает **вторая, независимая голова** — Opus получает тот же PNG и **не получает транскрипцию первой**, сверку делает оркестратор сопоставлением значений, а не вопросом модели «согласна ли ты». Расхождение → **оба** прочтения в зеркало (какое верное — решает Сюзерен по оригиналу), поле в `low_confidence_fields`, `needs_manual_review`. **Цена промаха: доля прочитана как «100 %, единственный акционер» вместо 15 %** — переворачивало конструкцию корпоративного спора; спасла бдительность оркестратора, не плагин.

**F.18, вторая часть — спот-сверка была не «поздней», а мёртвой.** Механизм описан в `ocr.md §6` и реализован в коде, но `grep spot` по `skills/` давал **0**: вызывать его было нечем. Причин две, обе сняты. Входом требовался готовый **кроп поля**, которого вызывающему негде взять (геометрию реквизита vision не отдаёт) — теперь вход «**PDF + номер страницы**», а `--region` в долях страницы остаётся запасным путём на случай таймаута. И сверку «прочитано агентом vs прочитано движком» делала на глаз **та же модель** — теперь `--expect` даёт **машинный троичный вердикт** (`match` / `mismatch` / `inconclusive`) с нормализацией разрядов и разделителей (`3 390 000,00` = `3390000`, ведущие нули ИНН сохраняются). Третье значение важно отдельно: без него слепой tesseract поднимал бы флаг на каждом документе и флаг перестал бы что-либо значить.

**F.18, граница, найденная при работе:** вторая голова включается **только там, где цифру прочитала модель**. Документ с текстовым слоем (`pdf-text` / `docx-parse` / `text-read`) проверяется **машинной** сверкой — значение в зеркале обязано буквально встречаться в программно извлечённом тексте; гибрид `pdf-text+vision` — постранично. Гонять Opus по текстовому слою значило бы **заменить точную проверку ещё одним модельным чтением**, то есть ослабить её.

**F.19 — дыра оказалась структурной.** Триаж классифицирует файл по **отношению отправителя к сторонам** — то есть отвечает на вопрос «чей документ», а не «этого ли дела»: ни `case.number`, ни ИНН, ни предмет спора в сверку не входили вовсе. Поэтому документ из соседнего дела за подписью нашего же клиента проходил как совершенно легитимный `client`. Заведена **вторая ось триажа** с ключевой оговоркой: флаг поднимает **только положительное противоречие** (найден реквизит другого дела), а **отсутствие реквизитов — не сигнал**: у памятки, справки, черновика их не бывает по природе. Оба боевых случая учтены: в одном деле поймано 16 чужих документов (номер отличался одной цифрой), в другом — **выброшены как «чужие» две аналитические справки**, которые и вскрыли ошибку по подсудности. ## [vassal-litigator] 0.24.0 — Волна 2 §F: правовые дыры (F.6–F.11) -- 2026-07-19

Закрывает **волну 2 §F** — шесть находок, пойманных боем на шести делах фазы 3. Все они — один класс: **знание в плагине было, а обязанности его прочитать не было**. **F.6 — компетенция: сначала профильный закон, потом кодекс.** `legal-review` шёл от общих правил кодексов (субъектный критерий → предметный → перечни), шага «открыть отраслевой закон» не было; поиск подтверждающей практики под уже сформулированный вывод давал ложную уверенность. Появился **шаг 0** с обязательным следом в выводе («Специальная норма: {норма} | не найдена (проверен {закон})») — пустой результат тоже результат, он показывает, что закон открывали. В `jurisdiction-reference.md` — общая рамка (§1) и подраздел §5 «Споры с арбитражным управляющим вне рамок дела о банкротстве»: **п. 12 ст. 20 ФЗ-127** (охватывает возмещение убытков и отношения с СРО, компетенция не зависит от утраты статуса), опоры — ППВАС № 60 от 23.07.2009 (ред. 17.12.2024) и Президиум ВАС № 6962/11. **Цена промаха: иск переписан в двух делах подряд с пересчётом пошлины.**

**F.7 — у госпошлины появился владелец.** `category-routing §3.4` не вызывался **ни одним** скиллом: справочник был верен и актуален, но на первичном пути его никто не открывал — цифру взяли из старого судебного акта. Теперь `legal-review` (новый блок h) детектирует потребность, называет секцию и требует цену иска, а `build-position` считает и пишет `case.amounts.court_fee` — **с показанным расчётом, а не только результатом**. Снято висячее делегирование в `style-spec.md`, где было написано «сверяет legal-review/build-position» при отсутствии у них такого шага. **Цена промаха: 30 193 ₽ вместо 117 760 ₽.**

**F.8 — норма из документа-рассуждения теперь гипотеза.** `verify-before-assert` охранял факты («что написано в документе»), но ссылка на **статью закона**, взятая из претензии, чужого иска или досье, не подпадала ни под одно правило — она не факт из зеркала и не судебная практика. Новое **правило 6**: такая ссылка — гипотеза до сверки с первоисточником, причём сверяется **содержание, а не наличие номера**. Приём (`intake` / `add-evidence` / `add-opponent`) помечает такие ссылки в зеркале — как флаг происхождения, без блокировки и без `needs_manual_review`. **Класс ошибок:** «п. 11 ст. 25.1» разошёлся по артефактам двух дел; несуществующее определение КС попало в иск; абз. 2 п. 4 ст. 20.4 ФЗ-127 подан как обязанность возместить убытки СРО — норма говорит о **членах** саморегулируемой организации (номер верен, содержание переврано).

**F.9 — вывод о подсудности перестал быть строкой в отчёте.** Уверенность была полем без последствий, а сам вывод о форуме **вообще не читался ниже по конвейеру**. Теперь `legal-review` пишет машиночитаемый статус (`confidence`, `special_norm_checked`, `special_norm`), а `prepare-hearing` читает его в фазе загрузки контекста: ниже высокой + **первичная подача** → блок до явного подтверждения Сюзерена (фиксируется в `confirmed_by_user`); тот же статус в идущем деле → флаг и повод заявить о неподсудности доводом. Блокировать подготовку отзыва там, где суд уже принял дело, смысла нет.

**F.10 — ст. 395: дата начала и ставка.** Дата начала начисления выбиралась молча, хотя вариантов всегда минимум два; ключевая ставка присутствовала только как элемент формулы — без требования источника и актуальности (`grep cbr` по репозиторию давал 0). Теперь: варианты даты предъявляются Сюзерену **с ценой каждого**, основание выбора фиксируется в документе; ставка — со значением, **датой начала действия и источником** (cbr.ru), дата введения берётся из официального сообщения Банка России, а не из даты заседания; период с несколькими ставками разбивается. Источник недоступен → расчёт с явной пометкой «не сверено», а не молча подставленное значение. Симметрично в `prepare-hearing` (просительная) и `draft-judgment` (резолютивная). **Цена промаха: недозаявленные 1,14 млн ₽.**

**F.11 — что квалификация ломает в уже достигнутом.** `build-position` проверял квалификацию только процессуально (не меняет ли предмет/основание). Добавлена вторая проверка — по чек-листу достигнутого (титул, процессуальная замена взыскателя, обеспечительные меры, включённое требование, преюдиция) и **тест «регресс — новое обязательство»**: регресс несовместим с заменой взыскателя, поскольку замена предполагает переход того же требования. Несовместимость подаётся как **развилка Сюзерену с ценой каждой ветки**, не решается молча. В деле фазы 3 процессуально безупречная переквалификация обнулила бы уже полученный титул; поймал юрист, не плагин.

**F.1 — CRLF в артефакте убивал `setup.sh`, а с ним всю работу с PDF.** `core.autocrlf=true` при отсутствующем `.gitattributes` кладёт в рабочее дерево CRLF; `build-plugin.ps1` пакует рабочее дерево → в `.plugin` уезжали виндовые переносы. Дефект воспроизведён строго (`bash -n` rc=2 на реальном фрагменте с CR, rc=0 без него).

**F.2 — `pymupdf` больше не единственный путь к PDF.** Обе ноги уходят на poppler: извлечение (`pdftotext -layout`, страницы по переводу формы (`\f`), без зависимости от `pdfinfo`) и рендер (`pdftoppm`, с учётом **плавающего паддинга имён** — боевая находка 16.07, из-за которой пакетный OCR молча выдавал 0 символов). Найдено при тестировании: poppler на PDF без ToUnicode-карты **молча теряет глифы** (293 симв. у pymupdf против 107 с выпавшей кириллицей) — добавлены два порога в классификатор fallback-пути.

**F.3 — `setup.sh` больше не прячет причину отказа.** Лог вместо `/dev/null`, значимые строки вместо хвоста, `--timeout 60 --retries 3`, поиск `python3 -m pip` → `pip3` → `pip`. Ст. 272.1 регулирует только особенности рассмотрения (единолично, без заседания, без вызова сторон). **Применено:** в таблице явное разделение «ч. 4 ст. 229 АПК (срок); ст. 272.1 АПК (порядок рассмотрения)».

## [vassal-litigator] этап 6.1 -- 2026-05-11

### Fixed
- **Кросс-машинная проблема пути к notion-config.** В этапе 6 путь `~/.vassal/notion-config.yaml` был захардкожен. На Windows `~` резолвится в `C:\Users\{имя}\` -- разные имена пользователей на разных машинах превращали путь в разные физические места без синхронизации. Симметрично проблема существовала бы и для `$VASSAL_GLOBAL_DIR` без env var override (он уже был в этапе 6).

### Added
- Новая переменная окружения `VASSAL_CONFIG_DIR` -- симметричный близнец `VASSAL_GLOBAL_DIR`. По умолчанию `~/.vassal/`. Если задана -- путь к конфигу становится `$VASSAL_CONFIG_DIR/notion-config.yaml`. Типовой сценарий: положить конфиг в OneDrive/Dropbox/Yandex.Disk-папку, на каждой машине установить env var на её локальный путь -- так на двух Windows-машинах с разными именами пользователей работает один и тот же синкаемый файл.

### Changed
- `skills/notion-sync/SKILL.md`: Phase 0 шаг 1 -- явный резолв `$VASSAL_CONFIG_DIR` с fallback на `~/.vassal/`. Раздел «Конфигурация» обновлён под новый путь. Постусловия -- упомянут резолв.
- `commands/sync-notion.md`, `commands/init-case.md`, `skills/analyze-hearing/SKILL.md`, `skills/appeal/SKILL.md`, `skills/cassation/SKILL.md`: хуки и предусловия проверяют конфиг по разрезолвленному пути, а не по жёстко прописанному `~/.vassal/`.
- `shared/conventions.md`: раздел «Notion-слой» → «Конфигурация» расширен описанием `$VASSAL_CONFIG_DIR`. Таблица «Внешние зависимости» обновлена.
- `scripts/notion-init.md`: расширенный раздел 3.1 -- два варианта хранения (А -- одна машина с `~/.vassal/`; Б -- кросс-машинный синк через `reg add /t REG_EXPAND_SZ` с встроенной Windows-переменной `%OneDrive%`); готовые команды; альтернативы (`%USERPROFILE%\OneDrive`, жёсткий путь через `setx`).
- `scripts/notion-config.example.yaml`: header дополнен инструкцией по env var.
- `shared/conventions.md`: подсказка по `REG_EXPAND_SZ` для Windows -- ключевая деталь: `setx` создаёт `REG_SZ` без раскрытия `%VAR%`, поэтому для кросс-машинной конфигурации не годится; нужен `reg add /t REG_EXPAND_SZ`.

### Note about Windows `reg add` vs `setx`
Изначально в этой же ветке предлагалось использовать `setx VASSAL_*_DIR "C:\Users\{имя}\OneDrive\..."`, что требовало знать имя пользователя на каждой машине. Лучшее решение -- `reg add /t REG_EXPAND_SZ /d "%OneDrive%\Документы\Claude Cowork\.vassal-..."`: значение хранится **с литералом `%OneDrive%`**, а Windows раскрывает его под каждого пользователя при создании нового процесса. Одна команда, два разных результата на двух машинах. См. `scripts/notion-init.md` §3.1 для готовых команд.
