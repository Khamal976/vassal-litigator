## 1. Общая концепция

### 1.1. Роли

- **Сюзерен** — юрист-пользователь, который ведёт дело и принимает решения.
- **Вассал** — агент (Claude), который выполняет рутинные и аналитические задачи по указаниям Сюзерена.

### 1.2. Принципы

1. **Агент не принимает решений за юриста.** Вассал анализирует, систематизирует, предлагает — но каждое юридически значимое действие утверждает Сюзерен.
2. **Preview → Apply.** Все команды, изменяющие файловую структуру или карточку дела, работают в два шага: сначала показывают план изменений (preview), затем выполняют только после подтверждения Сюзерена (apply). Это касается: `intake`, `add-evidence`, `add-opponent`, `update-index` (при удалении записей), обновлений `case.yaml` из транскрипций.
3. **Неизменяемость исходников.** Оригинальные файлы, полученные от клиента или оппонента, сохраняются нетронутыми в `.vassal/raw/`. Все переименования и перемещения выполняются как копирование в новое место. Оригинал никогда не удаляется и не перезаписывается.
   > ⚠️ **Ревизия аудита №2 (2026-06): принцип релаксируется.** `.vassal/raw/` переходит на **манифест** (`content_hash` + указатель на рабочую копию) вместо побайтовых копий — оригиналы Сюзерена всегда сохраняются локально и синхронизируются в OneDrive независимо от плагина. Пристинная побайтовая копия удерживается только для `source ∈ {opponent, court}` либо по явному флагу keep-pristine (chain of custody). См. [shared/conventions.md](shared/conventions.md) → «Cowork-first robustness» → операционные следствия. Реализация — в составе доработки ingest-скиллов и `index-schema.yaml`.
4. **Экономия токенов через md-зеркала.** Каждый документ дела при обработке получает полнотекстовое md-представление (канонизированный текст). Агент по умолчанию работает только с md-зеркалами, к оригиналам обращается в исключительных случаях (верификация цитат, проверка визуальных реквизитов). Md-зеркало — это кэш извлечённого текста, а не замена юридически значимого оригинала.
5. **Единый индекс дела.** Все скиллы и команды читают и пишут в один индекс — `.vassal/index.yaml`. Это «память» агента по делу.
6. **Маршрутизация моделей.** Дешёвые операции (саммаризация, классификация) делегируются Haiku через субагентов. Аналитическая работа — Sonnet. Глубокий правовой анализ — Opus. OCR выделен в отдельный pipeline (программный OCR → LLM для интерпретации).
7. **Идемпотентность.** Повторный запуск команды не дублирует файлы и записи в индексе; агент проверяет, что уже сделано.
8. **Аудируемость правовых выводов.** Каждый юридический вывод агента (сроки, подсудность, позиция) сопровождается структурой: заключение, фактическое основание, правовое основание, источники, степень уверенности, недостающие данные.

### 3.1. Правила именования процессуальных папок

Шаблон: `{ГГГГ-ММ-ДД} {Сторона} - {название процессуального документа или действия}`

Примеры:
- `2026-03-01 Истец - исковое заявление`
- `2026-03-15 Ответчик - отзыв на иск`
- `2026-04-01 Истец - пояснения по делу`
- `2026-04-10 к судебному заседанию` (если неясно, к какому документу)

Если составление процессуального документа не планируется, файлы перемещаются в `Материалы от клиента/`.

## 5. Формат индекса документов (index.yaml)

Индекс — это единый реестр всех документов дела. Каждый документ получает уникальный ID (`doc-NNN`), который используется для связи с md-зеркалом.

```yaml
# .vassal/index.yaml
version: 2
last_updated: 2026-03-26T14:30:00

documents:
  - id: doc-001
    file: "Материалы от клиента/Договоры/2025-06-01 ООО Ромашка Договор поставки №47.pdf"
    mirror: "mirrors/doc-001.md"
    type: договор
    title: "Договор поставки №47"
    date: 2025-06-01
    parties:
      - "ООО «Ромашка»"
      - "ООО «Лютик»"
    summary: "Договор поставки строительных материалов. Общая сумма 1 500 000 руб. Срок поставки — 30 дней с момента оплаты."
    seal: true
    signature: true
    completeness: full       # full | partial | fragment
    quality: high             # high | medium | low (качество извлечения текста)
    needs_manual_review: false  # true, если OCR низкого качества
    pages: 12
    source: client            # client | opponent | court | public | ally | own-work (E.9)
    added: 2026-03-26
    processed_by: haiku       # модель, которая обработала документ

    # Происхождение файла
    origin:
      name: "договор поставки.pdf"         # исходное имя файла, как получено
      received: 2026-03-26                   # дата получения
      intake_batch: "intake-2026-03-26"      # пакет приёма (папка в raw/)

    # Целостность зеркала
    mirror_stale: false       # true, если оригинал изменился после создания зеркала
    last_verified: 2026-03-26

    # Бандлы (группы связанных документов)
    bundle_id: null            # ID бандла, если документ входит в группу
    parent_id: null            # ID родительского документа (для приложений)
    role_in_bundle: null       # main | appendix | exhibit

    # Процессуальный статус
    filing_status: null        # null | draft | submitted | filed
    filing_folder: null        # путь к процессуальной папке, если подан

    tags:
      - основной-договор
      - поставка

  - id: doc-002
    file: "Материалы от клиента/Переписка/2025-09-15 ООО Ромашка Претензия.pdf"
    mirror: "mirrors/doc-002.md"
    type: претензия
    title: "Претензия о нарушении сроков поставки"
    date: 2025-09-15
    parties:
      - from: "ООО «Ромашка»"
        to: "ООО «Лютик»"
    summary: "Претензия Ромашки о нарушении сроков поставки по Договору №47. Требование: поставить товар в 10-дневный срок."
    seal: true
    signature: true
    completeness: full
    quality: medium
    needs_manual_review: false
    pages: 2
    source: client
    added: 2026-03-26
    processed_by: haiku
    origin:
      name: "претензия скан.pdf"
      received: 2026-03-26
      intake_batch: "intake-2026-03-26"
    mirror_stale: false
    last_verified: 2026-03-26
    bundle_id: null
    parent_id: null
    role_in_bundle: null
    filing_status: null
    filing_folder: null
    tags:
      - досудебный-порядок

# Бандлы — группы связанных документов (документ + приложения)
bundles:
  # Пример:
  # - id: bundle-001
  #   title: "Исковое заявление с приложениями"

next_id: 3
```

### 5.1. Типы документов (taxonomy)

Поле `type` — из фиксированного перечня:

**Договорные:** `договор`, `дополнительное-соглашение`, `приложение-к-договору`, `спецификация`, `акт`, `накладная`, `счёт`, `счёт-фактура`

**Переписка:** `претензия`, `ответ-на-претензию`, `уведомление`, `письмо`, `требование`

**Процессуальные:** `исковое-заявление`, `отзыв-на-иск`, `ходатайство`, `заявление`, `возражение`, `пояснения`, `дополнение-к-позиции`, `апелляционная-жалоба`, `кассационная-жалоба`

**Судебные:** `определение`, `решение`, `постановление`, `протокол-заседания`

**Платёжные:** `платёжное-поручение`, `выписка`, `справка-из-банка`

**Прочие:** `доверенность`, `выписка-из-егрюл`, `устав`, `свидетельство`, `заключение-эксперта`, `иной-документ`

## 6. Формат MD-зеркала

Каждый документ дела получает полнотекстовое md-зеркало (канонизированное текстовое представление) в `.vassal/mirrors/`. Имя файла — `{id}.md` (например, `doc-001.md`). MD-зеркало — это кэш извлечённого текста для экономии токенов, а не замена юридически значимого оригинала.

```markdown
---
id: doc-001
source: "Материалы от клиента/Договоры/2025-06-01 ООО Ромашка Договор поставки №47.pdf"
type: договор
title: "Договор поставки №47"
date: 2025-06-01
pages: 12
extraction_method: pdf-text    # pdf-text | ocr | docx-parse | image-read | manual
extraction_model: haiku
extraction_date: 2026-03-26
confidence: high               # high | medium | low (качество извлечения)
---

# Договор поставки №47

## от 01 июня 2025 года

**ООО «Ромашка»**, именуемое в дальнейшем «Покупатель», в лице генерального директора Петрова И.И., действующего на основании Устава, с одной стороны, и **ООО «Лютик»**, именуемое в дальнейшем «Поставщик», в лице генерального директора Сидорова А.А., действующего на основании Устава, с другой стороны, заключили настоящий Договор о нижеследующем:

## 1. Предмет договора

1.1. Поставщик обязуется поставить, а Покупатель — принять и оплатить строительные материалы (далее — «Товар») в ассортименте, количестве и по ценам, указанным в Спецификациях, являющихся неотъемлемой частью настоящего Договора.

[... полный текст документа ...]

---
<!-- EXTRACTION NOTES (технические пометки о качестве извлечения) -->
<!-- Страница 7: таблица извлечена приблизительно, проверить оригинал -->
<!-- Страница 11: подпись и печать — визуальная проверка по оригиналу -->
```

### 6.1. Правила создания md-зеркал

1. **Полный текст** — весь текст документа переносится в md, с сохранением структуры (заголовки, пункты, таблицы).
2. **Метаданные в frontmatter** — id, источник, метод извлечения, дата, уверенность.
3. **HTML-комментарии** — только технические пометки о качестве извлечения (проблемные страницы, неточности OCR). Юридические выводы и аналитика агента хранятся в `.vassal/analysis/` и в позициях `{корень дела}/*позиция.md`, а не в зеркале.
4. **Таблицы** — конвертируются в markdown-таблицы.
5. **Изображения** — не переносятся; вместо них ставится `[Изображение: описание]`.
6. **Нечитаемые фрагменты** — помечаются `[Нечитаемо: описание проблемы]`.
7. **Нечитаемые документы** — если OCR даёт низкое качество, документ всё равно получает зеркало с пометкой `confidence: low` и `needs_manual_review: true` в индексе. Агент должен предупредить Сюзерена о таких документах.

## 7. Маршрутизация: OCR pipeline и модели

### 7.1. OCR и извлечение текста (отдельный pipeline)

OCR концептуально отделён от LLM. Сначала программное извлечение, потом LLM для интерпретации.

**Уровень 1 — Программный OCR (бесплатно, детерминированно):**
- PDF с текстовым слоем → `pdftotext` / `pymupdf`
- DOCX → `python-docx` парсинг
- Изображения / сканы без текста → `tesseract` + `ocrmypdf`
- Реализация: `scripts/extract_text.py` + `scripts/setup.sh` (установка tesseract раз за сессию)

**Уровень 2 — MCP-сервер OCR (целевое решение):**
- Локальный MCP-сервер с tesseract, работающий на машине юриста (вне VM Cowork)
- Инструменты: `ocr_file(path) → text`, `extract_pdf_text(path) → text`, `convert_image_to_pdf(path) → path`
- Преимущества: не нужна переустановка каждую сессию, возможность подключить облачный OCR для сложных сканов
- Описывается в `.mcp.json` как опциональный коннектор

**Уровень 3 — LLM fallback:**
- Если программный OCR даёт `confidence: low` — отправить страницу Haiku-субагенту для дочистки
- Для изображений, которые tesseract не берёт (рукописный текст, плохое качество) — Haiku vision

### 7.2. Маршрутизация моделей

Дорогие модели используются только там, где нужна глубина анализа.

| Задача | Модель | Обоснование |
|--------|--------|-------------|
| Создание md-зеркала | Haiku (субагент) | Форматирование извлечённого текста |
| Саммаризация для индекса | Haiku (субагент) | Краткое описание, не юридический анализ |
| Переименование файлов | Haiku (субагент) | Анализ имён и начала документов |
| Систематизация по папкам | Sonnet | Требует понимания контекста дела |
| Составление таблицы | Sonnet | Структурирование данных |
| Первичный правовой анализ | Opus | Глубокий юридический анализ |
| Проверка сроков | Opus | Критически важно — ошибка = потеря права |
| Выработка позиции | Opus | Стратегическое мышление |
| Подготовка к заседанию | Opus | Аргументация, red team/blue team |
| Анализ транскрипции (структурирование) | Sonnet (субагент) | Разбивка, очистка от артефактов |
| Анализ транскрипции (глубокий) | Opus (субагент) | Юридический анализ позиций и рекомендации |
| Генерация процессуальных документов | Opus | Юридическое письмо |
| **Второе чтение критичных полей решающего документа** (F.18) | Opus (субагент) | Единственная **эскалация** в плагине: включается свойством документа (класс/пометка), а не фазой скилла. Читает тот же PNG **без** транскрипции первого чтения — иначе подтвердит прочитанное |

**Почему эскалация вообще понадобилась.** Все остальные строки таблицы — статические назначения по фазе. Приём же читал документ Haiku-субагентом и **им же** оценивал качество этого чтения (`quality`, `needs_manual_review`, пер-полевой confidence): петля самооценки, в которой уверенно и неверно прочитанная цифра флага не поднимает. Правило и список решающих классов — `shared/conventions.md` → «Решающие документы: вторая голова»; протокол чтения — `shared/ocr.md` §3.2.

### 7.3. Реализация маршрутизации

В SKILL.md каждого скилла указывается, какие задачи делегировать субагентам:

```

- Саммаризацию для summary в индексе

Делегируй Opus-субагенту (model: "opus"):

```

### 8.1. intake — Приём и систематизация материалов клиента

**Тип:** скилл + команда (`/vassal-litigator:intake`)
**Модель:** Haiku (скрейпинг) + Sonnet (систематизация)
**Вход:** Файлы в `Входящие документы/`
**Выход:** Переименованные файлы в структурированных подпапках `Материалы от клиента/`, сохранение оригинала = **манифест** (`origin` + `content_hash` в записи индекса; байтовой копии в `.vassal/raw/` для `client`-режима нет — только для `opponent`/`court`), обработанные файлы из `Входящие документы/` → `На удаление/`

**Зависимости:** `init-case` (должна существовать `.vassal/case.yaml`)
**Использует:** Логику file-renamer (шаблон переименования), но адаптированную для юридического контекста
**Маршрутизация (E.5):** триаж «источник по содержимому» перед Preview — обрабатывает только `client`-файлы; `opponent`/`court` предлагает оформить через `add-opponent` (offer-handoff, scope-список); опц. область-аргумент (подпапка/файлы). Контракт — `shared/conventions.md` → «Маршрутизация приёма по источнику»
**Доработки приёма (E.6):** флаг платежа третьим лицом (плательщик ≠ клиент, п. 1 ст. 45 НК); детект составного PDF по машинному сигналу `composite_suspected` из `extract_text.py`; apply — пофайловый commit + рестарт-добор по `content_hash`; `needs_manual_review` от текстового слоя, не от догадки; сопоставление имён по нормализованному виду (юникод-пробелы)
**Дисциплина транскрипции (E.13):** зеркало — дословный транскрипт (общий контракт `shared/ocr.md` §3.1, наследуется всеми зеркало-создателями): без реконструкции/домысливания норм (маркеры пересказа → `[Нечитаемо]` + `needs_manual_review`); контрольная сумма «разбивка = итог» внутри документа — в финальном ответе субагента; роли сторон и непечатные ссылки не выдумывать (позитивную сверку «кто есть кто» ведёт `study-evidence`)
**Робастность приёма (E.14):** `extract_text.py` классифицирует сбой открытия файла — `error_class` (`not_materialized` / `corrupt` / `empty`) + `retryable`. Не-материализованный cloud-only файл (OneDrive-заглушка) → ретрай с паузой (правило 2), **не** ложный «битый PDF»; реально битый (pymupdf не открывает) → ветка «оставить во Входящие + перезалить»; 0-байт → пропуск. Защита цикла страниц от дегидратации mid-read. (в) 0-байтовые пустышки закрыты E.6 (`mv`), (г) дубли raw — content_hash-дедуп + битый не индексируется

**Алгоритм:**

**Фаза 1 — Сохранение оригиналов (манифест-режим):**
1. Прочитать `case.yaml` для контекста (стороны, предмет спора).
2. Забрать файлы из `Входящие документы/` (опц. область-аргумент E.5). Если пуста — проверить корень дела/принесённые папки, затем стоп.
3. Вычислить `content_hash`; зафиксировать **манифест** (`origin.name`, `origin.received`, `intake_batch`, `content_hash`, `source: client`, `raw_pristine: false`). Байтовой копии в `.vassal/raw/` для `client` **не делаем** (оригинал сохранён внешне + рабочая копия в «Материалы»).

**Фаза 2 — Извлечение и анализ (скрытая работа):**
4. Обзор файлов (рекурсивно), распаковка архивов.
5. OCR pipeline по `shared/ocr.md` (`scripts/extract_text.py` → vision при `needs_vision`). **Детект составного PDF (E.6.2):** `composite_suspected` из выхода — предложить split в preview.
6. Анализ имён файлов — категоризация на 3 группы (как в file-renamer); дочтение начала через Haiku при нехватке.
7. Триаж источника (E.5) + **проверка платёжек: плательщик ≠ клиент (E.6.1)** → флаг «третье лицо, п. 1 ст. 45 НК».

**Фаза 3 — Preview (план на утверждение Сюзерену):**
8. Сформировать и показать Сюзерену: план переименования (`ГГГГ-ММ-ДД Отправитель Описание.расш`); структуру подпапок; файлы `needs_manual_review`; предложения split (составные) и offer-handoff (чужие файлы); флаги платежа третьим лицом; уведомление об очистке (Входящие → На удаление).
9. Дождаться подтверждения Сюзерена.

**Фаза 4 — Apply (пофайловый commit, E.6.3):**
10. **Рестарт-безопасность:** по `content_hash` пропустить полностью готовые файлы, достроить частично готовые (след оборванного прогона).
11. **По каждому файлу — атомарная тройка «копия → зеркало → запись индекса сразу»** (не одним блоком в конце): копия (матч имён по нормализованному виду, E.6.5; read-back), md-зеркало (Haiku), запись в `index.yaml` со всеми полями + `next_id`, валидация YAML. Обрыв на N-м оставляет согласованные первые N−1 в деле.
12. `history.md`.

**Фаза 5 — Очистка:**
13. Переместить обработанные файлы `Входящие документы/` → `На удаление/` (через **`mv`**, `rm` на маунте недостоверен). Оригинал не теряется: рабочая копия в «Материалы» + манифест в индексе. Необработанные/сбойные остаются.

**Отличия от standalone file-renamer:**
- Источник — выделенная папка `Входящие документы/`, а не произвольная директория.
- Сохранение оригинала — манифест (`origin` + `content_hash`), а не байтовая копия (для `client`).
- Двухфазный preview → apply; пофайловый commit с рестарт-безопасностью.
- После apply — очистка `Входящие документы/` (через `mv`).
- Добавляется этап систематизации по папкам (file-renamer не перемещает файлы).
- Добавляется создание md-зеркал.
- Добавляется обновление index.yaml.
- Контекст из case.yaml помогает точнее определять стороны.
- OCR через программный pipeline, а не напрямую через LLM.

### 8.3. legal-review — Первичный правовой анализ

**Тип:** скилл + команда (`/vassal-litigator:legal-review`)
**Модель:** Opus (основной анализ)
**Вход:** `case.yaml`, `index.yaml`, вводная от клиента/Сюзерена, md-зеркала
**Выход:**
- Единый документ для Сюзерена: `{case-root}/{ГГГГ-ММ-ДД} Предварительный анализ документов.md`
- Аналитические блоки для агента: `.vassal/analysis/{qualification.md, deadlines.md, pretrial.md, jurisdiction.md, completeness.md, questions-to-client.md}`

**Зависимости:** `catalog` (полный индекс с саммари)

**Выходы/ветки (E.15):** оценку перспектив/рисков `legal-review` **не даёт** — при запросе «оцени перспективы» неблокирующий офер `build-position` (граница чистая; фантомный `risks-preliminary.md` без блока-производителя упразднён). Банкротство без даты публикации → `registry_close_date: null` + `registry_close_basis` с объяснением + критичный запрос клиенту (P0 нерассчитываем — валидный исход, анализ не блокируется).

**Качество анализа (E.7):** сверка метаданных дела (№/судья/стадия) по КАД/sudrf — best-effort + флаг «сверить» (данные дрейфуют); дословная сверка пунктов Пленумов. Контракт — [shared/conventions.md](shared/conventions.md) → «Дисциплина качества анализа (E.7)».

**Алгоритм:**
1. Прочитать `case.yaml`, `index.yaml`.
2. Прочитать вводную от клиента (из текста команды или файла).
3. Загрузить md-зеркала ключевых документов (договор, претензия, иск).
4. Через Opus-субагент выполнить анализ. **Каждый вывод** оформляется в аудируемом формате:
   ```
   **Вывод:** [заключение]
   **Фактическое основание:** [на чём основано]
   **Правовое основание:** [нормы, статьи]
   **Источники:** [doc-001, doc-003]
   **Уверенность:** высокая | средняя | низкая
   **Недостающие данные:** [чего не хватает для уверенного вывода]
   ```

   **a) Ответы на вопросы Сюзерена** (→ `.vassal/analysis/answers.md` и в case-root документ)
   - Краткие ответы на поставленные вопросы.
   - Если указано расписать подробно — развёрнутый ответ.

   **b) Пресекательные сроки** (→ `.vassal/analysis/deadlines.md` и в case-root документ)
   - Исковая давность (общая — 3 года, специальные).
   - Течение, приостановление, перерыв исковой давности.
   - Процессуальные сроки (обжалование, предъявление ИД).
   - Для каждого срока: начало, истечение, статус (действует/истёк/под вопросом).

   **c) Досудебный порядок** (→ `.vassal/analysis/pretrial.md` и в case-root документ)
   - Требуется ли обязательный досудебный порядок.
   - Если да — проверка соблюдения (претензия направлена? срок выдержан?).

   **d) Подсудность** (→ `.vassal/analysis/jurisdiction.md` и в case-root документ)
   - Определение компетентного суда.
   - Проверка пророгационных / дерогационных оговорок в договоре.

   - Перечень документов, которые следует запросить.

5. Собрать весь анализ в один связный документ и сохранить в case root как `{ГГГГ-ММ-ДД} Предварительный анализ документов.md`; предыдущий снимок увести в `Архив/` (F.12).

### 8.8. prepare-hearing — Подготовка к заседанию

**Тип:** скилл + команда (`/vassal-litigator:prepare-hearing`)

**Чтение трекера задач (E.16):** штатный опциональный шаг Фазы 1 (3.3) — при доступном Asana/Notion MCP поиск по `case.number` + ФИО сторон/АУ подтягивает историю (прежние отказы/определения по делу или АУ) как материал для Red team. Коннектор гейтится feature-detect (нет/не авторизован → тихий skip, не блок). Находки — **лиды на сверку** (verify-before-assert): ссылка на акт из трекера резолвится в реальный документ дела до цитаты. «B.16 наоборот» (чтение vs запись). Контракт — [shared/conventions.md](shared/conventions.md) → «Чтение трекера задач (Asana/Notion)».

**Алгоритм (Opus-субагент):**
1. Загрузить полный контекст дела:
   - case.yaml, index.yaml

   - Все отчёты из `.vassal/hearings/` (если были предыдущие заседания)
   - md-зеркала процессуальных документов обеих сторон
2. Учесть:
   - Ранее подготовленные процессуальные документы Сюзерена.
   - Позицию оппонента из его документов и выступлений.
   - Ремарки и позицию судьи (из отчётов о заседаниях).
3. Работа по принципу **red team / blue team**:
   - **Blue team**: аргументы в пользу нашего клиента.
   - **Red team**: контраргументы, которые выдвинет оппонент, и слабости нашей позиции.
   - **Ответ на red team**: как парировать контраргументы.
4. Сформировать текст процессуального документа.
5. **Оформление через `format-doc`** — сохранить подаваемый `.md` (по якорному контракту) → `format-doc` печатает `.docx` (`--type` по документу; `arbitrum-docx` опц., `.md`-fallback при отсутствии `python-docx`). prepare-hearing — одна из двух точек печати `.docx` (вторая — `build-submission`).

В процессуальную папку `.docx` **не кладётся** — это остаток редакции до late-binding; комплект на подачу собирает `build-submission` в «На подачу/».
7. Обновить `index.yaml` и `history.md`.

### 8.13. settlement — Мировое соглашение / отказ от иска / признание иска

**Тип:** скилл + команда (`/vassal-litigator:settlement`)
**Модель:** Opus (трёхсторонняя оценка зоны компромисса + стресс-тест условий)
**Вход:** `case.yaml`, `index.yaml`, позиции, аналитика `build-position` (`strengths.md`, `weaknesses.md`, `risks.md`), глобальные профили (судья, оппонент), переписка вне процесса
**Выход:**
- Сводный документ для Сюзерена: `{case-root}/{ГГГГ-ММ-ДД} Мировое соглашение — анализ и проект.md` (либо аналоги для `withdrawal` / `admission` по `case.settlement.mode`)
- Подаваемые документы (`.md`; `.docx` печатается на `build-submission` через `format-doc`): `{ГГГГ-ММ-ДД} Ходатайство об утверждении мирового соглашения.md` (по умолчанию одностороннее от нашего клиента); `{ГГГГ-ММ-ДД} Заявление об отказе от иска.md`; `{ГГГГ-ММ-ДД} Заявление о признании иска.md`. **Мировое соглашение** (`{ГГГГ-ММ-ДД} Мировое соглашение.md`) — двусторонний документ для подписи обеими сторонами (ст. 140 АПК), **вне охвата `format-doc`**: оформляется вручную как двусторонний (arbitrum-docx опц.)
- Машинно-читаемые секции анализа: `.vassal/analysis/settlement-{ГГГГ-ММ-ДД}-{batna|zone-of-agreement|opponent-forecast|risks|terms-draft}.md`
- Обновление `case.yaml`: блок `case.settlement.*`, статус `pending_settlement → settled | withdrawn`, `timeline`

**Зависимости:** `build-position` (как источник аналитики позиции, желательна); `format-doc` / `build-submission` (оформление `.docx` — late-binding; мировое соглашение — вне охвата)

**Сценарии MVP (по `case.settlement.mode`):**
- `agreement` — мировое соглашение (ст. 138-142 АПК) на любой стадии + исполнительное производство.
- `withdrawal` — отказ от иска нашим истцом (ст. 49 ч. 2, ст. 150 ч. 1 п. 4 АПК).
- `admission` — признание иска нашим ответчиком (ст. 49 ч. 3 АПК; только в 1 инст.).

Зарезервированные значения `mode` (пост-MVP, по ст. 138.6 АПК) — `appeal_withdrawal`, `facts_agreement`, `circumstances_admission`, `tm_consent`. MVP-валидатор отказывает на них (см. `shared/case-schema.yaml` v4, блок `case.settlement`).

**Алгоритм (8 фаз):**

1. **Фаза 0** — Pre-flight + Phase 0 ФС↔индекс. Проверка совместимости `mode × stage` по матрице в case-schema (например, `admission × appeal` блокируется).
2. **Фаза 1** — Загрузка контекста. Помимо стандартного для аналитических — загрузка `build-position` секций (`strengths`, `weaknesses`, `risks`); глобальных профилей судьи (как принимает мировые) и оппонента (договороспособный / уходит от компромисса); расчёт возврата госпошлины по стадии (ст. 333.40 НК: 70% / 50% / 30%).
3. **Фаза 2** — Анализ зоны компромисса (Opus). Трёхсторонняя оценка: BATNA нашего клиента; zone of agreement; прогноз оппонента. Учёт последствий мирового — полное прекращение спора по этому правоотношению (п. 15 ППВАС № 50).
4. **Фаза 3** — Стресс-тест условий (Opus). 3 риска: юридический (чек-лист по пп. 13, 14, 16 ППВАС № 50 + ст. 140 АПК), исполнительный (астрент по Обзору ВС № 3 (2024) п. 32 + индексация по Обзору 18.12.2024 п. 4), тактический.
5. **Фаза 4** — Подготовка документов. Ветвление по `mode` и по `stage` (просительная часть ходатайства об утверждении различается: 1 инст. — прекращение производства; апелляция — отмена решения 1 инст. + прекращение; кассация — отмена актов нижестоящих + прекращение; исполнение — прекращение исполнительного производства). Сохранение подаваемых `.md`; `.docx` печатается на `build-submission` (мировое — вручную).
6. **Фаза 5** — Preview. Сводка зоны компромисса + риски + проекты документов + изменения case.yaml. Выбор Сюзереном формы подачи ходатайства об утверждении (одностороннее по умолчанию / два отдельных / совместное).
7. **Фаза 6** — Apply. Сводный `.md` + подаваемые `.md` документов + машинно-читаемые секции + обновление `case.settlement.*` + `case.status` (`.docx` печатается на `build-submission`).
8. **Фаза 7** — Сводка для Сюзерена (что готово / следующий шаг / deadlines / постусловия Notion-хука).

**Хук в `prepare-hearing`:** в фазе 2 п.13 (Стратегическая оценка) `prepare-hearing` условно предлагает `/vassal-litigator:settlement` при (а) слабой позиции по анализу; (б) `case.settlement.in_progress = true`; (в) явном упоминании мирового Сюзереном. Не блокирующий, не дублирует логику.

**Подключение к downstream:** после утверждения судом — `case.settlement.confirmed_date` фиксирует факт. Если обжалуется определение по ст. 141 ч. 11 АПК — путь через расширенный `cassation` (`cassation.target = 'ruling_settlement'`, 1 месяц со дня вынесения, минуя апелляцию).

**Out of scope MVP** (зарезервировано в OPEN-ITEMS): мировое в банкротстве (гл. VIII ФЗ-127); процессуальные основания ст. 150 АПК (это не примирение); соглашение по обстоятельствам ст. 70 ч. 2 АПК; отказ от жалобы как самостоятельный режим.

### 8.21. draft-claim — Досудебная претензия / ответ на претензию

**Тип:** скилл + команда (`/vassal-litigator:draft-claim`)
**Модель:** Opus (правовая квалификация обязательности порядка; red team отдельным субагентом) + Sonnet (расчёт, сборка текста, печать)
**Вход:** `case.yaml` (`parties`, `our_client`, `pretrial`), `index.yaml`; договор и допсоглашения, первичка по спорной сумме, переписка сторон, предыдущие претензии и ответы; правовой профиль `legal-review/references/pretrial-reference.md`; глобальный профиль оппонента (для red team); в режиме `reply` — входящая претензия
**Выход:**
- `{ГГГГ-ММ-ДД} Претензия {адресат}.md` + `.docx` — режим `claim`; при нескольких должниках **комплект по документу на каждого** (п. 8 ППВС № 18)
- `{ГГГГ-ММ-ДД} Ответ на претензию {адресат}.md` + `.docx` — режим `reply`
- `.vassal/analysis/claim-{ГГГГ-ММ-ДД}-redteam.md`, `claim-{ГГГГ-ММ-ДД}-calc.md`
**Зависимости:** `format_doc.py` тип `претензия` (шапка «Кому/От», без номера дела); хук-предложение из `legal-review` (порядок обязателен, но не соблюдён); правило ст. 395 (F.10) общее с `prepare-hearing` / `draft-judgment`; `intake` / `add-evidence` поставляют квитанции, из которых берётся дата направления

**Единственный документ плагина, адресат которого не суд** — отсюда четыре отличия: дела может ещё не быть (`case.number` пуст); ошибка проявится через месяцы возвратом иска или оставлением без рассмотрения; документ уходит противнику **до** процесса, поэтому red team проверяет не только прочность, но и **преждевременное раскрытие**; претензия **запускает часы** и потому пишет состояние в дело.

**Ядро — три несмешиваемые шкалы времени:** (A) срок добровольного исполнения, который мы даём должнику; (B) срок ожидания перед иском — по общей норме АПК **со дня направления**, по транспорту со дня получения, по связи со дня регистрации; (C) приостановление исковой давности на срок фактического соблюдения (п. 16 ППВС № 43 в ред. п. 49 ППВС № 18; правило п. 4 ст. 202 ГК о шести месяцах **не применяется**).

**`pretrial_date` скилл не проставляет** — документ не отправляется плагином. Дата вносится микро-шагом «претензия направлена» из сообщения Сюзерена (`source: user`) либо извлекается из квитанции / описи / отчёта об отслеживании, принятых во «Входящие» (`source: document`), после чего сразу считается `claim_ready_date`.

**Режим `reply`** зеркален по риску: главное — не сказать лишнего. Признание долга прерывает исковую давность (ст. 203 ГК), при этом «ответ на претензию, не содержащий указания на признание долга, сам по себе не свидетельствует о признании долга» (п. 20 ППВС № 43). Отдельно считается цена досрочного ответа: по п. 22 ППВС № 18 ответ-отказ **снимает** основание для возврата иска и открывает оппоненту суд раньше срока.

**Закрывает B.20.** Детали — [reviews/draft-claim-b20-proposal.md](reviews/draft-claim-b20-proposal.md); верификация правовой базы — [reviews/sources-b.20/pretrial-compass-verification.md](reviews/sources-b.20/pretrial-compass-verification.md).

**Тип:** скилл + команда (`/vassal-litigator:enforcement-adjustment`)
**Модель:** Opus (правовая квалификация подвида и стандарта; red team отдельным субагентом) + Sonnet (график, сборка текста, печать)
**Вход:** `case.yaml` (`enforcement`, `parties`, `our_client`, `amounts`), `index.yaml`; вступивший в силу судебный акт, исполнительный лист, постановление о возбуждении ИП и постановления пристава, финансовые документы под стандарт доказывания; правовой профиль `legal-review/references/enforcement-reference.md`; глобальный профиль оппонента (для red team); в режиме `objection` — заявление оппонента
**Выход:**
- `{ГГГГ-ММ-ДД} Заявление об отсрочке исполнения.md` (варианты по `kind`: о рассрочке / об изменении способа и порядка / об отсрочке взыскания исполнительского сбора) — режим `request`
- `{ГГГГ-ММ-ДД} Возражения на заявление об отсрочке.md` / `{ГГГГ-ММ-ДД} Частная жалоба на определение об отсрочке.md` (ветка ГПК) / `{ГГГГ-ММ-ДД} Заявление о прекращении рассрочки.md` — режимы `objection` / `termination`
- `.vassal/analysis/enforcement-{ГГГГ-ММ-ДД}-redteam.md`, `-disclosure.md`, `-appendices.md`
- **`.docx` не печатает** — late-binding, печать на `build-submission`
**Зависимости:** `format_doc.py` тип `заявление` (обычная процессуальная шапка, изменений не потребовал); хук-предложение из `legal-review` (детект стадии исполнения); развилка с `settlement` (`agreement` × `enforcement`) и с `appeal`/`cassation` (приостановление при обжаловании); `intake` / `add-evidence` поставляют определение суда, из которого берётся результат

**Первый скилл плагина на стадии исполнения.** До него «324» и «434» отсутствовали в коде как класс, а `case.yaml` не имел полей ни для исполнительного листа, ни для исполнительного производства — схема расширена блоком `case.enforcement` и значением `status: enforcement` (**v7**; в **v8** к нему добавлены `our_role`, разведённые `requested_*` / `granted_*`, `draft_date` и `adjustment_history[]`). Побочно закрыта тихая потеря: `settlement` на `stage='enforcement'` печатал номер ИП и реквизиты ИЛ в просительной части, собирая их в диалоге и нигде не сохраняя.

**Три режима, четыре подвида.** `request` / `objection` / `termination` (последний доступен только взыскателю и приставу — п. 26 ППВС № 50 от 17.11.2015). Каждый режим даёт **свой документ со своей просительной частью**; совместимость `mode × kind` проверяется в фазе 0 и блокирует несовместимые пары. Отсрочка и рассрочка — «неустранимые обстоятельства» (п. 25); исполнительский сбор — **без госпошлины** (п. 79).

> 🚫 **Снято как неверное (2026-07-29):** «изменение способа и порядка — „очевидные затруднения" (п. 35, планка ниже); смешение п. 25 и п. 35 — главная ошибка жанра». П. 35 ППВС № 50 от 17.11.2015 посвящён окончанию исполнительного производства в связи с фактическим исполнением; стандарта для изменения способа он не содержит, а действующая формула ВС по ст. 324 АПК — ограничительная, а не смягчающая. Так же снято, что ч. 2.1 ст. 324 АПК задаёт стандарт для исполнительского сбора: это процедурная норма, тест даётся пп. 74–75 того же Пленума. Дефект пришёл из compass-справочника и пережил верификацию F.21, потому что заявленное «сплошное сканирование 88 пунктов» пропустило пп. 64, 74, 75 — ровно те, что обслуживают подвиды скилла. Правовой профиль пересматривается.

**Наша сторона в исполнении — отдельное поле.** `case.enforcement.our_role` (`debtor` | `creditor`): право по ч. 1 ст. 324 АПК есть у обеих сторон, и от роли зависят доступные подвиды, предмет доказывания и роль red team-субагента. Прежде скилл по умолчанию считал клиента должником.

**Три процессуальных режима, а не два.** АПК — месяц, заседание с извещением; ГПК — 10 дней **без заседания и без извещения** (ст. 203.1); КАС — 10 дней, но заседание с извещением. Отсюда следствие: режим `objection` в СОЮ по умолчанию некуда подать «до» и он вырождается в частную жалобу (та же ст. 203.1 даёт суду право при необходимости вызвать лиц в заседание — но рассчитывать на это нельзя).

**Специфический риск режима — раскрытие.** Заявление должника держится на доказательствах имущественного положения, то есть добровольно передаёт взыскателю карту активов и дебиторки. Red team отвечает на это отдельным вопросом («что мы раскрыли и что это позволит сделать завтра»), а результат идёт в самостоятельный артефакт `-disclosure.md`. Сопутствующий риск — **ч. 3 ст. 324 АПК**: получив отсрочку должнику, суд вправе по заявлению взыскателя наложить обеспечительные меры.

**Закрывает F.21 (и слитый в него B.6).** Верификация правовой базы — [reviews/sources-f.21/enforcement-compass-verification.md](reviews/sources-f.21/enforcement-compass-verification.md).

### 8.23. index-samples — Разовое наполнение каталога образцов

**Тип:** служебный скилл + команда (`/vassal-litigator:index-samples`)
**Модель:** Sonnet (чистая механика: обход, отбор, запись; правовых суждений нет)
**Вход:** корни дел (аргументы команды); по каждому делу — только `.vassal/case.yaml` и `.vassal/index.yaml`
**Выход:** записи-указатели в `$VASSAL_GLOBAL_DIR/samples/{категория-slug}.yaml`; строка в `.vassal/history.md` каждого обработанного дела
**Зависимости:** `$VASSAL_GLOBAL_DIR` (F.26); механика обхода дел общая с `backfill-global`

**Закрывает F.22.** Отвечает на вопрос «а не писали ли мы это раньше и где оно лежит» — **не втягивая чужую фактуру в текущее дело**. Форма согласована Сюзереном: **указатель, не копия**. Отвергнуты хранение текстов (цена ошибки — чужая сумма в поданном документе, тот же класс риска, что вскрыл F.19) и скелет-«рыба» (отдельная функция со своей проверкой вычистки).

**Родство и различие с `backfill-global`.** Механика обхода дел одна (сбор корней с лимитом глубины 4, дедуп по `case_root`, «папка на обособленный спор» — не дубль, Preview → Apply, бэкапы). Различие принципиальное: `backfill-global` переносит **наблюдения** о субъектах, `index-samples` заносит **адреса документов**. Отдельно переписаны skip-критерии: критерии `backfill-global` («нет судьи», «нет аналитики оппонента») выбросили бы ровно те дела, которые каталогу нужнее всего — с готовыми документами и без разбора заседаний.

**Что заносится** (решение Сюзерена 2026-07-29): подаваемое + аналитика (позиция, карта доводов, проект решения, досье) + **судебные акты**. Акты — самый ценный ориентир: по ним видно, что суд принял, а что отклонил, и конфиденциальности клиента они не затрагивают (публикуются в КАД). Документы оппонентов **не заносятся** — их ведёт глобальный профиль оппонента.

**Адресация без абсолютных путей.** Полный путь к папке дела по факту несёт фамилию клиента и суть спора, а глобальная папка едина по всем клиентам и часто синхронизируется облаком, — поэтому в каталоге лежат только номер дела и путь **внутри** дела. Корень резолвится в момент обращения поиском по номеру и обратно в память не пишется.

**Наполнение двумя путями:** этот скилл — разово, по команде; инкрементально — сами производители. Для **подаваемых** документов точка привязки — шаг регистрации продукта в `index.yaml` (стандартизирован у всех в v0.30.0). Для **аналитики** привязка другая и отдельная: позиция, карта доводов, проект решения и досье по правилу F.12 в индекс **не заводятся**, поэтому у категории 2 своё постусловие — запись в каталог делается при сохранении сводного продукта. Судебные акты — постусловие ingest-скиллов (категория 1).

## 9. Взаимосвязи скиллов

```
init-case
    │
    ▼
  intake ──────────► catalog
    │                   │
    ▼                   ▼
add-evidence        legal-review
add-opponent            │
    │                   ▼
    └──► update-index   build-position ────┐
              │              │             │
              ▼              ▼             ▼
         prepare-hearing ◄───┘         settlement
              │   │                    (мировое /
              │   │ (хук фаза 2 п.13)   отказ /
              │   └──────────────────►  признание)
              ▼                              │
       analyze-hearing                       │
              │                              │
              ▼                              ▼
    ┌─── draft-judgment            case.status =
    │                              settled | withdrawn
    ▼                              (или → cassation
  appeal                           по ст. 141 АПК)
    │
    ▼
  cassation
```

**Критический путь:** init-case → intake → catalog → study-evidence → legal-review → build-position → prepare-hearing

**Циклические:** add-evidence, add-opponent, update-index, prepare-hearing, analyze-hearing — вызываются многократно по ходу дела.

**Ответвления (примирительный трек):** `settlement` может быть запущен на любой стадии — из `prepare-hearing` (через хук в фазе 2 п.13), из `build-position` (когда анализ позиции даёт «слабо, лучше уступить»), напрямую (когда оппонент прислал проект мирового). Возможные стадии — `1inst / appeal / cassation / enforcement` (ст. 139 АПК). Поток замыкается на `case.status` (settled / withdrawn) или, при обжаловании определения об утверждении мирового, уходит в `cassation` с `target='ruling_settlement'`.

**Аналитический шаг (study-evidence)** -- между `intake` и `legal-review` / `build-position`: собирает фактологическое досье (`.vassal/analysis/evidence-dossier.md`) с фактами со ссылкой на лист, которое нижестоящие скиллы читают вместо поверхностного summary. `legal-review`, `build-position`, `prepare-hearing` при отсутствии досье предлагают его собрать (хук, не блокирует). См. §8.17.

**Карта доводов (argument-map)** -- тактический аналитический выход, **предлагается** (хук, не блокирует) из `build-position` (после позиции) и `prepare-hearing` (к заседанию): сводит доводы оппонента × наши контрдоводы в таблицу по узлам спора, подтягивает практику через CasusLegal, печатает чистую (для суда) и рабочую (для себя) версии. Не на критическом пути. См. §8.20.

**Обратное распространение правок (revise-position)** -- служебный проход между генерирующими скиллами: когда позиция правится по ходу дела, `revise-position` пишет леджер отзывов `.vassal/analysis/retractions.md`, а `build-position`, `prepare-hearing`, `appeal`, `cassation`, `settlement` читают его как **фильтр отозванного** (read-хук) -- чтобы отозванный вывод не воскрес из осевшего в служебном слое старого состояния. `prepare-hearing` / `build-position` при правке в драфте **предлагают** прогнать `revise-position` (не блокируя). Закрывает **E.2**. См. §8.19 и [shared/conventions.md](shared/conventions.md) → «Леджер отзывов позиции».

**Глобальная память (кросс-дельная)** -- ортогональный слой, общий для всех дел (см. раздел 15). Основные потоки данных через неё:
- `analyze-hearing`, `draft-judgment` → `$VASSAL_GLOBAL_DIR/judges/` (двойная запись профиля судьи).
- `add-opponent`, `analyze-hearing` → `$VASSAL_GLOBAL_DIR/counterparties/` (двойная запись профиля оппонента).
- `prepare-hearing`, `build-position`, `appeal`, `cassation`, `analyze-hearing`, `draft-judgment` ← читают глобальные профили **до** анализа как фон.

**Notion-слой (опционально)** -- если настроен `~/.vassal/notion-config.yaml`, скилл `notion-sync` (вызывается вручную через `/vassal-litigator:sync-notion` или предлагается хуками после `init-case` / `analyze-hearing` / `appeal` / `cassation`) пушит метаданные дела и глобальный профиль судьи в Notion-базы `Cases` и `Judges`. Односторонне, без обратного синка. См. раздел 15.7 и [skills/notion-sync/SKILL.md](skills/notion-sync/SKILL.md).

## 10. Оформление `.docx`: `format-doc` (основной) + `arbitrum-docx` (опц.)

**Основной путь — `format-doc`** (in-plugin, `python-docx`; §8.18). Оформление `.docx` — **late-binding**: печать привязана к точке потребления документа, актуальный перечень точек — [shared/conventions.md](shared/conventions.md) → «Где печатается `.docx`» (основная — `build-submission`; сразу печатают `prepare-hearing`, `draft-claim`, `argument-map`):
- **`prepare-hearing`** — документ к заседанию;
- **`build-submission`** — сборка на подачу: `.docx` печатается из финального подаваемого `.md` (слот `00`).

`appeal` / `cassation` / `settlement` / `analyze-hearing` (замечания на протокол) выдают **подаваемый `.md`** — `.docx` печатается позже (на подаче или вручную `/format-doc`), из финальной версии текста, поэтому не отстаёт от правок (конструктивно снимает риск устаревшего `.docx`, E.2/E.4).

**`--type` по документу:** `жалоба` (appeal / cassation) · `отзыв` / `ходатайство` / `заявление` / `возражение` / `пояснения` (prepare-hearing) · `ходатайство` / `заявление` (settlement) · `замечания-на-протокол` (analyze-hearing) · `претензия`.

**Вне охвата `format-doc`** (прежний путь / ручное оформление; `arbitrum-docx` — опц. альтернатива):
- **мировое соглашение** (`settlement`) — двусторонний документ (ст. 140 АПК): «Сторона 1» / «Сторона 2», подписи обеих сторон, без «отправитель → адресат». Материально иной формат, чем процессуальная жалоба.
- **проект судебного решения** (`draft-judgment`) — судебный акт (вводная / описательная / мотивировочная / резолютивная; состав суда вместо «отправителя», без подписи представителя). Генерирует `.docx` напрямую.
- **отчёт клиенту** (`analyze-hearing`, Тип 2) — аналитический документ без шапки, не судебное производство.

**`arbitrum-docx`** — **опциональная альтернатива**: если установлен и Сюзерен предпочитает, используется вместо `format-doc`; в Cowork недоступен, поэтому основной путь — `format-doc`. Логика генерации содержания документов не дублируется внутри плагина в любом случае.

**Feature detection и fallback** — единый паттерн в [shared/conventions.md](shared/conventions.md) → «Внешние зависимости и fallback» (порядок: `format-doc`/`python-docx` → `arbitrum-docx` опц. → `.md`-only терминальный).

## 13. Порядок реализации (рекомендуемый)

**Фаза 1 — Фундамент** (приоритет):
1. `init-case` — без него ничего не работает
2. `intake` — основной конвейер обработки
3. `catalog` — визуализация для человека
4. `update-index` — поддержание целостности

**Фаза 2 — Анализ:**
5. `legal-review` — первичная аналитика
6. `build-position` — стратегия

**Фаза 3 — Ведение дела:**
7. `add-evidence` — входящие от клиента
8. `add-opponent` — входящие от оппонента
9. `prepare-hearing` — ключевой рабочий скилл
10. `analyze-hearing` — обработка результатов
11. `settlement` — мировое / отказ от иска / признание иска (ответвление от prepare-hearing, доступно на любой стадии включая исполнение)

**Фаза 4 — Завершение и обжалование:**
12. `draft-judgment` — проект судебного акта (используется до вынесения решения)
13. `appeal` — апелляционная жалоба (после решения первой инстанции)
14. `cassation` — кассационная жалоба (после постановления апелляции; в т.ч. кассация на определение об утверждении мирового по ст. 141 АПК через `cassation.target = 'ruling_settlement'`)

## 15. Кросс-дельная память (глобальное хранилище)

**Проблема, которую закрывает.** До этапа 6 ценные кросс-дельные наблюдения (профиль судьи, паттерны оппонента) хранились внутри одного дела:
- 5 дел у судьи Иванова → 5 пустых стартовых `judge-profile.md`, ни один не знает про остальных.
- Тот же оппонент в трёх делах → три отдельных экспресс-анализа в трёх `.vassal/`, четвёртое дело снова с нуля.

**Решение.** Глобальное хранилище `~/.vassal-global/` (с переопределением через `$VASSAL_GLOBAL_DIR`). Скиллы пишут в **два места одновременно** (локальный файл дела + глобальный файл), и читают глобальный профиль до анализа.

Полные правила -- в [shared/conventions.md](shared/conventions.md) → раздел «Глобальная память (кросс-дельная)».

### 15.1. Структура хранилища

```
$VASSAL_GLOBAL_DIR/                              # по умолчанию ~/.vassal-global/
├── judges/
│   └── {ФИО-slug}--{court-slug}.md             # один файл на пару (судья × суд)
├── counterparties/
│   ├── inn-{ИНН}.md                            # для юрлиц с ИНН
│   └── noinn-{slug-name}.md                    # fallback для физлиц / без ИНН
├── samples/                                     # каталог образцов (F.22) -- УКАЗАТЕЛЬ, не копия
│   └── {категория-slug}.yaml                   # один файл на значение case.category
└── README.md                                    # опционально
```

**`samples/` — третья сущность памяти, и единственная, которая индексирует документы, а не субъектов.** Хранит **адрес** (номер дела + путь внутри дела + тип + нормы), никогда — текст, суммы, контрагентов и абсолютные пути. Шардируется по `case.category`, чтобы читатель собирал имя файла детерминированно из карточки своего дела: перечисления папки и поиска по ней в плагине нет нигде, и каталог их не вводит. Полное правило — [shared/conventions.md](shared/conventions.md) → «Глобальная память» → «Каталог образцов».

`templates/` -- **зарезервирована только на бумаге**: физически папки нет, ни один скилл её не создаёт и не читает. Замысел (курируемая человеком библиотека формулировок) -- этап 7 / OPEN-ITEMS → A.6.

### 15.2. Кто пишет, кто читает

| Файл | Пишет (двойная запись) | Читает (фон до анализа) |
|---|---|---|
| `judges/{judge}--{court}.md` | `analyze-hearing` (устные паттерны), `draft-judgment` (письменный стиль), `backfill-global` (разовый перенос накопленного) | `analyze-hearing`, `draft-judgment`, `prepare-hearing`, `appeal`, `cassation`, `settlement` (как принимает мировые: формально / с пристрастием), `notion-sync` (push в базу `Judges`) |
| `counterparties/{key}.md` | `add-opponent` (письменные паттерны), `analyze-hearing` (устные паттерны), `backfill-global` (разовый перенос накопленного) | `add-opponent`, `prepare-hearing`, `build-position`, `appeal`, `cassation`, `settlement` (договороспособный / уходит от компромисса), `argument-map` (фон столбца «довод оппонента»), `draft-claim`, `enforcement-adjustment`, `notion-sync` (push в базу `Counterparties`) |
| `samples/{категория}.yaml` | **инкрементально** — каждый производитель в момент регистрации продукта в `index.yaml` (кат. 2 и 3) и ingest-скиллы для судебных актов; **разово** — `index-samples` | `build-position`, `prepare-hearing`, `draft-claim`, `enforcement-adjustment`, `appeal`, `cassation`, `settlement`, `argument-map` |

`build-position` в строке judges отсутствует намеренно — он читает только профиль оппонента.

### 15.3. Двойная запись и обратные ссылки

- **Локальный файл** в `.vassal/` дела (`judge-profile.md`, `opponent-filing-*.md`, `opponent-hearing-*.md`) -- наблюдения только этого дела, привязка к конкретным `[doc-NNN]`.
- **Глобальный файл** -- агрегированные наблюдения по всем делам Сюзерена с этой парой/сущностью; каждое наблюдение помечено `(дело {номер}, {дата})`.
- Локальный связан с глобальным через `shared_profile:` во frontmatter -- путь относительно `$VASSAL_GLOBAL_DIR`.

### 15.4. Правило накопления (аппенд-only)

- Новые наблюдения **дописываются** в соответствующий раздел.
- Старые **никогда не удаляются и не редактируются**, даже если новое им противоречит -- противоречие добавляется как «уточнение» с новой датой.
- Счётчики (`hearings_total`, `written_decisions_total`, `filings_analyzed`, `hearings_analyzed`) считают **события, а не наблюдения**: инкрементируются на число новых уникальных маркеров `(дело, заседание/решение/документ …)`. Одно заседание с восемью наблюдениями — это +1. Полное правило и разбор разъехавшихся реализаций — [shared/conventions.md](shared/conventions.md) → «Правило накопления».
- Список `cases:` пополняется без дублей по номеру.
- `last_updated` и `last_case` обновляются.

### 15.5. Конфигурируемый путь

- По умолчанию: `~/.vassal-global/`.
- Переопределение через `$VASSAL_GLOBAL_DIR`.
- Сценарии переопределения:
  - Хранение в облачном диске (Яндекс.Диск / Dropbox / OneDrive) -- кросс-машинный синк между рабочей и поездочной машинами.
  - Изоляция глобальной памяти разных юристов команды на одной рабочей станции.
- **Резолв и онбординг (F.26):** резолв кросс-платформенный (в PowerShell -- `$env:VASSAL_GLOBAL_DIR`, буквальное `$VASSAL_GLOBAL_DIR` даёт пустоту и уводит в fallback даже при заданной переменной). Переменная не задана → fallback + **разовое уведомление** (не тихо), а в песочнице Cowork fallback **эфемерен** (не переживает сессию) → предупреждение на записи и пометка в `history.md`. Онбординг-подсказку выводит `init-case`. Полное правило -- [shared/conventions.md](shared/conventions.md) → «Резолв переменной и онбординг (F.26)»; команда задания пути -- README → «Глобальная память» / [scripts/notion-init.md](scripts/notion-init.md) §4.1.

### 15.6. Конфиденциальность

Глобальная память -- **производная аналитика**, не копия документов. Допустимо: паттерны судьи, типовые формулировки оппонента, статистика, ФИО представителей, ИНН/ОГРН (публичные). Недопустимо: тексты документов клиентов, **конкретные суммы по конкретным делам клиентов**, персональные данные третьих лиц **без юридической необходимости** (контрагенты клиента -- да, физлица -- осторожно).

Глобальная папка, как и `.vassal/` дела, лежит **локально на машине Сюзерена**; при кросс-машинном синке через облако ответственность за приватность канала на Сюзерене.

⚠️ Это **пересказ**. Канон и единственный источник объёма запрета — [shared/conventions.md](shared/conventions.md) → «Глобальная память (кросс-дельная)» → «Конфиденциальность». Прежняя редакция этого абзаца расходилась с ним в обе стороны: сужала («**чувствительные** ПДн» вместо «персональные данные») и одновременно расширяла («суммы по делам» вместо «суммы по конкретным делам **клиентов**»). При любом расхождении действует канон.

### 15.7. Связь с Notion-слоем

Глобальная память -- **локальный** аналог баз `Judges` и `Counterparties` Notion-слоя. После настройки Notion (этап 6 п.23, см. ниже) данные синхронизируются в Notion для дашборда и более удобного UX, но локальная папка остаётся **источником правды** -- Notion получает push односторонне (см. раздел «Notion-слой» в conventions и [NOTION-INTEGRATION-PROPOSAL.md](NOTION-INTEGRATION-PROPOSAL.md)).
