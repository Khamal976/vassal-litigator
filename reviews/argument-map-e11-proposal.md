## Ядро: что такое E.11

Заявка Сюзерена (29.06, дело А40-85553 «Сеть Связной», ответчик): к заседанию 30.06 руками собиралась **аналитическая таблица доводов сторон по узлам спора**. Просьба — автоматизировать. Карта — не новый анализ, а **поворот в таблицу** того, что плагин уже производит по кускам:

- **Доводы оппонента + наше парирование** — `add-opponent` кладёт `.vassal/analysis/opponent-filing-{дата}-{doc-id}.md`; `prepare-hearing` в prep-артефакте (§3 Red team, §4 Парирование) даёт то же тактически структурированным.
- **Обстоятельства со ссылкой на лист** (столбец «контрдовод») — из досье `study-evidence` (`evidence-dossier.md`; там уже есть «Сводная сверка по узлам спора»).
- **Оценка силы/слабости узла** (рабочая версия) — из `build-position` (`position-*-strengths.md` / `-weaknesses.md` / `-opponent-forecast.md`).
- **Живая практика** — CasusLegal по паттерну «поиск → дайджест в файл → точечная карточка `get_case_details`»; реквизиты — списком под таблицей.
- **DOCX** — существующий `format_doc.py` (он уже парсит и рендерит markdown-таблицы в фирменной типографике), тот же feature-detection fallback в `.md`.

Значит E.11 — **скилл-сборщик**: тянет из готовых источников → предлагает узлы спора → (approve) → заполняет таблицу с живой практикой → печатает две версии.

**Легенда:** 🔴 риск подать/показать не то · 🟠 существенно · 🟡 точность/эргономика.

## Структура скилла (по паттерну «детальная структура → approve → драфт»)

### Вход
`case.yaml`, `index.yaml`; `.vassal/analysis/evidence-dossier.md` (если есть); `.vassal/analysis/opponent-filing-*.md`; `.vassal/analysis/position-*-{strengths,weaknesses,opponent-forecast}.md`; последний `.vassal/hearings/{дата}-prep.md` (§3/§4); последняя `*позиция.md` в корне; глобальный профиль оппонента `$VASSAL_GLOBAL_DIR/counterparties/`; папки «Практика*» в корне; `.vassal/analysis/retractions.md` (фильтр отозванного). CasusLegal-коннектор — для практики.

**Приоритет источника доводов оппонента и узлов:** prep-артефакт (§3 Red team + §4 Парирование, если есть — самый структурированный) → `opponent-filing-*.md` → `position-*-opponent-forecast.md`. Всё — сквозь фильтр `retractions.md`.

### Фаза 0 — Phase 0 (консистентность ФС↔индекс), как у всех аналитических скиллов.

### Фаза 1 — Загрузка контекста
Читатель служебного слоя → **хук `revise-position`** (исключить отозванное) + **хук `study-evidence`** (нет досье → неблокирующе предложить собрать: без фактуры контрдовод «по обстоятельствам» пуст). Разрезолвить `$VASSAL_GLOBAL_DIR`, загрузить профиль оппонента (фон типовых доводов). Если ни одного источника доводов оппонента нет → сообщить: карта строится по одной нашей позиции, столбец «довод оппонента» — прогноз (пометить).

### Фаза 2 — Сборка узлов + практика (Opus)
1. **Кластеризация в узлы спора:** сгруппировать доводы оппонента × точки нашей позиции в узлы (спорный вопрос = строка). Засев — «Сводная сверка по узлам спора» досье + Red team.
2. Для каждого узла заполнить: **довод оппонента** (дословно/сжато + двойная ссылка `[doc-NNN]`, при наличии — «уже наблюдалось у этого оппонента (дело …)» из глобального профиля); **наш контрдовод** (норма · практика · обстоятельство со ссылкой на лист из досье); **вывод** (наша позиция по узлу сильнее/слабее); **оценка узла** (откровенно: сила/слабость, критичность `[!]`/`[*]`/`[ ]`, что усилит).
3. **Практика (CasusLegal), по паттерну E.12:** узкий `search_practice` (фильтры суд/статья/`limit`) → ответ 90–110 КБ сбросить в `outputs/` песочницы → дайджест (id/суд/реквизит/тезис) → `get_case_details` по 1–3 ведущим актам для дословной опоры. Корпус — ВС/ВАС/КС; **СОЮ-кассация и свежак-2026 вне корпуса → пометка «сверить вручную по СПС»**. `verify-before-assert`: практика, не резолвящаяся в коннектор или локальную папку «Практика*», в таблицу идёт с явным флагом «не подтверждено — сверить до подачи», не как готовая опора.

Opus (`model: "opus"`) — вся Фаза 2 (стратегическая работа + оценка силы). Практику-дайджест можно делегировать Sonnet.

### Фаза 3 — Preview (approve структуры)
Показать **список узлов** + 1–2 образцовые строки. Сюзерен правит состав узлов (добавить/убрать/переформулировать). Это и есть точка «approve структуры» до заполнения всей таблицы.

### Фаза 4 — Заполнение + Preview таблицы
Заполнить полную таблицу, показать сводку (узлов N; критичных слабых узлов K; практики M актов, из них L «сверить вручную»). Дождаться подтверждения.

### Фаза 5 — Apply (две версии, [Q2] = вычитанием)
- **Рабочая (каноническая, для агента и Сюзерена-для-себя):** `.vassal/analysis/argument-map-{дата}-working.md` — **полная** (5 столбцов, вкл. «оценку узла»), с `[doc-NNN]`, frontmatter (`type: argument-map`, `sources`, `nodes_count`, `practice_refs`, `based_on`, `supersedes`). + список реквизитов практики.
- **Чистая (для суда, корень дела):** `{ГГГГ-ММ-ДД} Карта доводов.md` — **выводится из рабочей удалением** столбца «оценка узла» + подчисткой формулировок контрдовода от наших слабых мест; **tag-free** (без `[doc-NNN]`; ссылки на доказательства — человекочитаемые). → печать `{ГГГГ-ММ-ДД} Карта доводов.docx` через `format_doc.py --type карта-доводов`.
- **Безопасность подачи (🔴):** чистая рождается **только вычитанием** из рабочей (последний явный шаг), не собирается заново — слабые места физически не могут просочиться в судебную версию. Рабочая живёт в служебной `.vassal/` (не в комплекте на подачу; `build-submission` её не видит — Phase 0 игнорит `.vassal/`). Опционально по запросу — рабочий DOCX `{ГГГГ-ММ-ДД} Карта доводов (рабочая).docx` (не дефолт).
- `case.yaml` **не пишется** (скилл — читатель, как `study-evidence`). Запись в `history.md`. `.docx`-fallback (нет `python-docx`) — по шаблону conventions.

### Формат карты (для `format_doc.py`)
`# Карта доводов сторон по делу №… ` · дата · вводная строка · markdown-таблица · `Реквизиты судебных актов:` + нумерованный список (суд, дата, №, СКЭС/Пленум; помета «сверено через CasusLegal» / «сверить вручную»). Всё — существующие блоки парсера.

Широкая аналитическая таблица (4–5 столбцов) на A4 **портрет** тесна. Добавить **тип `карта-доводов`/`argument-map`** → **альбомная ориентация** (swap `page_width`/`page_height`). Всё остальное (таблица, шапка, fallback, детерминизм) переиспользуется.

## Зоны сверки для Сюзерена (после драфта)

1. **Столбцы карты** — совпадают ли с вашей таблицей к 30.06: «узел | довод оппонента+ссылки | контрдовод (норма·практика·обстоятельства) | вывод» (+ «оценка узла» в рабочей). Ничего не потеряно/лишнего?
2. **Гранулярность узлов** — не слишком ли дробит/укрупняет; устраивает ли точка approve (список узлов до заполнения).
3. **Практика через CasusLegal** — глубина (сколько актов на узел), формат реквизитов под таблицей, помета «сверить вручную» для СОЮ/2026.
4. **Безопасность двух версий** — достаточно ли «вычитания» + раздельного хранения, чтобы рабочая со слабостями не ушла в суд; нужна ли рабочая-DOCX по умолчанию.
5. **Альбомная карта** — ориентация/типографика широкой таблицы (проверяется в бою — `python-docx` локально нет).
