## Ядро проблемы

Три приёмных скилла читают **одну** «Входящие документы/» и берут **всё подряд** (`conventions.md` → «Папка „Входящие документы/“» стр. 53):

- `intake` (Фаза 1 шаг 2) → `source: client`;
- `add-evidence` (шаг 3) → `source: client`;
- `add-opponent` (Фаза 1 шаг 3) → `source: opponent`.

**Боевой сценарий (17.06 §4.4; 29.06 Связной §1):** Сюзерен кладёт отзыв ответчика во «Входящие», по привычке запускает `intake` → отзыв помечен `source: client`, заведены записи, оригинал уведён в «На удаление/» — **до** `add-opponent`. Дело испорчено: документ оппонента лежит как клиентский, chain of custody (пристинная копия в `.vassal/raw/`, `raw_pristine: true`) не создан. То же — при смешанной пачке.

**Корень:** скиллы **уже определяют отправителя** при категоризации (`intake` Фаза 2 шаг 9; `add-opponent` Фаза 1 шаг 6), но **не используют это для маршрутизации** — считают, что все файлы во «Входящие» их.

## Назначение

Общий шаг **«источник по содержимому» (source triage)** перед Preview: классифицировать каждый файл по источнику и обрабатывать **только свои**, а «чужие» — предлагать оформить нужным скиллом (не портить, не хватать вслепую).

## Место — общий контракт в `conventions.md`

Один канонический раздел (DRY, как Phase 0 / verify-before-assert / OCR), на который ссылаются все три приёмника. Скиллы не дублируют прозу — вызывают контракт в своей фазе перед Preview.

## Классификация источника (по уже прочитанному содержимому)

| Класс | Сигналы | Владелец |
|---|---|---|
| `client` | отправитель = наш клиент (`case.yaml.our_client`) ИЛИ контрагент в отношениях с клиентом (договоры, платёжки, переписка) ИЛИ собственный процессуальный черновик клиента | `intake`, `add-evidence` |
| `opponent` | отправитель/подписант = оппонент (`case.yaml.parties[]`, роль ответчик/истец-оппонент/третье лицо на стороне оппонента) ИЛИ процессуальный документ за подписью оппонента (отзыв, возражение, встречный иск, пояснения оппонента) | `add-opponent` |
| `court` | тип ∈ {определение, решение, постановление, судебное извещение, протокол-заседания} + реквизиты суда (шапка «Арбитражный суд …», «именем Российской Федерации», печать суда) | `add-opponent` (`source: court`) |
| `unclear` | отправителя/сторону не определить (голый скан без реквизитов, документ третьего лица без явной стороны) | спросить Сюзерена |

**Якорь сверки** — `case.yaml.parties[]` (кто `our_client`, кто оппонент). Оба скилла его уже читают.

**Низкий риск ложных срабатываний:** на первом `intake` «Входящие» — обычно всё клиентское (иск, договоры), оппонент ещё не ответил, стороны в `case.yaml` уже заданы `init-case`. Детект «выстреливает» позже, когда приходят документы оппонента/суда.

## Поведение [Q1 = «предложить обработать сразу», offer-handoff]

В Preview приёмный скилл разделяет пачку:

1. **Свои файлы** (класс = владелец скилла) → обрабатываются штатно.
2. **Чужие файлы** (класс ≠ владелец) → **не обрабатываются**; скилл показывает их отдельным списком и **предлагает**: *«N файлов похожи на документы {оппонента/суда} — оформить их через `add-opponent` прямо сейчас?»*
   - **Да** → скилл доводит **свою** часть (свои файлы → apply → «На удаление/»), затем **передаёт управление** нужному скиллу, ограниченному этими файлами (через scope-список, [Q2]). Порядок гарантирует, что к моменту handoff во «Входящие» остались только чужие файлы.
   - **Нет** → чужие файлы **остаются во «Входящие»** + сообщение «оформите через `{skill}`». Ничего чужого не тронуто.
3. **`unclear`** → спросить Сюзерена, к какому источнику отнести (или отложить).

**Симметрия:** `add-opponent`, наткнувшись на клиентские файлы, предлагает `intake`/`add-evidence`; `intake`/`add-evidence`, наткнувшись на оппонента/суд, предлагают `add-opponent`.

**Крайний случай — вся пачка чужая** (запустили `intake` на чисто-оппонентской пачке): 0 своих → Preview «клиентских документов нет; все N похожи на оппонента — оформить через `add-opponent`?» → при согласии полный handoff, `intake` сам ничего не пишет. Это ровно предотвращение порчи из боевого сценария.

## Область как опция [Q2 = «да, поддержать»]

Каждый приёмник принимает **необязательную область** из `$ARGUMENTS`:

- **подпапка** — `/intake Входящие документы/от-клиента/` → берёт только файлы под ней;
- **список файлов** — конкретные имена → берёт только их;
- **не задано** — сканирует всю «Входящие» + применяет триаж (дефолт).

Область — и есть механизм handoff: скилл A передаёт скиллу B список чужих файлов как scope. При заданной области триаж всё равно прогоняется (защита от «в подпапке от-клиента случайно лежит отзыв»), но по умолчанию файлы считаются своими.

## Зоны сверки для Сюзерена (после драфта)

1. **Сигналы классификации** — полны ли (отправитель vs `case.yaml`, тип документа, подпись)? Не путает ли документ третьего лица на **нашей** стороне (тогда `client`) с оппонентом.
2. **Court → add-opponent с `source: court`** — согласен ли, что судебные акты во «Входящие» идёт принимать `add-opponent` (как единственный внешний приёмник), проставляя `source: court` и **без** экспресс-анализа оппонента; или предпочитаешь отдельную обработку.
3. **Формулировка offer-handoff** — что показывать в Preview и как формулировать предложение переключиться.
4. **Область-аргумент** — подпапка и/или список файлов; синтаксис вызова.
5. **`unclear`** — всегда спрашивать или для одиночного unclear в остальном-однородной пачке делать оговорённое предположение.
