# `format-doc` — детальная структура (proposal → approve)

**Статус:** структура на approve (закрывает OPEN-ITEMS **E.1**). Паттерн: детальная структура → approve Сюзерена → драфт SKILL.md → ревью с зонами сверки.
**Связь:** E.1 (.docx-путь в Cowork: arbitrum-docx недоступен, proc-doc-style только под Word-аддин), E.9 (суммы прописью НЕ писать; приоритет типографики над чек-листом просительной).

---

## Назначение
Headless, **детерминированный и идемпотентный** рендер процессуального документа из его `.md` в `.docx` по фирменному стандарту типографики. Заменяет два неработающих в Cowork пути:
- **arbitrum-docx** — движок .docx, на который ссылаются 6 скиллов, в песочнице не установлен → скиллы деградируют в «.md only», хотя валидный .docx получить можно;
- **proc-doc-style** — написан целиком под Word-аддин (Office.js: `paragraph.getRange`, OOXML-патчи) → headless неисполним; в прогонах применялся частично / непоследовательно / **без идемпотентности** (повторный прогон давал разное оформление).

## Место в пайплайне
Терминальный шаг оформления для любого doc-producing скилла + отдельная команда.
`prepare-hearing / appeal / cassation / settlement / draft-judgment / analyze-hearing(замечания)` → **`format-doc`** → `.docx` → (далее `build-submission` для комплекта на подачу).

## Тип
Скилл + команда `/vassal-litigator:format-doc` (по образцу `build-submission`). **Два входа:**
1. **Санкционированный .docx-шаг** doc-producing скиллов — заменяет их `feature-detection arbitrum-docx`.
2. **Standalone** — юрист: «оформи этот документ в .docx».

## Вход
- Готовый **подаваемый `.md`** (tag-free, без `[doc-NNN]` — см. conventions «Двойные ссылки») — продукт doc-producing скилла.
- Тип документа (жалоба / отзыв / ходатайство / мировое / проект решения) — выбор шаблона/секций.
- `case.yaml` — шапка: суд, стороны, № дела, представитель.

## Выход
- `{ГГГГ-ММ-ДД} {название}.docx` в корне дела (имя = как у исходного `.md`; при заблокированном целевом файле → `_v2.docx`, не перезапись — Cowork-robustness).
- Запись в `.vassal/history.md` (чем оформлено, идемпотентный прогон).

---

## РЕШЕНИЕ 1 — движок [главное]
Развилка: **docx-js** (прежний lean; но node в Cowork хрупок — симлинк `docx`/`NODE_PATH` сломан, E.12) vs **python-docx** (уже вендорится `setup.sh`, `import docx` проверяется в статусе; без root, без node).

**Рекомендация — python-docx**, причём **делегировать рендер уже доступному скиллу `anthropic-skills:docx`** (обёртка над python-docx: шрифты, интервалы, нумерация, поля страницы — всё поддерживается). Тогда `format-doc` = **вассал-специфичный слой стиля** (парсинг .md + применение спецификации), а физический OOXML пишет проверенный `docx`-скилл. Не переизобретаем движок.
- Плюсы: уже в зависимостях, headless, робастно в песочнице без root/node.
- docx-js оставляем как **опциональную** альтернативу (если у Сюзерена рабочий node и нужен тонкий OOXML-контроль) — feature-detect, но не основной путь.

## РЕШЕНИЕ 2 — источник точных значений стиля [нужен вход Сюзерена]
Декларативную спецификацию выносим в `skills/format-doc/references/style-spec.md` (движко-независимо). Рубрики известны из E.1:
- шрифт **Garamond 11**, межстрочный **1.15**;
- шапка с отступом (выравнивание, поля);
- **авто-нумерация доводов**; тире-списки;
- формат подписи / блока приложений;
- чек-лист просительной части;
- **суммы прописью НЕ писать** (E.9);
- коллизия «чек-лист vs типографика» → приоритет **типографики / решения Сюзерена** (E.9).

⚠️ **Точные числа** (поля страницы в см, отступы, кегль заголовков) в структуре НЕ фиксируем — их надо **сорсить**: (а) из `proc-doc-style` (внешний скилл — приложишь / дашь доступ?), либо (б) из `.docx`, которые делал тестер в прогонах, либо (в) задать твой эталон. Без этого стиль будет «примерно», а не «как принято у тебя».

## РЕШЕНИЕ 3 — markdown-контракт (как format-doc понимает .md)
Чтобы разложить `.md` по абзацам/секциям .docx, нужен предсказуемый вход. Развилка: **строгий якорный контракт** (doc-producers эмитят фикс. заголовки-маркеры: «Шапка», «Просительная часть», «Приложения», «Подпись») vs **эвристический парсинг** свободного текста.
**Рекомендация — лёгкий якорный контракт по заголовкам + эвристика для тела:** doc-producers уже пишут структурированный `.md` (шапка → тело → просительная → приложения → подпись); формализуем минимум якорей, тело (доводы, списки) парсим эвристически. Побочно улучшает единообразие выходных `.md`.

## Идемпотентность / детерминизм
- Тот же `.md` → тот же `.docx` (фиксированные метаданные документа: без случайных id/времени-создания в пределах допустимого) — снимает «повторный прогон = разное оформление» (E.1).
- Прогон **read-only по .md**; только пишет .docx.

## Интеграция (замена arbitrum-docx в 6 скиллах)
В `prepare-hearing / appeal / cassation / settlement / draft-judgment / analyze-hearing`: фаза оформления → **сначала `format-doc`** (in-plugin, приоритетный путь); `arbitrum-docx` — опц., если установлен и Сюзерен предпочитает; нет ни одного движка → `.md`-only fallback + предупреждение (существующий паттерн). Обновить `conventions.md` «Внешние зависимости и fallback» + постусловия категории 3 + ARCHITECTURE §8.

## Границы
- Не генерирует контент (это doc-producing скиллы) — только оформляет готовый текст.
- Не подаёт в суд (это `build-submission`).
- Не изобретает стиль вне спецификации.
- Не трогает правовой слой.

## РЕШЕНИЕ 4 — фазировка [процесс]
Развилка: (а) построить standalone `format-doc` СНАЧАЛА, интеграцию в 6 скиллов — отдельным заходом; vs (б) всё сразу.
**Рекомендация — (а):** сначала работающий standalone-скилл + спецификация стиля (можно проверить на одном реальном `.md`), затем — интеграция в 6 doc-producing скиллов. Меньше риск, есть точка проверки типографики до массовой замены.
