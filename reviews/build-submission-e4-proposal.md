## Ядро: что такое E.4

`build-submission` (переработан в WS-5 аудита №2, v0.7.0) собирает физический комплект «на подачу»: читает готовый процессуальный документ → сверяет «заявлено vs вложено» → раскладывает нумерованный комплект с самоописывающими именами. Скилл рабочий; E.4 — **не переработка, а закалка «последней мили»**: 7 кромочных дефектов, всплывших на реальных прогонах июня 2026 (Связной, ОСК↔ФССП, убытки с АУ, жалоба на КУ). Один из семи — 🔴 (риск подать в суд удалённое/лишнее приложение).

**Легенда:** 🔴 блокер целостности подачи · 🟠 существенно · 🟡 неудобство.

## Что уже закрыто E.1 (не переделывать)

Late-binding (v0.11.0) печатает `.docx` **один раз в конце** — слот `00` рождается через `format-doc` из финального подаваемого `.md` в момент сборки. Это снимает грань «устаревший исходящий `.docx`» из E.4. Но **не** снимает: (а) черновые маркеры в самом `.md` (E.4.1); (б) расхождение состава приложений между документом и устным указанием Сюзерена (E.4.7 — правка живёт вне `.md`); (в) резолв/бандлы/форматы/листаж/орфаны (E.4.2–E.4.6). Их и чиним.

## По подпунктам

### E.4.1 🔴 Маркеры черновика не проверяются

**Где:** `build-submission` Фаза 2–3; печать слота `00`.
**Что сейчас:** подаваемая `.docx` уходила с тремя незакрытыми `[ПЛЕЙСХОЛДЕР]` — скилл «собрал + флагнул комплект», но **тело основного документа на маркеры не грепал**.
**Что делаем:** перед печатью слота `00` грепать финальный подаваемый `.md` (и, если пришёл готовый `.docx` — его текст) на паттерны черновика: `[ПЛЕЙСХОЛДЕР]`, `[TODO]`, `[…]`, `XXX`, «указать (дату/номер/сумму)», «__», «< >`. Любое совпадение → **🔴 флаг** в Preview (с номером места/цитатой) + `needs_manual_review: true` на манифесте. Не блокирует (принцип скилла), но поднимает на самый видимый уровень — «в суд уходит черновик».

### E.4.2 🟠 Резолв приложений без `[doc-NNN]` → [Q1: надёжно]

**Где:** `build-submission` Фаза 1 шаг 3 / Фаза 2 шаг 5; генераторы `appeal` / `cassation` / `prepare-hearing` / `settlement`.
**Что сейчас (уточнено разведкой):**
- `prepare-hearing` (§6 prep-артефакта `.vassal/hearings/{дата}-prep.md`) и `cassation` (§7 `.vassal/analysis/cassation-prep-{дата}.md`) — рабочий перечень приложений «с двойными ссылками» **есть**, но блок не гарантированно машинно-парсабелен для build-submission.
- **`appeal` — рабочей версии не сохраняет вовсе** (анализ в фазах 2-3 не персистится). Постусловие (стр. 333) требует `[doc-NNN]` у приложений, но класть их некуда: подаваемый `.md` — tag-free (`conventions.md` → «Двойные ссылки» стр. 548). **Это корень пустого primary-резолва** → эвристический фолбэк по индексу (риск привязать не тот файл).
- `settlement` — подаваемые tag-free; выделенного теггированного перечня приложений нет.

**Что делаем (обе половины):**
1. **Генераторная (root-fix).** Каждый генератор персистит **машинно-читаемый «Рабочий перечень приложений»** с `[doc-NNN]` на каждом пункте, в фиксированном месте, которое читает build-submission. Формат строки: `- NN. Наименование от ДД.ММ.ГГГГ [doc-NNN]` (или `[doc-НЕ-В-ИНДЕКСЕ]`, если приложения нет в деле — напр. свежая госпошлина). Размещение:
   - `prepare-hearing` §6 prep-артефакта — привести к явному блоку;
   - `cassation` §7 `cassation-prep` — то же;
   - **`appeal`** — новый минимальный prep-артефакт `.vassal/analysis/appeal-prep-{дата}.md` (симметрия с cassation) с блоком «Рабочий перечень приложений» (+ краткий перечень оснований);
   - `settlement` — новая машинно-читаемая секция `.vassal/analysis/settlement-{дата}-appendices.md` (перечень приложений ходатайства/заявления с тегами).
   Теги **только в рабочей версии**, подаваемый `.md` остаётся tag-free (инвариант conventions стр. 548 не нарушаем).
2. **Сборочная (fail-loud).** build-submission Фаза 1 шаг 3 — явно перечисляет рабочий источник приложений по каждому генератору; Фаза 2 шаг 5 — primary-резолв из теггированного блока; **если у пункта нет `[doc-NNN]` → эвристический фолбэк, но каждый такой пункт помечается ⚠ «привязано эвристически — проверьте привязку»** и Preview требует явного подтверждения этих пунктов (не молча).

### E.4.3 🟠 Приложения-бандлы (1 пункт перечня = N физических документов)

**Где:** `build-submission` Фаза 2/5, раздел «Наименование файлов».
**Что сейчас:** один пункт перечня «Платёжные поручения, 19 шт.» = 19 физических файлов; нумерация «файл NN ↔ приложение NN» (1:1) это не описывает.
**Что делаем (схема уже готова — не новая):** `index-schema.yaml` уже несёт бандлы (`bundle_id`, `parent_id`, `role_in_bundle`, top-level `bundles:` с `members`, `next_bundle_id`). build-submission: когда пункт перечня резолвится в бандл / группу из N `doc-NNN` — **под-нумерация** `NN.01 … NN.k`:
```
05.01 Платёжное поручение №47 от 2026-05-12 1л.pdf
05.02 Платёжное поручение №48 от 2026-05-13 1л.pdf
…
05.19 Платёжное поручение №65 от 2026-05-31 1л.pdf
```
Раскрытие бандла отражается именами файлов (папка = опись): пункт 05 перечня → 19 файлов `05.01…05.19`. Сумма/число единиц бандла участвует в кросс-проверке E.4-«число единиц»/«суммы».

### E.4.4 🟠 Форматы для подачи (РЛ RTF / реестр XLSX → PDF для «Мой арбитр») → [Q2: опционально]

**Где:** `build-submission` Фаза 5; `conventions.md` → «Внешние зависимости»; `setup.sh`.
**Что сейчас:** офисные форматы (RTF/XLSX) копируются «как есть»; «Мой арбитр» ждёт PDF.
**Что делаем (feature-detected, graceful):** введём **опциональную** зависимость `libreoffice`/`soffice`. Детект `command -v soffice` (или `libreoffice`):
- **есть** → предложить в Preview конвертацию офисных приложений в PDF (`soffice --headless --convert-to pdf`); при согласии — конвертнуть, приложить PDF, оригинал оставить рядом/в исходнике;
- **нет** (обычный Cowork без root — как tesseract) → копировать как есть + ⚠ флаг «для „Мой арбитр“ сконвертируйте {файл} в PDF вручную».
Никакого тихого падения; конвертация — не по умолчанию, а по подтверждению (детерминизм/чувствительность).

### E.4.5 🟠 Листаж `.docx` (нет поля `pages`) → [Q2: опционально]

**Где:** `build-submission` Фаза 5 / «Наименование файлов».
**Что сейчас:** для описи нужен «N л.»; у свеже-напечатанного слота `00` `.docx` нет поля `pages` (у PDF-приложений листаж берётся из зеркала).
**Что делаем (feature-detected):** если `soffice` доступен — посчитать листы `00`: `soffice --headless --convert-to pdf` → `pdfinfo` (или `pymupdf` по полученному PDF, `pdfinfo` не гарантирован) → число страниц → `Nл` в имени. Недоступно → **`Nл` опустить + пометка в манифесте «листаж уточнить вручную»** (текущее поведение для неизвестного листажа сохраняется). Грань: приложения-PDF листаж по-прежнему из зеркала (`pages`), фикс только про слот `00`.

### E.4.6 🟡 Ложные орфаны «На подачу/» (Phase 0)

**Где:** `conventions.md` → «Проверка консистентности ФС ↔ индекс (Phase 0)», шаг 2 (классификация). Общий пролог — правит **всех** аналитических читателей, не только build-submission.
**Что сейчас:** Phase 0 сканирует диск, **игнорируя** `На подачу/` (и др. игнор-папки), но `orphan_records` = записи индекса, чей `file:` не в `files_on_disk`. Запись, чей `file:` указывает **в игнор-папку**, → её файл не попал в `files_on_disk` (папка проигнорирована) → **ложно помечается осиротевшей**, хотя файл на месте.
**Что делаем:** в шаге 2 при вычислении `orphan_records` **исключать записи, чей `file:` лежит под игнор-папкой** (`На подачу/`, `На удаление/`, `Входящие документы/`, `.vassal/`). Такие записи не орфаны — они вне периметра быстрого скана by-design. (Канонический перечень игнор-папок уже задан в шаге 1.)

### E.4.7 🔴 Сессионные правки/удаление приложений игнорируются → [Q3: обнаружить и спросить]

**Где:** `build-submission` Фаза 1 (захват) / Фаза 3 (сверка) / Фаза 4 (Preview).
**Что сейчас:** Сюзерен правил приложения или просил **перед сборкой убрать** часть — build-submission всё равно собирал по **изначальному** блоку «Приложения» документа/индекса. **Риск: подать удалённое приложение** (или не подать добавленное).
**Почему late-binding не спасает:** правка живёт **в устном указании сессии**, не в `.md`. `.docx` печатается из `.md` свежим, но состав приложений берётся из перечня, которого правка не коснулась.
**Что делаем:**
- **Фаза 1 (новый шаг):** зафиксировать **сессионные указания об изменении состава приложений** (убрать/добавить/заменить пункт), если Сюзерен давал их в этой сессии (из `$ARGUMENTS` и из контекста диалога). Сформировать «текущий заявленный состав» = перечень документа ± сессионные правки.
- **Фаза 3 (новая проверка):** сверить «перечень в документе ↔ текущий заявленный состав». Расхождение → **🔴 флаг** (не молча брать старое).
- **Фаза 4 (Preview):** при расхождении — **выбор из 3**:
  1. **Обновить документ через генератор** (`prepare-hearing`/`appeal`/`cassation`/`settlement`) — *рекомендуется*: документ, перечень и физический комплект остаются согласованы (уважает границу «build-submission не правит перечень в документе»);
  2. **Собрать по текущему указанию** (без убранного приложения) — комплект соберётся, но `заявлено(документ) ≠ вложено` → это штатный флаг сверки «заявлено vs вложено»;
  3. **Собрать как в документе** (со всеми) — игнорировать сессионную правку.
  Молча старый набор не берётся. Сохраняет принцип скилла «собираем всегда, помечаем расхождения» (не жёсткий блок — [Q3] отклонён вариант B).

## Согласованные развилки (AskUserQuestion, 2026-07-06)

- **[Q1] Привязка приложений** → **надёжно: метки в генераторах + флаг.** Генераторы персистят теггированный рабочий перечень; build-submission при отсутствии тега — громкий фолбэк с подтверждением. (Отклонён B: только флаг в сборке.)
- **[Q2] PDF-нормализация + листаж `.docx`** → **ввести опционально (feature-detect `soffice`).** Где движок есть — конвертим/считаем; где нет — копия как есть + флаг. (Отклонён B: только напоминания без движка.)
- **[Q3] Сессионные правки приложений** → **обнаружить расхождение и спросить (3 варианта).** (Отклонён B: жёсткий блок до обновления документа.)

## Зоны сверки для Сюзерена (после драфта)

1. **Паттерны маркеров черновика** (E.4.1) — полон ли список (`[ПЛЕЙСХОЛДЕР]`/`[TODO]`/«указать …»/`XXX`/`[…]`)? Не даёт ли ложных срабатываний на легитимном тексте.
2. **appeal-prep-артефакт** (E.4.2) — согласен ли на новый служебный файл у `appeal` (симметрия с cassation) ради надёжной привязки; или предпочитаешь иное размещение перечня.
3. **Поведение конвертации в PDF** (E.4.4) — по подтверждению в Preview (как заложено) или всегда-авто, когда `soffice` есть.
4. **3-выбор при расхождении состава** (E.4.7) — формулировки вариантов и что считать «сессионным указанием» (только явное «убери приложение N» или любые правки приложений в диалоге).
5. **Под-нумерация бандлов** (E.4.3) — формат `NN.kk` (`05.01…05.19`) читаем ли для описи/канцелярии суда.
