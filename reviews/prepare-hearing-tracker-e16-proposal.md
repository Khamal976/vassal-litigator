## 1. Что закрываем

E.16 (🟡 `prepare-hearing` — чтение трекера задач). Боевой сигнал (03.07 backlog #2): при подготовке к заседанию Asana выдала **два прежних отказа по нашему АУ = фактически готовый раздел документа**, но делалось ad-hoc по просьбе Сюзерена. Нужен **штатный опциональный шаг** «поиск по трекеру (Asana/Notion) по № дела и ФИО сторон» перед фазой 2.

Это **«B.16 наоборот»**: тот же коннектор, но на **чтение** истории по делу/АУ (B.16 — пост-MVP, на **запись** задачи-заседания). Два сценария одного коннектора.

## 2. Механизм

**Размещение:** новый шаг Фазы 1 (**3.3**) в `prepare-hearing`, рядом с существующими хуками `revise-position` (3.2) и `study-evidence` (Шаг 2) — «перед фазой 2», как требует E.16; находки питают Red team / Парирование.

**Гейтинг (по образцу feature-detection `notion-sync`):**
- короткая проба коннектора (Asana MCP `search_tasks` / Notion `notion-search`);
- недоступен / не авторизован → **тихий skip** + отметка в `.vassal/`-логе, **не блокировать** (в Cowork-сессии без интерактивной auth это норма, а не ошибка);
- оба коннектора гейтятся **независимо**.

**Запрос:** по `case.number` (№ дела) + ФИО/наименованиям сторон из `case.parties[]` + ФИО АУ (`parties[]` с ролью «Арбитражный управляющий»). Конфиг (workspace/project) — только для сужения области.

**Находки → контекст фазы 2** как материал для Red team / Парирования / Blue team; фиксируются в prep-артефакте §1 (Обновление ситуации) с пометкой статуса сверки.

**Канон** вынесен в `shared/conventions.md` → «Чтение трекера задач (Asana/Notion)» (DRY, стыкуется с verify-before-assert; расширяемо на legal-review/build-position позже).

## 3. Обоснование развилок

### [Q1] Запуск шага → **штатно при наличии коннектора** (не opt-in в конфиге)

E.16 просит «штатный шаг». При доступном Asana/Notion MCP шаг запускается сам (feature-detect, как notion-sync, но на чтение); конфиг нужен только для сужения области, не для включения. Нет коннектора → тихий skip. Это убирает ad-hoc-режим боевого случая: раньше Сюзерен просил вручную — теперь подтягивается штатно.

### [Q2] Находки → **лиды на сверку** (verify-before-assert)

Трекер — **личные заметки Сюзерена, не авторитетный источник**. Находка («два прежних отказа по нашему АУ») — указатель на судебный акт, который **обязан быть в материалах дела**, чтобы его цитировать в подаваемый документ. Скилл черновит раздел от лида, но помечает «найдено в трекере: {что} — подтянуть акт в дело (`add-evidence`/`add-opponent`) и сверить перед цитированием»; в суд цитата идёт только с подтверждённым локальным источником. Это то же правило, что «непроверяемое — флаг-задача, не вывод». Вариант «готовый материал» нарушил бы verify-before-assert (в суд могла бы уйти ссылка на акт, которого нет в деле).

## 5. Зоны сверки (на ревью Сюзерену)

1. **Штатная авто-проба.** Устраивает ли, что при доступном коннекторе скилл сам лезет в Asana/Notion каждый раз? Если предпочтёте opt-in через конфиг (не трогать трекер без явного включения) — обратный ход [Q1].
2. **Поля запроса.** Ищем по № дела + ФИО сторон + ФИО АУ. Если у вас в трекере история чаще привязана к иному ключу (напр. кодовое имя проекта, ИНН) — добавим.
3. **Граница verify-before-assert.** Согласны, что находка трекера всегда идёт как лид с флагом «подтянуть акт в дело», даже если это ваш собственный прежний документ? Это защищает от цитаты акта, которого нет в материалах текущего дела.
4. **Коннектор в Cowork.** Asana/Notion MCP требуют интерактивной авторизации; в headless/cron-сессии шаг тихо пропустится. Это ожидаемо (не баг) — при живой сессии с авторизованным коннектором шаг сработает.
