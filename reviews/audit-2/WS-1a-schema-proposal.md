## 0. Принцип проектирования

Все поля проектируются так, чтобы **ключи роутинга 1b уже были на месте**: `case.category` + `jurisdiction.competent_court` + `bankruptcy.procedure` — то, по чему `legal-review`/`prepare-hearing` будут выбирать секцию references (контент банкротства/ГПК/КАС/ТК **уже написан** — нужен только маршрут).

Net-new поля, обратная совместимость не ломается: ни один скилл сейчас не читает `case.bankruptcy.*` или `case.production_type` как структурное поле (проверено grep'ом — упоминания только в init-case SKILL с явным фолбэком «если поля нет в схеме», в справочнике и в доках). Старые `case.yaml` v4 остаются валидными: все новые поля либо `null`, либо отсутствуют → читаются как `null`.

## B. `case.category` — расширение enum (F1.6)

**Сейчас** (строка 29): `экономические споры | банкротство | административные`

**Проблема:** enum не покрывает трудовые/корпоративные/КАС/ГПК-исковое; роутинг 1b не на что опереть. `category` — **субстантивная** ось (что за спор), процессуальный кодекс отражает `jurisdiction.competent_court` (`арбитражный | СОЮ | КАС | банкротный` — уже есть).

**Предложение:**

```yaml
  category: "исковое (АПК)"
  # writes: init-case | Субстантивная категория спора — ключ роутинга к секциям references.
  # Допустимые значения:
  #   исковое (АПК)          — экономический спор в исковом порядке (АПК, гл. 13-21)
  #   банкротство            — дело о несостоятельности (ФЗ-127; спец. производство)
  #   корпоративный спор     — гл. 28.1 АПК (ст. 225.1)
  #   административное (АПК)  — оспаривание ненормативных актов/решений в АС (гл. 24-26 АПК)
  #   исковое (ГПК)          — гражданское исковое в СОЮ
  #   трудовой спор          — индивидуальный трудовой спор (ТК; СОЮ, общеисковое — упрощёнка неприменима)
  #   административное (КАС)  — публичные правоотношения в СОЮ (КАС РФ)
  # Процессуальный кодекс/инстанция фиксируется отдельно — case.jurisdiction.competent_court.
```

**🔸 Точка решения B1.** Гранулярность. Варианты:
- **(рекомендую) 7 значений выше** — ровно те оси, что различают существующие references (production-types, labor, administrative, jurisdiction). Не плодим то, под что нет контента.
- (минимум) оставить как есть + только `трудовой спор` (буквально F1.6), остальное позже.
- (расширенно) добавить ещё `семейное`, `жилищное`, `земельное` (СОЮ) — но под них нет references → роутить некуда → преждевременно.

**🔸 Точка решения B2.** Миграция значения `экономические споры` → `исковое (АПК)`. Старые дела имеют `category: экономические споры`. Варианты: (а) принять оба, старое — синоним (надёжнее для старых дел); (б) переименовать и пометить старое deprecated. Рекомендую **(а)** — не ломать существующие карточки.

## C. `parties[].role` + `party_id` + новое `role_detail` (F1.2)

**Сейчас** (строка 63): `Истец | Ответчик | Третье лицо | Заявитель | Заинтересованное лицо`; `party_id` формата `{role}-NN` (исковой: plaintiff-01, defendant-01).

**Предложение — расширить enum роли:**

```yaml
      role: "Истец"
      # Исковые:      Истец | Ответчик | Третье лицо | Заявитель | Заинтересованное лицо
      # Банкротные:   Должник | Арбитражный управляющий | Кредитор | Уполномоченный орган |
      #               СРО | Контролирующее должника лицо (КДЛ)
      # СОЮ:          Прокурор (ст. 45 ГПК)
      role_detail: null
      # Подтип роли (только где применимо):
      #   для Арбитражный управляющий — стадийный подтип:
      #       временный (наблюдение) | административный (фин. оздоровление) |
      #       внешний (внешнее управление) | конкурсный (конкурсное производство) |
      #       финансовый (банкротство гражданина)
      #   для Кредитор — статусный подтип:
      #       заявитель по делу | реестровый | зареестровый | текущий
      #   иначе — null
```

**Предложение — party_id-слаги по профилю** (расширить правило init-case `{role}-NN`):

| Роль | Слаг party_id |
|---|---|
| Истец / Ответчик / Третье лицо / Заявитель / Заинтересованное лицо | `plaintiff` / `defendant` / `third-party` / `applicant` / `interested` |
| Должник | `debtor` |
| Арбитражный управляющий | `manager` |
| Кредитор | `creditor` |
| Уполномоченный орган | `authority` |
| СРО | `sro` |
| Контролирующее должника лицо (КДЛ) | `cdl` |
| Прокурор | `prosecutor` |

Формат прежний `{слаг}-NN` (`creditor-01`, `creditor-02`, `manager-01`). Документируется в init-case (это уже 1b-правка SKILL, но слаг-таблицу фиксируем здесь как контракт).

**🔸 Точка решения C1.** `role_detail` для АУ — **стадийный** (меняется по ходу дела: временный→конкурсный). Дублировать стадию в `bankruptcy.procedure` и в `role_detail` АУ — риск рассинхрона. Варианты:
- **(рекомендую)** `role_detail` АУ хранит подтип как «снимок на момент актуальной процедуры»; источник истины о стадии — `bankruptcy.procedure`; при смене процедуры owner (legal-review) обновляет оба согласованно. Просто и явно.
- Не хранить подтип в party вовсе, выводить из `bankruptcy.procedure` + `bankruptcy.manager_party_id`. Чище по нормализации, но теряем подпись роли в карточке сторон.

## D. Блок `bankruptcy:` (F1.3 — P0)

Ядро WS-1a. Машиночитаемый дом для банкротной специфики. Критично: **`registry_close_date`** — дата, после которой требование кредитора попадает за реестр (потеря очерёдности удовлетворения = потеря денег/права). Сейчас её негде хранить машиночитаемо.

Размещение: верхнеуровневый блок `case.bankruptcy:` (рядом с `case.settlement:`), активен только при `category: банкротство`.

```yaml
  # Банкротный профиль — заполняется только при case.category = "банкротство".
  # Для прочих категорий блок отсутствует или весь null.
  # writes: init-case (структура + известное из материалов: процедура, даты, тип должника),
  #         legal-review (уточнение registry_close_date, procedure, дат публикации после анализа)
  # reads:  build-position, prepare-hearing, appeal, cassation, legal-review
  bankruptcy:
    debtor_type: null               # юрлицо | ИП | гражданин
                                    # Определяет применимый набор процедур (граждане:
                                    # реструктуризация долгов / реализация имущества).
    debtor_party_id: null           # ссылка на parties[].party_id должника (обычно debtor-01)

    procedure: null                 # Текущая процедура:
                                    #   наблюдение | финансовое оздоровление | внешнее управление |
                                    #   конкурсное производство            — для юрлиц/ИП
                                    #   реструктуризация долгов | реализация имущества
                                    #                                      — для граждан
                                    # Ключ роутинга reference-секции (реестровые сроки зависят
                                    # от процедуры: наблюдение 30 дн с публикации — ст. 71 ФЗ-127;
                                    # конкурс — реестр 2 мес с публикации — ст. 142 ФЗ-127).
    procedure_introduced_date: null # Дата введения текущей процедуры (определение суда), ГГГГ-ММ-ДД
    case_opened_date: null          # Дата возбуждения дела о банкротстве (принятие заявления судом)

    # Публикация сведений — якорь отсчёта реестровых сроков.
    publication:
      source: null                  # Коммерсантъ | ЕФРСБ
                                    # (Коммерсантъ — офиц. печатный орган; ЕФРСБ — fedresurs.ru.
                                    #  Для разных сроков релевантна разная публикация — хранить факт.)
      date: null                    # Дата публикации, ГГГГ-ММ-ДД — точка отсчёта 30 дн / 2 мес
      message_number: null          # Номер сообщения ЕФРСБ / номер и дата газеты (для проверяемости)

    # КРИТИЧНО (P0). Дата закрытия реестра требований кредиторов.
    # После неё требование нашего кредитора — зареестровое (удовлетворяется после реестровых).
    # Расчёт: как правило publication.date (конкурс) + 2 месяца (ст. 142 ФЗ-127);
    # для наблюдения — 30 дн с публикации для участия в первом собрании (ст. 71).
    # Хранить ФАКТИЧЕСКУЮ дату (а не только формулу) — на неё завязаны дедлайны build-position/prepare-hearing.
    registry_close_date: null       # ГГГГ-ММ-ДД
    registry_close_basis: null      # норма + от какой публикации считали (текст, для аудита)

    # Арбитражный управляющий — ссылка на party (АУ заводится как parties[].role=Арбитражный управляющий).
    manager_party_id: null          # ссылка на parties[].party_id АУ (обычно manager-01)
    manager_sro: null               # Наименование СРО, членом которой состоит АУ
                                    # (важно для дел о замене СРО / жалоб на АУ; defendant в защите СРО).

    # Основание участия НАШЕГО клиента в деле — почему мы здесь и в каком качестве.
    # Свободный текст: фиксирует то, что не выводится из role автоматически.
    # Примеры: «кредитор-заявитель, требование 1,26 млрд из договора поставки»;
    #          «СРО, защищаем АУ от жалобы должника на ненадлежащее исполнение».
    our_position_basis: null
```

**🔸 Точка решения D1.** `registry_close_date` — хранить и **факт-дату**, и **basis** (норма+от какой публикации). Рекомендую да (оба) — verify-before-assert требует проверяемости, а basis даёт аудиторский след, почему именно эта дата. Альтернатива — только дата (легче, но теряем след).

**🔸 Точка решения D2.** Глубина блока для MVP. Сейчас спроектировано «достаточно для реальных 3 банкротных дел из боевой базы» (жалоба на ФУ, включение требования, защита СРО). Можно добавить (но предлагаю **не сейчас**, пост-MVP): реестр требований как список (суммы по очередям), даты собраний кредиторов, обособленные споры списком. Это — отдельная структура, не «карточка». Зафиксируем в OPEN-ITEMS как кандидата.

**🔸 Точка решения D3.** Размещение блока. Варианты: (а) верхнеуровневый `case.bankruptcy:` (как `case.settlement:`) — рекомендую, симметрично; (б) вложить в `case.jurisdiction.bankruptcy`. Рекомендую **(а)** — банкротная специфика шире подсудности.

## E. `production_type` — снять дрейф (F1.4)

**Сейчас:** в схеме поля нет. init-case фаза 3 (строка 95) пишет `case.production_type`, `case.production_type_basis`, флаг в `case.notes` — **с фолбэком** «если поля нет в схеме». Справочник production-types.md §6 пишет **4 поля**. → классический дрейф, предсказанный аудитом №1.

**Предложение — добавить в блок `case:` (рядом с `amounts`):**

```yaml
  # Порядок производства — квалификация по сумме+категории (НЕ выбор истца).
  # Определяется в init-case (фаза 3, при наличии amounts.claim) по алгоритму
  # legal-review/references/production-types.md §6; уточняется legal-review при анализе.
  # writes: init-case, legal-review
  # reads:  build-position, prepare-hearing, appeal (срок апелляции: упрощёнка — 15 дней vs 1 мес)
  # N/A для category ∈ {банкротство, корпоративный спор, административное (КАС)} — спец. производство:
  #   оставлять null (init-case ветка «category=банкротство» пропускает определение).
  production_type: null             # приказное | упрощённое | общеисковое | null
  production_type_basis: null       # Обоснование с нормой, напр.:
                                    # "ст. 227 ч. 1 п. 1 АПК — цена иска 850 000 ₽ для юрлица,
                                    #  в пределах 1 200 000 ₽ (ред. ФЗ № 667-ФЗ от 25.12.2023)"
  production_type_set_by: null      # init-case | legal-review — кто зафиксировал
  production_type_set_date: null    # ГГГГ-ММ-ДД
```

**🔸 Точка решения E1.** Сколько полей. Варианты:
- **(рекомендую) все 4** — ровно то, что пишет справочник §6 (строки 228-233). Полностью снимает дрейф, даёт трекинг «кто/когда квалифицировал» (полезно: init-case ставит предварительно, legal-review уточняет).
- (минимум) только 2 (`production_type` + `_basis`) — буквально F1.4. Тогда справочник §6 надо подрезать до 2 полей (иначе дрейф остаётся в другую сторону). Лишняя правка.

**Сопутствующе:** после добавления `production_type` в схему фолбэк init-case «если поля нет → флаг в `case.notes`» становится мёртвым. `case.notes` в схеме тоже нет (вторичный дрейф). → в 1b при правке init-case убрать мёртвую ветку фолбэка. **Точка решения E2:** добавлять ли общий `case.notes:` в схему? Рекомендую **нет** — вместо «свалки notes» значимое идёт в `timeline`/`history.md`; ветку фолбэка просто удалить в 1b.

## F. Ownership-матрица (обновить комментарии схемы + таблицу conventions)

Новые поля → новые строки в матрице ownership (`shared/conventions.md` → «Ownership полей case.yaml» + комментарии `# writes:` в схеме):

| Блок | Writes | Reads |
|---|---|---|
| `case.category` | `init-case` | все |
| `case.production_type`, `*_basis`, `*_set_by`, `*_set_date` | `init-case`, `legal-review` | `build-position`, `prepare-hearing`, `appeal` |
| `case.bankruptcy.*` | `init-case` (структура, известные даты), `legal-review` (`registry_close_date`, `procedure`, даты публикации) | `build-position`, `prepare-hearing`, `appeal`, `cassation`, `legal-review` |
| `parties[].role_detail` | `init-case` (нач.), `legal-review` (уточнение при смене процедуры) | все |

**🔸 Точка решения F1.** Кто owner `bankruptcy.registry_close_date` — `init-case` или только `legal-review`? Рекомендую **оба пишут, но разделение ответственности явное**: init-case фиксирует, что **известно из материалов сразу** (процедура, даты публикации, тип должника); `registry_close_date` как **расчётную правовую дату** уточняет/подтверждает legal-review (это правовой вывод, а не голый факт из шапки). Согласуется с принципом «карточка ревизуема» (init-case SKILL строка 54).
