## 3. СЛОЙ 1 — `shared/category-routing.md` (новый файл, механизм)

**Назначение:** диспетчерская таблица «`case.category` (+ для банкротства `case.bankruptcy.procedure`) → какие секции каких references применять, какой `competent_court`, какие нормы-маркеры профиля». Скиллы не зашивают нормы в теле — берут маршрут отсюда.

**Почему отдельный файл, а не раздел conventions:** `conventions.md` — контракт «как агент ведёт себя в среде/формате» (Phase 0, verify-before-assert, ownership). Роутинг — «куда смотреть по существу спора», растёт под ГПК/КАС позже (D10). Держать раздельно. legal-review, prepare-hearing, далее appeal/cassation ссылаются на один файл.

**Структура файла:**
1. **Назначение + как читать** — алгоритм диспетчера: нормализуй `category` (синоним «экономические споры» → «исковое (АПК)»); если `банкротство` — возьми доп. ключ `bankruptcy.procedure`; найди строку; читай указанные секции; применяй нормы-маркеры профиля, а не дефолт-АПК.
2. **Главная матрица** (таблица из §1 выше + столбец `competent_court` + столбец «нормы-маркеры профиля»).
3. **Банкротный под-роутер** `procedure → реестровый срок`: наблюдение → deadlines §3 абзац «наблюдение» (якорь — publication.date); конкурс → deadlines §3 абзац «конкурс» (ст. 142). Прямое указание: **registry_close_date считает legal-review** (P0).
4. **Степень наполнения профилей:** банкротство / исковое-АПК / административное / трудовой — **полные**; корпоративный — частичный (гл. 28.1 поверх АПК-искового); ГПК-исковое / КАС — **секции есть, профиль активен** (наполнение латентных краёв — позже, D10). Профиль не помечается «не готов» — все 7 маршрутизируемы.
5. **Связи** — на case-schema (`category`, `bankruptcy.procedure`), на потребителей.

## 4. СЛОЙ 2 — `legal-review` ветвление (точечные правки)

**4.1. Новый шаг — Фаза 1.5 «Определение профиля» (между загрузкой контекста и анализом).**
Прочитать `case.category` (нормализовать синоним) → если банкротство, `case.bankruptcy.procedure` → открыть `shared/category-routing.md`, получить набор секций/competent_court/норм-маркеров. Зафиксировать профиль в шапке анализа (аудируемо: «Профиль: банкротство / конкурсное производство; competent_court=банкротный»).

**4.2. Блоки c/d/e фазы 2 — из «зашито-АПК» в «диспетчер по профилю».**
Текст блоков переписывается так: «по профилю из Фазы 1.5 читай deadlines §X / pretrial §Y / jurisdiction §Z; применяй нормы-маркеры профиля». Дефолт-АПК-нормы из тела убираются (остаются как «профиль: исковое (АПК)»). Контент справочников **не трогаем**.

**4.3. Банкротная специфика (профиль=банкротство):**
- Блок c) Сроки → **добавляется расчёт `registry_close_date` (P0)**: legal-review вычисляет дату закрытия реестра от `bankruptcy.publication.date` по `procedure` (по нормам deadlines §3 как написано) и пишет в `case.bankruptcy.registry_close_date` + `registry_close_basis`. Ownership ✅ (схема: writes legal-review). Новый машинно-читаемый выход `analysis/registry-deadlines.md`.
- Блок d) Досудебка → заменяется на «предъявительский ценз / Федресурс» (pretrial §5): для кредиторского входа — просуженность долга / уведомление ст. 7 п. 2.1; классическая претензия ч.5 ст.4 АПК неприменима.
- Блок e) Подсудность → jurisdiction §5 (ст. 33 ФЗ-127; обособленные споры ст. 60).
- Блок b) Квалификация + порядок производства → `production_type` остаётся `null` (спец. производство; в выводе явно «N/A для банкротства»).

**4.4. Сводка (Фаза 3) + единый документ (Фаза 4)** — добавить строку «Профиль дела: {category} / {procedure}». Для банкротства в сводку выносится `registry_close_date` как **критичный дедлайн** (П0-маркер).

**4.5. Выходные файлы** — таблица дополняется условным `analysis/registry-deadlines.md` (только для банкротства).

## 5. СЛОЙ 3 — `prepare-hearing` ветвление (глубина — см. R2)

## 8. Зоны сверки для ревью (после правок, перед коммитом)

1. **Контент references не тронут** — diff только в SKILL.md + новый shared-файл; `*-reference.md` без изменений.
2. **Нет осиротевших ссылок** — все §-указатели маршрутной таблицы соответствуют реальным заголовкам секций (сверить с картой §1).
3. **Ownership не нарушен** — legal-review пишет только `registry_close_date`/`procedure`/даты публикации/`production_type`/`qualification`/`jurisdiction`/`pretrial`; init-case — `category`/структура `bankruptcy`/`production_type`. Сверить с conventions §537.
4. **Синоним-нормализация** — «экономические споры» → «исковое (АПК)» обрабатывается в обоих потребителях (v4-карточки не ломаются).
5. **Граница B.3** — ни одна правка не «исправляет» нормы; только маршрут и расчётный механизм.
6. **YAML/links валидны** — относительные пути `../../skills/...` и `shared/...` резолвятся.
7. **Деградация профиля** — если `category=null` (старая/неполная карточка) → дефолт «исковое (АПК)» с явным warning, не падение.
