## 0. Диагноз — что зашито под «один трек» (верифицировано `файл:строка`)

**`shared/case-schema.yaml` — `appeal`/`cassation` = одиночные объекты, не списки:**
- `appeal:` ([case-schema.yaml:301-311](../../shared/case-schema.yaml)) — `judgment_issued_date`, `deadline`, `filed_date`, `hearing_date`, `ruling_date`, `result`. Один обжалуемый акт на дело.
- `cassation:` ([case-schema.yaml:315-337](../../shared/case-schema.yaml)) — `target` (enum: `judgment_with_appeal` / `ruling_settlement` / `ruling_termination`), `appealed_ruling_doc_id`, `appeal_ruling_date`, `deadline`, `filed_date`, `hearing_date`, `ruling_date`, `result`, `instance` (окружной / СКЭС ВС РФ). Три пути — но всё равно **один трек** на дело.
- Прецедент трек-статуса: блок `settlement` имеет `in_progress: false` ([case-schema.yaml:294](../../shared/case-schema.yaml)) — образец для пер-трекового флага активности.

**`shared/conventions.md` — ownership (≈556):** `appeal.*` writes `appeal` + `analyze-hearing` (`hearing_date`/`ruling_date`); reads `cassation`. `cassation.*` writes `cassation` + `analyze-hearing`.

**`init-case/SKILL.md` — запрет на appeal/cassation (мишень F1.8):**
- [SKILL.md:98](../../skills/init-case/SKILL.md): «Поля блоков `appeal.*` / `cassation.*` НЕ заполняй — у них свои owner'ы».
- [SKILL.md:178](../../skills/init-case/SKILL.md): «Остальные поля (… `appeal.*`, `cassation.*` …) при инициализации не трогать».
- НО: образец пометки источника уже есть — [SKILL.md:101](../../skills/init-case/SKILL.md) `production_type_set_by: init-case` + `_set_date`. F1.8 зеркалит этот паттерн.

**Скиллы-потребители (полный список из разведки):** `appeal` (пишет основные `appeal.*`, один акт/один дедлайн), `cassation` (пишет `cassation.*`, выбор одного из трёх `target`), `analyze-hearing` (дописывает `hearing_date`/`ruling_date` обеих инстанций), `draft-judgment` (читает прогноз для сравнения в appeal), `legal-review` (считает сроки обжалования через routing, сами поля не пишет), `settlement` (генерит `court_ruling_id` для `cassation.target=ruling_settlement`).

**References у appeal/cassation УЖЕ существуют (research → дедуп, не с нуля):**
`skills/appeal/references/permissible-grounds.md`; `skills/cassation/references/{permissible-grounds.md, ruling-appeals.md, vs-rf-citation-format.md}`.

## 1. Research-файл «Апелляция регулирование» — применимость и дедуп

Содержание: АПК гл. 34 (ст. 257–272.1) + ГПК гл. 39 (ст. 320–335) — **общий процесс апелляции**, не банкротный.

**Ценное для плагина (3 узла):**
1. **Архитектурный крючок F1.7** (прямое подтверждение): «Апелляционная жалоба может быть подана на несколько судебных актов по одному делу в одной жалобе, **кроме актов по делам о несостоятельности (банкротстве)**» (ППВС № 12 от 30.06.2020) → в банкротстве акты обжалуются **раздельными треками**. + «по банкротным делам — всегда коллегиально (ч. 3 ст. 223 АПК)»; частные определения — 10 дней (ст. 188.1 АПК).
2. **Якорные пленумы:** ППВС № 12 от 30.06.2020 (АПК апелляция); ППВС № 13 от 30.06.2020 (АПК кассация); ППВС № 16 от 22.06.2021 (ГПК апелляция); ППВС № 17 от 22.06.2021 (ГПК кассация); безусловные основания ч. 4 ст. 270 АПК / ч. 4 ст. 330 ГПК.
3. **ГПК-материал** (гл. 39) — для плагина **латентный** (D10: фокус арбитраж/банкротство; ГПК-профиль активен, края позже). Не разворачивать.

**Дедуп-таргеты (проверить пересечение перед встройкой):** `appeal/references/permissible-grounds.md` и `cassation/references/permissible-grounds.md` (основания отмены — возможно, ч. 4 ст. 270/330 уже там); `cassation/references/ruling-appeals.md` (обжалование определений); `deadlines-reference §2` (сроки обжалования АПК). Встраиваем только недублирующее + банкротные крючки.

## 3. СЛОЙ 1 — Схема: `appeal`/`cassation` → списки треков (F1.7)

**Рекомендуемая модель (R1 = вариант C, единый список):** оба блока — список треков; для искового дела обычно **1 элемент**, для банкротства — **по треку на каждый обжалуемый обособленный спор** (ст. 60 ФЗ-127; жалобы по банкротным актам не объединяются).

```yaml
# Треки апелляционного обжалования (F1.7) — СПИСОК.
# Исковое дело: обычно 1 элемент. Банкротство: трек на каждый обжалуемый обособленный спор
# (ст. 60 ФЗ-127; объединять обжалование банкротных актов в одной жалобе нельзя — ППВС № 12).
# writes: appeal (расчётные поля выбранного трека), analyze-hearing (hearing_date/ruling_date),
#         init-case (ФАКТИЧЕСКИ известные поля при постапелляционном входе, origin=intake — F1.8)
# reads: cassation (последовательность/сроки)
appeals: []
  # элемент трека:
  # - track_id: appeal-01            # стабильный id трека
  #   subject: "основной спор"       # что обжалуется (для банкротства — имя обособленного спора)
  #   subject_doc_id: null           # doc-id обжалуемого акта 1-й инстанции (если в index.yaml)
  #   judgment_issued_date: null
  #   deadline: null                 # по типу акта: решение +1 мес; определение/банкротное — спец. (10 дн и др.)
  #   filed_date: null
  #   hearing_date: null
  #   ruling_date: null
  #   result: null                   # upheld | overturned | modified | dismissed | null
  #   in_progress: false             # активен ли трек (образец — settlement.in_progress)
  #   origin: computed               # computed (appeal-скилл) | intake (зафиксировано init-case при входе)
  #   _set_by: null                  # appeal | init-case | analyze-hearing
  #   _set_date: null

# Треки кассационного обжалования — симметрично appeals[].
cassations: []
  # элемент трека: track_id, subject, target (judgment_with_appeal|ruling_settlement|ruling_termination),
  #   appealed_ruling_doc_id, appeal_ruling_date, deadline, filed_date, hearing_date, ruling_date,
  #   result, instance (окружной|СКЭС ВС РФ), in_progress, origin, _set_by, _set_date
```

**Что добавляется к существующим полям:** `track_id`, `subject`, `subject_doc_id`, `in_progress`, `origin`, `_set_by`, `_set_date`. Остальные поля переносятся как есть.

**Версия и миграция (R2):** структурное изменение (объект → список) → **v5 → v6**. Существующие карточки (4 боевых дела) имеют одиночный `appeal:`/`cassation:`. Стратегия совместимости — на выбор:
- (R2-a) **read-compat**: скиллы трактуют legacy-одиночный блок как трек `appeal-01`/`cassation-01` (мягко, без перезаписи файлов);
- (R2-b) **разовая миграция** через `update-index` (или однократный проход): обернуть одиночные блоки в 1-элементный список.
Рекомендация: **R2-a (read-compat)** — у Сюзерена мало дел, ломать карточки не нужно; миграция «лениво» при первом касании трека.

## 4. СЛОЙ 2 — Потребители: выбор/итерация трека (F1.7)

- **`appeal`** — Фаза 0 получает вопрос «какой акт обжалуем?» (для банкротства — какой обособленный спор). Скилл **находит-или-создаёт** элемент `appeals[]` по `subject`/`subject_doc_id` и пишет в него (а не перезаписывает единый объект). Для искового — один трек. Дедлайн считается по типу акта (таблица в appeal SKILL уже есть; банкротные определения — 10 дн / спец., нормы из `deadlines §3`).
- **`cassation`** — то же: работает с выбранным элементом `cassations[]`; `target`/`instance` — пер-трек. Три пути (`judgment_with_appeal`/`ruling_settlement`/`ruling_termination`) сохраняются внутри трека.
- **`analyze-hearing`** — дописывает `hearing_date`/`ruling_date` в **нужный трек**: матчинг по обжалуемому акту (`subject_doc_id`) или, если неоднозначно, уточняющий вопрос Сюзерену. (Design-точка — §4 зоны сверки.)
- **`legal-review`** — при банкротстве может считать дедлайны обжалования пер-трек; основной выход не меняется.
- **`draft-judgment`** — читает прогноз (`expected_outcome`); трек-агностичен, правок не требует (кроме упоминания «трек», если сравнивает с конкретным обжалованием).
- **`conventions.md` ownership** — строка `appeal.*`/`cassation.*` обновляется: writes `appeal`/`cassation`/`analyze-hearing` **+ `init-case` (фактические поля, origin=intake — F1.8)**; модель — список треков.

## 5. F1.8 — `init-case` фиксирует фактические `appeal.*`/`cassation.*` при постапелляционном входе

**Проблема:** клиент часто приходит, когда решение 1-й инстанции (а то и апелляция) уже вынесено. Сейчас init-case это игнорирует ([SKILL.md:98,178](../../skills/init-case/SKILL.md)) → карточка не отражает реальную стадию, у `cassation` нет результата апелляции на входе.

**Решение:**
- В Фазе 3 init-case — определить **стадию входа** по материалам/диалогу: `1 инстанция` (по умолчанию) / `постапелляционная` / `посткассационная`.
- Если стадия > 1 инстанции — создать соответствующий трек `appeals[]`/`cassations[]` и записать **ФАКТИЧЕСКИ известные** поля (`judgment_issued_date`, `ruling_date`, `result`, `instance`) с **`origin: intake`**, `_set_by: init-case`, `_set_date`. **Расчётные/стратегические** поля (`deadline`, выбор оснований) НЕ заполняет — это зона `appeal`/`cassation`.
- Правка [SKILL.md:98](../../skills/init-case/SKILL.md) и [:178](../../skills/init-case/SKILL.md): запрет смягчается — «не заполняй **расчётные** поля `appeal`/`cassation`; при постапелляционном входе зафиксируй **фактически известные** с `origin=intake`».
- Ownership-матрица `conventions.md` + init-case §«Ownership» (≈175): добавить init-case как условного writer фактических полей треков (с пометкой источника).
- Глубина (R3): (a) только зафиксировать известное из материалов; (b) активный структурный опрос Сюзерена по стадии и реквизитам. Рекомендация: **(a) + один уточняющий вопрос о стадии** (в духе уже существующих уточняющих вопросов init-case).

## 8. Зоны сверки для ревью (после правок, перед коммитом)

1. **Совместимость карточек** — 4 боевых дела с одиночным `appeal:`/`cassation:` не ломаются (read-compat R2-a отрабатывает; `yaml.safe_load` проходит).
2. **Все потребители обновлены согласованно** — appeal/cassation/analyze-hearing читают/пишут список, нет осиротевшего кода под одиночный объект; матчинг трека в analyze-hearing определён (по `subject_doc_id` или вопрос).
3. **Ownership не нарушен** — `conventions.md` + init-case §Ownership отражают: init-case пишет только **фактические** поля треков с `origin=intake`; расчётные — appeal/cassation. Сверить.
4. **`origin`/`_set_by` дисциплина** — фактические (intake) и расчётные (computed) поля различимы; downstream не путает «зафиксировано при входе» и «рассчитано скиллом».
