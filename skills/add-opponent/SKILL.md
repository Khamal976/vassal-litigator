# add-opponent -- Прием документов оппонента

Прием, систематизация и первичный анализ документов от процессуального оппонента. Работает по принципу **preview -> apply**. Ключевое отличие от add-evidence: документы маркируются `source: opponent`, раскладываются в процессуальные папки (не в «Материалы от клиента/»), и агент сразу фиксирует ключевые аргументы оппонента.

## Предварительные условия

- Дело инициализировано: `.vassal/case.yaml` существует.
- В `case.yaml` определены стороны (чтобы знать, кто оппонент).
- Папка `Входящие документы/` существует.

## Алгоритм

### Фаза 1 -- Сохранение и обработка

1. Прочитай `.vassal/case.yaml` -- определи, кто оппонент (ответчик, истец, третье лицо). Возьми его `inn`, `ogrn`, `name`, `short_name` из `parties[]` -- это понадобится в фазе 4 для двойной записи в глобальную память.
2. Прочитай `.vassal/index.yaml` -- контекст существующих документов.
2.1. **Загрузи глобальный профиль оппонента** (если есть) -- по правилу из [shared/conventions.md](../../shared/conventions.md) → раздел «Глобальная память (кросс-дельная)»:
   - Разрезолви `$VASSAL_GLOBAL_DIR` (правило «Резолв переменной и онбординг (F.26)»: `$env:` в PowerShell; не задана → fallback + разовое уведомление).
   - Собери **оба** возможных имени файла:
     - `primary_path` = `counterparties/inn-{ИНН}.md`, если `inn` оппонента известен из `case.yaml`; иначе `null`.
     - `fallback_path` = `counterparties/noinn-{slug-name}.md` (slug по правилам conventions на основе `short_name`, иначе `name`).
   - Проверь существование обоих:
     - **Если существуют оба** -- ⚠️ это «теневой дубль» (см. раздел «Дедуп оппонента: inn-/noinn- теневой дубль» ниже). Выведи Сюзерену warning по шаблону оттуда. Рабочий профиль -- `primary_path`; но **загрузи оба** -- наблюдения из fallback не теряются, их можно учесть при сжатии для глобального профиля.
     - **Если существует только `primary_path`** -- загрузи его. Это типовой кейс «оппонент с ИНН, уже встречался».
     - **Если существует только `fallback_path`** -- загрузи его как рабочий. Если в текущем `case.yaml` `inn` теперь известен (а в прошлый раз был null) -- зафиксируй в шаге 19 факт: новый exp-анализ ляжет в `primary_path`, на `fallback_path` останется warning «теневой дубль появится после apply».
     - **Если ни один не существует** -- работай без глобального профиля, не падай. Это первый раз, когда этот оппонент встречается в твоей практике (или глобальная память ещё пуста).
   - Что даёт глобальный профиль: фон «у этого оппонента в других делах уже наблюдалось» **до** экспресс-анализа в фазе 4. Особенно ценно: типовые доводы (любит ли ст. 333 ГК, ходатайствует ли о снижении неустойки регулярно), известные представители, тактика по аналогичным категориям споров.
3. **Источник файлов -- `Входящие документы/`**. **Папка пуста** → отработай единую последовательность из [shared/conventions.md](../../shared/conventions.md) → «Папка „Входящие документы/"» → «Папка пуста — единое поведение трёх приёмников (F.15)»: наружу → `history.md` → `update-index` для разложенного вручную дела → и только потом завершение. Прежнее «сообщи и завершись» было самым бедным из трёх поведений: документ оппонента, положенный Сюзереном мимо «Входящих», просто не находился.
   - **Область (опция, E.5):** если в `$ARGUMENTS` задана подпапка или список файлов (в т.ч. переданный при handoff из `intake`/`add-evidence`) -- бери только их (`shared/conventions.md` → «Маршрутизация приёма по источнику» → «Область»); без аргумента -- вся папка + триаж (после шага 6).
4. Скопируй все файлы в `.vassal/raw/opponent-{ГГГГ-ММ-ДД}/` -- **пристинная копия сохраняется** (документы оппонента/суда удерживаются байт-в-байт ради chain of custody; в записи индекса поставь `raw_pristine: true`). Параллельно вычисли `content_hash` для каждого файла.
4.1. **Дедуп по `content_hash`** (по правилу [shared/conventions.md](../../shared/conventions.md) → «Дедупликация по content_hash»): сверь `content_hash` каждого файла пакета с записями `index.yaml`. Совпадение = документ уже в деле (наш, ранее приобщённый или повторно вложенный оппонентом) → **НЕ создавать** новую `doc-NNN`; запланировать дописать копию в `duplicate_copies` существующей записи (поле `duplicate_copies` в [shared/index-schema.yaml](../../shared/index-schema.yaml): `source`/`file`/`added`) и отразить дубль в Preview.
5. **Извлечение текста — по протоколу `shared/ocr.md`** (как в intake): vision основной; кэш по `content_hash`; `${CLAUDE_PLUGIN_ROOT}/scripts/extract_text.py <файл>` → `text`/`needs_vision`/`vision_pages`/`content_hash`; при `needs_vision` — vision по PNG из `outputs/` (§3); скан/изображение/мусорный слой → vision; длинный скан → структурный режим; low-conf критичные реквизиты → `needs_manual_review` + флаг.
6. **Классификация документов оппонента:**
   - Основной процессуальный документ (отзыв, ходатайство, пояснения, возражение, встречный иск)
   - Приложения к нему (доказательства оппонента)
   - **Бандл или самостоятельные акты?** — по критериям ниже, а не на глаз.

**Критерий «бандл или самостоятельные акты» (F.17).** Раньше шаг 6 ставил этот вопрос и не давал ни одного признака различения — отсюда боевое «пять актов — пять папок» и слипшиеся пакеты. Признаки:

| Бандл (один основной + приложения) | Самостоятельные акты (папка на каждый) |
|---|---|
| Просительная часть **одна**, у основного документа | У **каждого** своя просительная часть / своё процессуальное требование |
| Остальные файлы **перечислены** в нём («Приложения: 1. …») | Ни один не назван приложением другого |
| Приложения суду самостоятельно не адресованы (договор, акт, платёжка) | Каждый адресован суду и подписан отдельно |
| Один исходящий № / одна сопроводительная | Разные исходящие №, каждый — самостоятельное обращение |
| Сквозная нумерация листов через все файлы | В каждом своя нумерация, с первого листа |

**Правило разрешения: перечень приложений основного документа — главный признак.** Файл, названный в перечне, — член бандла, даже если по типу похож на самостоятельный. Файл, не названный нигде и со своей просительной частью, — самостоятельный акт. Признаки противоречат друг другу либо перечня нет → **спроси в Preview**, не угадывай (тот же образец, что для документов от нескольких оппонентов — см. «Граничные случаи»).

**Триаж по источнику (E.5, перед Preview).** Примени [shared/conventions.md](../../shared/conventions.md) → «Маршрутизация приёма по источнику»: классифицируй каждый файл (`opponent` / `court` / `client` / `unclear`), сверяя отправителя/подписанта с `case.yaml.parties[]`. `add-opponent` -- владелец **`opponent`** и **`court`**:
- `opponent` → `source: opponent`, пристинная копия, экспресс-анализ (Фаза 4);
- `court` (определение / решение / постановление / судебное извещение) → `source: court`, пристинная копия, **без** экспресс-анализа оппонента (это не довод оппонента; анализ судебного акта -- дело `appeal` / `analyze-hearing`);
- `client` → **не обрабатывай**; предложи `intake` / `add-evidence` (offer-handoff, Фаза 2);
- `unclear` → уточни у Сюзерена.
При заданной области (в т.ч. handoff) триаж всё равно прогоняется.

**Сверка принадлежности документа делу (F.19, вместе с триажем).** Сверь № дела / ИНН / стороны / суд из текста с `case.yaml` — [shared/conventions.md](../../shared/conventions.md) → «Вторая ось: принадлежность документа делу». Для документов оппонента и суда это особенно предметно: № дела в шапке есть почти всегда, и отличие в одну цифру — типовой случай, а не совпадение. Флаг поднимает **только положительное противоречие**; отсутствие реквизитов — не сигнал. Найдено → отдельный блок в Preview + вопрос (обработать · оставить во «Входящие» · документ другого дела); **файл не двигать, пристинную копию до решения не делать**. Флаг `composite_suspected` из `extract_text.py` **обрабатывай** (раньше `add-opponent` его молча игнорировал): предложи split в Preview, затем сверь принадлежность каждой части отдельно.

**Решающие документы (F.18).** Класс из закрытого списка или пометка Сюзерена ([shared/conventions.md](../../shared/conventions.md) → «Решающие документы: вторая голова») → критичные поля перечитывает **вторая, независимая голова** (Opus, **без** транскрипции первой) + спот-сверка вторым движком; протокол — `shared/ocr.md` §3.2/§6. Для документов оппонента это частый случай: реестр акционеров, бюллетени, протокол собрания приходят именно от него, и цифра в них решает исход. Расхождение → **оба** прочтения в зеркало, поле в `low_confidence_fields`, `needs_manual_review: true`, строка в Preview.

### Фаза 2 -- Preview

7. Определи целевое расположение. Документы оппонента идут в процессуальную папку:
   ```
   {ГГГГ-ММ-ДД} {Сторона оппонента} - {действие}/
   ```
   Например: `2026-04-10 Ответчик - отзыв на иск/`

   `{действие}` — **тип процессуального документа** (единый термин, [shared/conventions.md](../../shared/conventions.md) → «Именование процессуальных папок»; прежде этот скилл называл третий сегмент двумя способами — `{тип документа}` здесь и `{действие}` в разделе «Формат процессуальной папки», F.17).

   **Несколько самостоятельных актов одной датой (F.17)** → папка на **каждый** акт, различаются типом документа:
   ```
   2026-04-10 Ответчик - ходатайство об отложении/
   2026-04-10 Ответчик - возражения на ходатайство о назначении экспертизы/
   ```

   **Коллизия имён** — та же дата + та же сторона + тот же тип (два ходатайства об отложении за день; повторный прогон приёма) → суффикс времени `-{ЧЧММ}` после даты: `2026-04-10-1435 Ответчик - ходатайство об отложении/`. Время берётся из документа (исходящий / отметка о подаче), иначе — время приёма. Суффикс `(2)` для процессуальных папок не используем: он не говорит о содержимом и даёт случайный порядок.

8. Если есть приложения -- оформи как бандл:
   - Основной документ -- anchor бандла
   - Приложения -- members бандла

9. Покажи Сюзерену план:

```
Пакет: opponent-2026-04-10 (4 файла)

2026-04-10 Ответчик - отзыв на иск/
  отзыв.pdf -> 2026-04-10 ООО АСнова Отзыв на исковое заявление.pdf  [основной]
  прил_1.pdf -> 2025-12-15 ООО АСнова Акт приема-передачи.pdf  [приложение]
  прил_2.pdf -> 2026-01-20 ООО АСнова Платёжное поручение №45.pdf  [приложение]

ТРЕБУЮТ ПРОВЕРКИ:
  скан.jpg -> 0000-00-00 Неизвестный Документ.jpg

Ключевые аргументы оппонента (предварительно):
  - Оспаривает сумму: ссылается на частичную оплату 200 000 руб.
  - Заявляет о ненадлежащем качестве товара
  - Просит снизить неустойку по ст. 333 ГК
```

10. Дождись подтверждения.

**Клиентские файлы в Preview (E.5, offer-handoff).** Если триаж нашёл `client`-файлы -- покажи их отдельным блоком и предложи: «N файлов похожи на документы клиента -- оформить через `add-evidence` (или `intake`, если дело только заводится) сейчас?»
- **Да** → доведи опп/court-часть (Фаза 3: свои файлы → «На удаление/»), затем передай управление `add-evidence` / `intake`, ограниченному этими файлами (список файлов как область).
- **Нет** → оставь их во «Входящие» (**не** трогай оригиналы, **не** заводи записи) + сообщи «оформите через `/vassal-litigator:add-evidence`».

### Фаза 3 -- Apply

11. Создай процессуальную папку в корне дела.
12. Скопируй файлы с новыми именами.
13. Создай md-зеркала (Haiku-субагенты, model: "haiku").
14. Обнови `.vassal/index.yaml`:
    - Новые записи с `source` **по факту триажа** (`opponent` для документов оппонента; `court` для судебных актов -- E.5), `raw_pristine: true`, заполненным `content_hash`
    - **Дубль (из шага 4.1):** при совпадении хэша -- не создавай `doc-NNN`, допиши копию в `duplicate_copies` существующей записи (`source: opponent`, `file`, `added`); новую запись не плодить ([shared/conventions.md](../../shared/conventions.md) → «Дедупликация по `content_hash`»)
    - Оформи бандл (если есть приложения): `bundle_id`, `anchor`, `members`. **Самостоятельные акты бандлом не оформляются** (F.17): у каждого своя запись и своя процессуальная папка
    - Поля качества (`seal`/`signature`/`completeness`/`quality`/`needs_manual_review`) -- как в [intake/SKILL.md](../intake/SKILL.md) → «Поля качества документа»; для решающих документов -- `decisive`/`decisive_reason`/`verified_fields` (F.18)
    - Обнови `next_id` (на число новых записей) и `next_bundle_id` (на число созданных бандлов) -- index-schema.yaml, постусловия conventions.md → «Категория 1»
15. Добавь запись в `.vassal/history.md`. Если в фазе 4 был выполнен экспресс-анализ -- укажи: создан локальный `opponent-filing-*.md` и обновлён глобальный `counterparties/{slug}.md`. **Если запись ушла в эфемерный fallback** (`VASSAL_GLOBAL_DIR` не задана, `shared/conventions.md` → «Резолв переменной и онбординг (F.26)» п. 3) -- пометь `(резервный путь ~/.vassal-global/, вне синка -- в песочнице не сохранится)`, не рапортуй как о постоянном. Сбой записи -- укажи причину.
16. **Очистка «Входящие документы/»** -> «На удаление/» через `mv` (как в intake; см. `shared/conventions.md` → «Cowork-first robustness»).

### Фаза 4 -- Экспресс-анализ (опционально)

17. Если основной документ оппонента -- процессуальный (отзыв, возражение, пояснения), предложи Сюзерену:
    «Сделать экспресс-анализ аргументов оппонента?»
18. Если да -- через Opus-субагент (model: "opus"):
    - Извлеки ключевые доводы оппонента
    - Сопоставь с нашей позицией — актуальная сводная `* позиция.md` в корне дела (она там **одна**, F.12); нужна эволюция доводов — `.vassal/analysis/position-*`
    - Сопоставь с глобальным профилем оппонента (загружен в фазе 1 шаг 2.1, если есть): какие доводы повторяются из дела в дело, что нового именно в этом отзыве, какие представители подписали (новые vs известные).
    - Кратко: что нового, что опасно, что легко парируется
    - ⚠️ **Нормы из документа оппонента — гипотезы (F.8).** Процессуальный документ оппонента **сам рассуждает о праве**: его ссылки на статьи, пункты и судебные акты — позиция автора, а не проверенный источник. Не переноси их в аналитику как установленные: сверяй **содержание** нормы (не только номер) по правилу [shared/conventions.md](../../shared/conventions.md) → verify-before-assert, правило 6. Не сверено → «норма {X} заявлена оппонентом — не сверена с текстом закона». Это же поле для контрдовода: перевранная оппонентом норма — сильный аргумент, но только после сверки. Строку-пометку добавь и в EXTRACTION NOTES зеркала.
    - Сохрани в `.vassal/analysis/opponent-filing-{ГГГГ-ММ-ДД}-{doc-id}.md` (префикс `opponent-filing-` -- анализ **письменного** процдокумента оппонента; зеркальный префикс `opponent-hearing-` использует `analyze-hearing` для анализа устной позиции; doc-id -- идентификатор основного процессуального документа оппонента из `index.yaml`).
    - Покажи краткую сводку Сюзерену в чате
19. **Двойная запись в глобальный профиль оппонента** -- по правилу из [shared/conventions.md](../../shared/conventions.md) → «Глобальная память (кросс-дельная)»:
    - Разрезолви `$VASSAL_GLOBAL_DIR` **по правилу «Резолв переменной и онбординг (F.26)»** (в PowerShell -- `$env:VASSAL_GLOBAL_DIR`; не задана → fallback `~/.vassal-global/` + разовое уведомление; в песочнице fallback эфемерен — предупреди на записи).
    - Создай папку `$VASSAL_GLOBAL_DIR/counterparties/` если её нет (`mkdir -p`).
    - **Целевое имя файла -- по приоритету:**
      - Если `inn` известен в `case.yaml` → `inn-{ИНН}.md` (канонический путь).
      - Иначе → `noinn-{slug-name}.md` (slug по правилам conventions из `short_name`/`name`).
    - **Проверь теневой дубль перед записью:** ещё раз пройдись по обоим путям (`inn-...md` и `noinn-...md`) -- они уже были собраны в фазе 1 шаг 2.1. Если **существует не-целевой** файл (например, цель = `inn-7707083893.md`, и при этом найден `noinn-OOO-Romashka.md`) -- после успешной записи в целевой выведи Сюзерену warning по разделу «Дедуп оппонента: inn-/noinn- теневой дубль» ниже. Запись в целевой выполняется в любом случае -- агент **не редактирует и не удаляет** соседний файл (аппенд-only принцип распространяется и на «соседей»; мёрдж -- решение Сюзерена).
    - **Если целевой файл существует** -- открой и аппенд-only дополни наблюдениями из текущего экспресс-анализа. Каждое наблюдение помечается маркером `(дело {case.number}, документ "{краткое имя процдокумента}", {ГГГГ-ММ-ДД})`. Старые наблюдения не редактировать; противоречие -- добавлять как «уточнение».
    - **Если целевого файла нет** -- создай новый со фронтматтером (см. раздел «Формат глобального профиля оппонента» ниже) и наполнением из текущего экспресс-анализа. В `cases:` -- единственный текущий номер дела.
    - В обоих случаях: инкрементируй `filings_analyzed` на 1; добавь `case.number` в `cases:` (без дублей); если в подписантах оппонента есть новые ФИО представителей -- добавь в `representatives:`; обнови `last_updated` и `last_case`.
    - **Сбой записи** (нет прав, ФС недоступна): не падай -- зафиксируй локальный `opponent-filing-*.md`, предупреди Сюзерена шаблоном из conventions, отметь факт в `.vassal/history.md` (см. шаг 15).

**Зачем разведение префиксов:** `prepare-hearing` подтягивает аналитику оппонента glob-ом `.vassal/analysis/opponent-*.md`. Без префикса `filing` / `hearing` устная и письменная аналитика конфликтовали бы по имени файла; с префиксом -- обе попадают в контекст одновременно и не теряются между подготовками.

**Зачем двойная запись:** локальный `opponent-filing-*.md` живёт только в этом деле и насыщен doc-id'ами текущего индекса. Глобальный `counterparties/...md` накапливает паттерны оппонента **сквозь все дела Сюзерена** (типовые доводы, тактика, представители) и читается до анализа -- это ровно то, что в одном деле всегда «слепое пятно», а к третьему делу с тем же оппонентом становится ценным фоном.

20. Если в Notion-конфиге задана `notion.databases.counterparties` (путь резолвится по [shared/conventions.md](../../shared/conventions.md) → «Notion-слой» → «Конфигурация») **и** был выполнен экспресс-анализ (фаза 4) -- предложи Сюзерену:

Неблокирующая рекомендация (как в `analyze-hearing` / `appeal` / `cassation`); при отсутствии конфига или `counterparties` -- пропустить молча. Закрывает заявленный авто-триггер `add-opponent` в `notion-sync` («Авто-триггеры»).

## Постусловия

- Все **свои** (opponent/court) файлы из «Входящие документы/» разложены по процессуальным папкам и перемещены в «На удаление/» (`mv`). Клиентские файлы (триаж E.5) либо переданы `intake`/`add-evidence` (handoff), либо оставлены во «Входящие» -- их `add-opponent` не трогает.
- Каждый новый документ в `index.yaml` с `source: opponent` (или `court` для судебных актов -- E.5), `raw_pristine: true`, заполненным `content_hash`; дубли (по хэшу) -- в `duplicate_copies`, без отдельных записей.
- `next_id` и `next_bundle_id` инкрементированы; пристинные копии в `.vassal/raw/opponent-{дата}/`.
- **Разложение по папкам (F.17):** каждый самостоятельный акт -- в своей процессуальной папке, бандл -- в одной; решение принято по критериям шага 6, при неоднозначности спрошено у Сюзерена. Коллизия имён разведена суффиксом `-{ЧЧММ}`, не `(2)`.
- **Решающие документы (F.18) и принадлежность делу (F.19)** -- по общим постусловиям [shared/conventions.md](../../shared/conventions.md) → «Постусловия скиллов» → «Категория 1»: `verified_fields` заполнен либо явно пуст с указанием причины; ни один файл не отбракован молча.
- Запись в `history.md` добавлена; при экспресс-анализе -- локальный `opponent-filing-*.md` и (если доступна) глобальная память оппонента обновлены.
- `case.yaml` не изменялся (add-opponent его не пишет).

### Правило накопления

При двойной записи (фаза 4 шаг 19):
- В соответствующий раздел дописываются новые наблюдения с маркером `(дело {номер}, документ "{краткое имя}", {ГГГГ-ММ-ДД})`.
- Старые наблюдения **не удаляются и не редактируются**; противоречие -- добавлять как «уточнение» с новой датой.

## Дедуп оппонента: inn-/noinn- теневой дубль

**Как возникает:** в одном деле `case.yaml.parties[].inn` оппонента не заполнен (например, забыли при init-case) → `add-opponent` создаёт `noinn-{slug}.md`. В другом деле тот же оппонент уже с ИНН → создаётся `inn-{ИНН}.md`. На один реальный субъект -- два файла в `$VASSAL_GLOBAL_DIR/counterparties/`, наблюдения раздроблены.

**Что делает скилл (фаза 1 шаг 2.1, фаза 4 шаг 19):** обнаруживает оба файла перед чтением/записью и предупреждает Сюзерена, **не редактирует** и **не удаляет** ни один из них -- мёрдж это решение человека (риск потерять наблюдения слишком велик, чтобы автоматизировать).

**Шаблон warning Сюзерену:**

```
⚠️ Теневой дубль профиля оппонента в глобальной памяти

Оппонент: {display_name из case.yaml}
Найдено две записи в $VASSAL_GLOBAL_DIR/counterparties/:
  • {primary_path}   (по ИНН -- канонический, рабочий)
  • {fallback_path}  (без ИНН -- образовался, когда в каком-то деле ИНН не был указан)

Текущий экспресс-анализ записан в: {фактический целевой путь}.
Соседний файл не тронут.

Рекомендация: смёрджить вручную.
  1. Открыть оба файла, сравнить разделы «1. Типовые доводы», «2. Тактика», «3. Представители», «4. Доказательственная стратегия», «5. Что работало против него».
  2. Скопировать уникальные наблюдения из {fallback_path} в {primary_path} (с сохранением маркеров источника).
  3. Обновить во frontmatter {primary_path}: `cases:` -- объединение списков; `filings_analyzed` и `hearings_analyzed` -- сумма; `representatives:` -- объединение; `last_updated` -- max.
  4. Удалить {fallback_path} вручную (или переместить в «На удаление/» на уровне глобальной папки -- если такая практика принята).

Превенция повторения: убедись, что в `case.yaml` всех новых дел этого оппонента ИНН заполнен (см. чек в legal-review фазы 3).
```

**Когда warning не выводится:** если найден только canonical (`inn-*.md`) или только fallback (`noinn-*.md`) -- это нормальная работа, тишина.

## Идемпотентность

Секции не было -- `add-opponent` оставался единственным ingest-скиллом без неё, а повторный прогон в ту же дату упирался прямо в коллизию имён процессуальных папок (F.17).

- **Дедуп по `content_hash`** (шаг 4.1) -- основной ключ: файл с уже известным хэшем новую `doc-NNN` не создаёт, копия дописывается в `duplicate_copies`. Повторный запуск на том же пакете записей не плодит.
- **Процессуальная папка уже существует** (та же дата + сторона + тип):
  - содержимое совпадает по хэшам -> ничего не делаем, сообщаем «пакет уже принят {дата}»;
  - пришли **новые** файлы к тому же документу -> доносим в существующую папку, новую не заводим;
  - пришёл **другой** акт того же типа и даты -> новая папка с суффиксом `-{ЧЧММ}` (F.17).
- **Пристинные копии** в `.vassal/raw/opponent-{дата}/` не перезаписываются: то же имя + тот же хэш -> пропуск; то же имя + другой хэш -> суффикс `(2)`.
- **Глобальный профиль оппонента** аппенд-only: повторный экспресс-анализ того же процдокумента **не** инкрементирует `filings_analyzed` второй раз -- сверяй по маркеру наблюдения (`дело`, краткое имя документа, дата).
- **Второе чтение решающих полей** (F.18) не перезапускается при неизменном `content_hash` и заполненном `verified_fields` -- переиспользуется кэш зеркала (`shared/ocr.md` §4).

## Граничные случаи

- Документы от нескольких оппонентов в одном пакете -> создай отдельную папку для каждого.
- **Несколько самостоятельных актов одного оппонента одной датой** (F.17) -> папка на каждый акт, третий сегмент имени -- тип документа; критерии отличия от бандла -- шаг 6. Боевой случай: пять актов пришли одним пакетом, и правила для них не было.
- **Документ, похожий на «из другого дела»** (F.19) -> флаг и вопрос, никогда молчаливый отсев; до решения Сюзерена файл остаётся во «Входящие», пристинная копия не делается.
- **Решающий документ, для которого не отработала вторая голова** (F.18) -> индексируется штатно, `verified_fields` пуст, и это прямо сказано в отчёте: «критичные поля не прошли второе чтение -- сверить по оригиналу».
- **Судебный акт** (определение / решение / постановление / судебное извещение) во «Входящие» -> `add-opponent` его принимает с `source: court` (пристинная копия, **без** экспресс-анализа оппонента; триаж E.5). Дальнейший анализ решения -- `appeal` / `analyze-hearing`.
- **Клиентские документы во «Входящие»** (триаж E.5) -> `add-opponent` их **не обрабатывает** (не помечает `source: opponent`, не двигает оригинал); предлагает `intake` / `add-evidence` (offer-handoff, Фаза 2).
- Оппонент прислал документ, уже имеющийся в деле (наши же документы либо ранее приобщённое) -> по дедупу `content_hash` (шаг 4.1) не создавай отдельную запись, а допиши копию в `duplicate_copies` существующей ([shared/index-schema.yaml](../../shared/index-schema.yaml), поле `duplicate_copies`).
- **Сбой извлечения по `error_class` (E.14)** -> `not_materialized`/`retryable: true` -- файл не синкнут OneDrive: ретрай с паузой (сначала Read материализует), **не** «битый» и **не** делай пристинную копию до успеха; `corrupt` -- реально битый: не индексируй, не копируй в пристинную, оставь во «Входящие», «перезалейте»; `empty` -- 0-байт, пропуск. Детали -- `shared/ocr.md` §9.
