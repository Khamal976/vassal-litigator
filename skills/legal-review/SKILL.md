# Legal-Review — Первичный правовой анализ дела

Скилл выполняет комплексную правовую проверку дела и генерирует набор аналитических документов в `.vassal/analysis/`. Работает с Opus для глубокого анализа. Каждый вывод оформляется в аудируемом формате (см. `shared/conventions.md` → Аудируемость выводов).

## Предварительные условия

- Дело инициализировано: `.vassal/case.yaml` существует.
- Документы приняты: `index.yaml` содержит хотя бы 1 документ.
- **Рекомендуется:** перед запуском провести `catalog` (чтобы в index.yaml были summary).
- Установлены зависимости: `${CLAUDE_PLUGIN_ROOT}/scripts/setup.sh`.

## Входные данные

1. **case.yaml** — карточка дела (стороны, суть спора, суд, представитель).
2. **index.yaml** — полный реестр документов с summary.
3. **md-зеркала** ключевых документов (скилл сам определяет, какие загрузить).
4. **Вводная Сюзерена** (опционально) — конкретные вопросы, которые нужно разобрать. Может быть передана как аргумент команды или файл.

## Алгоритм

### Фаза 0 — Проверка консистентности ФС ↔ индекс

Перед загрузкой контекста выполни Phase 0 по правилу из [shared/conventions.md](../../shared/conventions.md) → раздел «Проверка консистентности ФС ↔ индекс (Phase 0)». При обнаружении рассинхрона предложи Сюзерену запустить `update-index`. Если Сюзерен выбрал «продолжить» -- зафиксируй в выходном артефакте, что анализ выполнен на устаревшем индексе.

### Фаза 1 — Загрузка контекста

1. Прочитай `.vassal/case.yaml` — получи стороны, предмет спора, суд, даты.
2. Прочитай `.vassal/index.yaml` — получи список документов.
3. Определи **ключевые документы** для анализа — те, которые нужно читать целиком:
   - Договор (основной) и все допсоглашения
   - Претензия / ответ на претензию
   - Исковое заявление (если есть)
   - Отзыв на иск (если есть)
   - Гарантийные письма, акты сверки — если есть
4. Загрузи md-зеркала ключевых документов из `.vassal/mirrors/`.
5. Для остальных документов достаточно summary из index.yaml.
5.1. **Хук `study-evidence`:** проверь `.vassal/analysis/evidence-dossier.md`. Если досье есть — загрузи его как приоритетный источник фактуры (факты со ссылкой на лист, кросс-сверка сумм / реквизитов). Если нет — предложи Сюзерену (**не блокируя**) собрать его через `study-evidence` до анализа; при отказе работай на зеркалах как прежде, отметив в выходном артефакте «фактура не верифицирована study-evidence».
6. Если Сюзерен передал вводную / вопросы — прочитай и зафиксируй. **Если вводная просит оценить перспективы / шансы / риски по требованию (E.15а) — пометь: это зона `build-position`, legal-review её не выполняет; офер запустить `build-position` дашь в Фазе 3.** Первичные вопросы клиенту (что запросить, где пробелы) собираются как обычно в блоке g.

### Фаза 1.5 — Определение профиля дела

Профиль задаёт маршрут всех нормоёмких блоков (сроки, досудебка, подсудность). Источник маршрута — [`shared/category-routing.md`](../../shared/category-routing.md). Выполни ДО анализа:

1. Прочитай `case.category`. **Нормализуй:** `"экономические споры"` → `"исковое (АПК)"`; `null` / неизвестно → дефолт `"исковое (АПК)"` + **warning** Сюзерену («категория дела не указана — анализ по профилю АПК-искового; уточни `case.category`, если это банкротство / СОЮ / КАС»). Не падать.
2. Если `category = банкротство` — прочитай `case.bankruptcy.procedure` (ключ банкротного под-роутера `category-routing.md §4`).
3. По `category-routing.md` определи: `competent_court`, секции справочников для блоков c/d/e, нормы-маркеры профиля. Если `case.jurisdiction.competent_court` ещё пуст — заполни (owner — `legal-review`).
4. Зафиксируй профиль в шапке анализа аудируемо: «Профиль дела: {category}{ / procedure — для банкротства}; competent_court = {...}; маршрут блоков — `category-routing.md`».

Блоки c/d/e Фазы 2 применяют секции и нормы **профиля**, а НЕ дефолт-АПК-искового.

### Фаза 2 — Анализ (Opus)

> **verify-before-assert** (см. `shared/conventions.md`): перед каждым выводом сверь опорные факты, цитаты и реквизиты по md-зеркалам/оригиналам. Непроверяемое по материалам → не вывод, а пометка «факт не проверен — сверить» (уверенность «низкая»). Зеркало с `needs_manual_review: true` не используй как источник дословных формулировок/реквизитов.
> **Дословная сверка Пленумов (E.7 п.2):** цитируя конкретный пункт ППВС / Обзора, сверь **дословный текст пункта** (не только номер — содержание могло перепутаться) по B.3-верифицированному reference / коннектору / web-whitelist; не сверено дословно → пометка «пункт {X} ППВС № {Y} не сверён дословно — проверить текст», не подавать как установленную позицию Пленума.

Выполни каждый блок анализа. **Каждый вывод** оформляй в аудируемом формате:

```
**Вывод:** [заключение]
**Фактическое основание:** [на чём основано — факты из документов]
**Правовое основание:** [нормы, статьи, пункты]
**Источники:** [названия документов с датами — НЕ doc-ID; человек читает названия, а не идентификаторы]
**Уверенность:** высокая | средняя | низкая
**Недостающие данные:** [чего не хватает для уверенного вывода]
```

#### a) Ответы на вопросы Сюзерена → `analysis/answers.md`

Если Сюзерен задал конкретные вопросы — ответь на каждый в аудируемом формате. Если вопросов не было — пропусти этот блок.

#### b) Квалификация правоотношений → `analysis/qualification.md`

- Тип правоотношений (поставка, подряд, услуги, аренда, заём и т.д.)
- Применимые нормы (глава ГК РФ, специальные законы)
- Существенные условия договора — соблюдены ли
- Есть ли основания для признания договора незаключённым / недействительным

#### c) Пресекательные сроки → `analysis/deadlines.md`

**Маршрут по профилю** (Фаза 1.5): открой секцию `references/deadlines-reference.md`, указанную в [`category-routing.md §3.1`](../../shared/category-routing.md) для текущего профиля, и применяй её нормы-маркеры. НЕ переноси сроки АПК-искового на иной профиль.

Для каждого выявленного срока — таблица:

| Срок | Тип | Начало | Истечение | Статус |
|------|-----|--------|-----------|--------|
| ... | материальный / процессуальный | дата | дата | действует / истёк / под вопросом |

Что проверить — по профилю:
- **Исковые (АПК / ГПК), корпоративный:** исковая давность (общая 3 года ст. 196 ГК + специальные; течение ст. 200; приостановление ст. 202 — претензия/мораторий; перерыв ст. 203 — признание долга) + процессуальные сроки обжалования профиля (АПК — апелляция 1 мес / кассация 2 мес, §2; ГПК — §4).
- **Трудовой спор:** специальные сроки обращения **ст. 392 ТК** (1 мес по увольнению / 3 мес общий / 1 год по зарплате) — это материальные сроки, НЕ исковая давность ГК (deadlines §6).
- **Административное (КАС / АПК гл. 24):** срок обращения (КАС — ст. 219; АПК — 3 мес) — deadlines §5.
- **Банкротство:** реестровые сроки и расчёт даты закрытия реестра — под-блок ниже (P0).

**Банкротство — расчёт даты закрытия реестра (P0) → `analysis/registry-deadlines.md`:**
По банкротному под-роутеру ([`category-routing.md §4`](../../shared/category-routing.md)) и `case.bankruptcy.{procedure, publication}` рассчитай дату закрытия реестра требований кредиторов (наблюдение — 30 дн с публикации, ст. 71; конкурс — 2 мес с публикации, ст. 142 — нормы из `deadlines-reference §3` как написано, не выводи свои). Запиши в `case.bankruptcy.registry_close_date` + `registry_close_basis` (норма + от какой публикации считал). Пропуск = зареестровое требование (потеря очерёдности) — вынеси как **критичный дедлайн**. При релевантности позиции клиента проверь также сроки оспаривания сделок (гл. III.1) и субсидиарки (ст. 61.14). Сохрани отдельным файлом `analysis/registry-deadlines.md`.

**Нет даты публикации → `registry_close_date: null` (E.15б).** Если `bankruptcy.publication.date` пуст / неизвестен (зрелое дело, клиент пришёл поздно, публикация о процедуре не в материалах) — P0-поле **нерассчитываемо**. Это **валидный исход, не провал и не «падение»**: поставь `registry_close_date: null`, а `registry_close_basis` заполни объяснением — «публикация о {procedure} не найдена в материалах / не наступила — реестровый срок не рассчитан; получить дату публикации ЕФРСБ (fedresurs.ru) или Коммерсантъ (№ сообщения) и пересчитать». Вынеси запрос даты публикации в `questions-to-client.md` как **критичный [!]**, а в `registry-deadlines.md` отметь «P0 не рассчитан — нет даты публикации; риск пропуска реестрового срока не оценён». Остальной анализ (подсудность, полнота, квалификация, прочие сроки) выдаётся штатно — одно недостающее поле не блокирует заключение.

#### d) Досудебный порядок → `analysis/pretrial.md`

**Маршрут по профилю** (Фаза 1.5): открой секцию `references/pretrial-reference.md` по [`category-routing.md §3.2`](../../shared/category-routing.md). Досудебный порядок профиль-специфичен — НЕ применяй ч. 5 ст. 4 АПК к небанкротному / неисковому профилю по умолчанию.

- **Исковое (АПК), корпоративный:** обязательный претензионный порядок ч. 5 ст. 4 АПК (30 кал. дней) + договорный порядок; претензия направлена / получена / в срок? (pretrial §1–§4).
- **Банкротство:** классическая претензия НЕ требуется; вместо неё — предъявительский ценз кредитора (просуженность долга / уведомление на Федресурсе, ст. 7 п. 2.1) — проверь готовность кредиторского входа (pretrial §5).
- **Исковое (ГПК):** досудебка по ГПК — потребители / ОСАГО / ЖКХ (pretrial §6).
- **Трудовой спор:** досудебный порядок НЕ обязателен; КТС / ГИТ — альтернативы, не обязательный порядок (pretrial §9).
- **Административное:** налоговые — обязательное досудебное обжалование (ст. 138 НК, §7); иные ненорм. акты — §8.
- Вывод: соблюдён / не соблюдён / частично / **не требуется для профиля**.

**Развилка убытков — проверять всегда (B.20).** По п. 43 ППВС № 18 к денежным спорам абз. 1 ч. 5 ст. 4 АПК относятся **убытки по гл. 25 ГК (договорные)** — претензия обязательна. Убытки из причинения вреда (гл. 59 ГК) и регрессное требование изъяты (п. 44 ППВС № 18) — не нужна. Квалификация решает исход; при неоднозначности фиксируй развилку в `pretrial.md`, а не выбирай молча.

**Точка отсчёта срока (B.20).** По общей норме АПК срок течёт **со дня направления** претензии, а не получения. По специальным нормам иначе: транспорт — со дня получения (ст. 124 УЖТ, ст. 40 ФЗ № 259-ФЗ, ст. 163 КВВТ, ст. 407 КТМ), связь — со дня регистрации (п. 4 ст. 55 ФЗ № 126-ФЗ). Бери точку отсчёта из колонки «Точка отсчёта» таблицы `pretrial-reference.md`, не по умолчанию.

**Хук на `draft-claim` (B.20).** Если по итогам вывод — **«не соблюдён»** или **«частично»**, а порядок обязателен (`pretrial.required = true`), предложи Сюзерену в Preview отдельной строкой:

> «Досудебный порядок обязателен ({норма}), претензия не направлена. Запустить `draft-claim` — подготовить претензию?»

Запиши `pretrial.required` / `required_source`; остальные поля блока `pretrial` заполняет `draft-claim` (см. `shared/case-schema.yaml` → ownership). Если пришла **входящая** претензия к нашему клиенту — тот же хук, но с `mode = reply`.

**Хук на `enforcement-adjustment` (F.21).** Если в материалах есть признаки **стадии исполнения** — исполнительный лист, постановление о возбуждении исполнительного производства, требование пристава, постановление о взыскании исполнительского сбора, — зафиксируй известное в `case.enforcement` (реквизиты ИЛ, номер ИП, пристав) и предложи Сюзерену в Preview отдельной строкой:

> «По делу идёт исполнительное производство ({реквизиты}). Если исполнение затруднено — `enforcement-adjustment` подготовит заявление об отсрочке, рассрочке или изменении способа и порядка исполнения (ст. 324 АПК / ст. 203, 434 ГПК / ст. 358 КАС). Если заявление подал оппонент — тот же скилл в режиме возражений.»

Правовой профиль — [references/enforcement-reference.md](references/enforcement-reference.md). **Три развилки, которые надо назвать сразу, а не после:**
- акт **обжалуется** → нужна не отсрочка, а приостановление исполнения, и его вправе дать только апелляция / кассация / надзор (п. 29 ППВС № 50 **от 17.11.2015**) → `appeal` / `cassation`;
- взыскатель **готов договориться** → дешевле мировое на стадии исполнения → `settlement` (`mode='agreement'`, `stage='enforcement'`);
- речь про отсрочку уплаты **госпошлины** → это ст. 333.41 НК, другой институт (`filing-fees.md` §4).

⚠️ В плагине два разных акта под номером 50: **ППВС № 50 от 17.11.2015** (исполнительное производство) и **ППВАС № 50 от 18.07.2014** (примирение). Всегда с датой и префиксом.

#### e) Подсудность → `analysis/jurisdiction.md`

**Шаг 0 (обязательный, до всего остального) — специальная норма о компетенции в профильном законе (F.6).**

Общие правила кодексов (субъектный критерий ст. 27 АПК → предметный → закрытый перечень ст. 33) применяются **только после** проверки профильного закона. Специальная норма о подведомственности бьёт общий критерий, и её отсутствие в кодексе ничего не доказывает — она живёт в отраслевом законе.

1. Определи, из каких отношений вырос спор и **какой отраслевой закон** их регулирует: банкротство и профессиональная деятельность арбитражного управляющего — ФЗ-127; страхование — ФЗ-4015-1 / ФЗ-40; корпоративные — ФЗ-14 / ФЗ-208; интеллектуальные права — ч. IV ГК; закупки — ФЗ-44 / ФЗ-223; деятельность СРО — профильный закон о соответствующей СРО.
2. **Открой этот закон** и проверь, есть ли в нём норма о том, каким судом рассматриваются споры этой категории. Не по памяти — по тексту (B.3-верифицированный reference / коннектор / web-whitelist).
3. Только после этого иди к субъектному и предметному критериям кодекса.

**Проверяемый след — обязателен в выводе:** строка «**Специальная норма:** {норма + где сверена} | не найдена (проверен {закон})». Вывод о компетенции без этой строки не выдаётся. Пустой результат — тоже результат: он показывает, что закон открывали.

⚠️ **Подтверждающая практика не заменяет шаг 0.** Боевой промах: компетенция выводилась от общего критерия, поиск практики дал ложную уверенность, а специальная норма (п. 12 ст. 20 ФЗ-127 — споры, связанные с профессиональной деятельностью АУ, включая возмещение убытков и отношения с СРО) осталась непрочитанной. Итог — иск переписывали в двух делах подряд с пересчётом пошлины. Практика подтверждает найденное в законе, а не заменяет его чтение.

Готовый разбор для споров с арбитражным управляющим вне рамок дела о банкротстве — `references/jurisdiction-reference.md §5`, подраздел «Споры с арбитражным управляющим вне рамок дела о банкротстве».

**Маршрут по профилю** (Фаза 1.5): открой секцию `references/jurisdiction-reference.md` по [`category-routing.md §3.3`](../../shared/category-routing.md).

- **Исковое (АПК), корпоративный:** компетенция (ст. 27/33; корп. — 225.1); территориальная — общая ст. 35 / договорная ст. 37 / исключительная ст. 38 АПК; пророгационная / дерогационная оговорка (§1–§4).
- **Банкротство:** по месту нахождения должника (ст. 33 ФЗ-127); обособленные споры (ст. 60); проверь «миграцию должника» перед банкротством (§5).
- **Исковое (ГПК):** ст. 28–32 ГПК (§7).
- **Трудовой спор:** ст. 24/28/29 ГПК; альтернатива по выбору работника; **договорная подсудность ИСКЛЮЧЕНА** (§10).
- **Административное:** КАС — §8; АПК (гл. 24/25) — разграничение §9.
- Если дело уже подано — проверь, в правильный ли суд.

**Машиночитаемый статус вывода (F.9).** Вывод о компетенции — единственный, который скиллы ниже по конвейеру принимают как данность, поэтому кроме аудируемого блока запиши его статус в карточку (зона ownership `legal-review`):

- `case.jurisdiction.confidence` — `высокая | средняя | низкая`, та же оценка, что в аудируемом выводе;
- `case.jurisdiction.special_norm_checked` — `true | false`: прогонялся ли шаг 0 (профильный закон открыт);
- `case.jurisdiction.special_norm` — найденная специальная норма или `null`.

Уверенность **ниже высокой** — не просто поле отчётности: по правилу [shared/conventions.md](../../shared/conventions.md) → «Статус вывода о компетенции (F.9)» это **блокирует первичную подачу** (иск / заявление по существу / заявление об обеспечительных мерах) до явного подтверждения Сюзерена. Скажи об этом прямо в сводке Фазы 3 — вопрос дешевле решить сейчас, чем на этапе подачи.

#### h) Госпошлина — детект потребности (F.7)

`legal-review` пошлину **не считает** (владелец расчёта — `build-position`, он владеет `case.amounts.court_fee`), но обязан заметить, что она потребуется, и не дать уйти в подачу с цифрой «на глаз».

1. **Потребуется ли пошлина** — по стадии и типу предстоящего обращения: первичный иск / заявление, заявление об обеспечительных мерах (оплачивается **отдельно от иска, за каждое**), апелляционная / кассационная жалоба, заявление о выдаче исполнительного листа. Если по делу ничего не подаётся (анализ для оценки) — блок пропускается.
2. **Какая секция справочника** — по [`category-routing.md §3.4`](../../shared/category-routing.md) → `references/filing-fees.md`. Назови секцию явно: «пошлина — `filing-fees.md` §{X}».
3. **Есть ли чем считать** — цена иска (`case.amounts.claim`) известна и подтверждена материалами? Нет → **критичный вопрос [!]** в `questions-to-client.md`: без цены иска пошлина не считается, а ошибка в ней — это отказ в принятии или оставление без движения.
4. **Льготы** — проверь применимость (`filing-fees.md` §1.4 для АС / §2.4 для СОЮ; для трудовых споров работник освобождён).

**Выход:** отдельного файла нет — строка в сводке Фазы 3 и, при нехватке данных, вопрос в `questions-to-client.md`. Расчёт передаётся `build-position`:

> «Пошлина по делу потребуется ({тип обращения}); секция — `filing-fees.md` §{X}. Расчёт — зона `build-position` (поле `case.amounts.court_fee`). {Цена иска не подтверждена — см. критичный вопрос клиенту.}»

⚠️ Боевой промах, который закрывает этот блок: справочник был актуален и содержал прямую строку «обеспечение иска — 30 000 за каждое», но на первичном пути его никто не открывал — цифру взяли из старого судебного акта и ошиблись в 3,9 раза (30 193 ₽ вместо 117 760 ₽).

#### f) Качество и полнота документов → `analysis/completeness.md`

Для каждого документа из index.yaml оцени:
- Читаемость (по полю quality в индексе)
- Полнота (completeness): есть ли все страницы, подписи, печати
- Юридическая значимость (оригинал / копия / скан)

**Сверка полноты (заявлено vs вложено).** Если в описи вложения / расчёте / перечне приложений заявлено N единиц (платёжки, документы) — сверь N и их реквизиты с фактически извлечёнными из файла-доказательства; итоговые суммы проверь пересчётом (сумма единиц = заявленный итог). Расхождение → пометь документ `needs_manual_review: true` и вынеси явный флаг Сюзерену (риск недоказанной суммы / отсутствующего приложения). Не переноси заявленное число, не убедившись в фактическом.

Сформируй список:
- **Имеющиеся доказательства** — что есть и в каком состоянии
- **Отсутствующие документы** — что следует запросить у клиента
- **Документы, требующие дополнительных действий** — нотариальное заверение, апостиль, перевод, запрос оригинала

#### g) Вопросы клиенту → `analysis/questions-to-client.md`

Собери все вопросы, возникшие при анализе:
- Фактические вопросы (хронология событий, суммы, обстоятельства)
- Запрос недостающих документов (конкретный список)
- Уточнения по позиции клиента (что хочет: взыскать, отбить, мировое?)

Каждый вопрос пометь приоритетом: [!] критичный | [*] важный | [ ] желательный.

## Идемпотентность

**Детект повторного прогона.** Если в `.vassal/analysis/` уже есть файлы от прошлого `legal-review` — это повторный запуск. Сначала через Phase 0 выясни, появились ли новые документы с прошлого прогона. Затем предложи Сюзерену выбор:
- **полный** — переанализировать всё заново;
- **инкрементальный** — учесть только новые документы и обновить затронутые блоки.

**Версионирование, не перезапись.** Новые файлы анализа создаются с `supersedes`-ссылкой на предыдущие (см. `shared/conventions.md` → «Двухуровневое сохранение для аналитических скиллов»); старые **не удаляются** (история мысли по делу). В preview покажи diff (что изменилось с прошлого раза).

**Архивация сводного (F.12).** Перед записью нового `* Предварительный анализ документов.md` уведи предыдущий в `Архив/` (`mkdir -p`, затем `mv`) — в корне остаётся **ровно один**. Файлы в `.vassal/analysis/` (`qualification.md`, `deadlines.md`, `pretrial.md`, `jurisdiction.md`, `completeness.md`, `questions-to-client.md`, `answers.md`) **не архивируются**: служебная зона остаётся на месте, а `questions-to-client.md` / `answers.md` вообще аппенд-только. **Изменений нет → снимка нет:** инкрементальный прогон, не изменивший выводов, нового сводного файла не создаёт.

## Граничные случаи

- Нет ни одного документа в индексе → сообщи, что анализировать нечего, предложи intake.
- Нет договора → анализ возможен, но пометь: «Договор отсутствует, выводы по квалификации предварительные».
- Данных недостаточно для вывода → не додумывай, честно укажи «Недостающие данные» и уверенность «низкая».
- Противоречия между документами → зафиксируй в `completeness.md` и в `questions-to-client.md`.
- Нестандартный спор (не из ГК) → примени ту же структуру анализа, адаптируй нормативную базу.
