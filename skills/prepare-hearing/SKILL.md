# prepare-hearing -- Подготовка к заседанию

Ключевой рабочий скилл фазы ведения дела. Формирует обновленную позицию с учетом всех новых обстоятельств (документы оппонента, новые доказательства, результаты предыдущих заседаний) и генерирует процессуальный документ (подаваемый `.md`; оформление в `.docx` -- через `format-doc`, headless in-plugin).

## Ключевой принцип: сначала контекст, потом документ

> Источник: алгоритм Мошкина С.А. (runetlex.academy)

Главная ошибка -- сразу просить нейросеть "написать возражение на иск". Без контекста результат будет формально похож на документ, но по существу бесполезен. Правильный порядок: сначала насытить контекст всеми материалами дела, и только потом ставить задачу на составление документа.

## Предварительные условия

- Дело инициализировано, intake выполнен.
- Есть позиция в корне дела (`* позиция.md` — по F.12 она там одна).
- Для первого заседания: достаточно начальной позиции.
- Для последующих: желательны отчеты о предыдущих заседаниях (`.vassal/hearings/`).

## Входные данные от Сюзерена

Перед началом уточни у Сюзерена:

1. **Какой документ готовим?** (отзыв на иск, ходатайство, пояснения, дополнение к позиции, возражение на отзыв, заявление)
2. **Есть ли специальные указания?** (акценты, стратегия, что не включать)
3. **Дата заседания** (если известна -- для контекста срочности)
4. **Есть ли образец стиля?** (если Сюзерен хочет документ в определенном стиле -- загрузить образец)

Если Сюзерен сразу дал конкретные указания в аргументах команды -- не переспрашивай, работай по ним.

## Алгоритм

### Фаза 0 -- Проверка консистентности ФС ↔ индекс

Перед загрузкой контекста выполни Phase 0 по правилу из [shared/conventions.md](../../shared/conventions.md) → раздел «Проверка консистентности ФС ↔ индекс (Phase 0)». Если в деле появились новые материалы (напр., только что пришли документы оппонента, файлы судьи) или зеркала переименованы вручную -- предложи Сюзерену запустить `update-index` или соответствующий ingest-скилл (`add-evidence` / `add-opponent`) перед подготовкой к заседанию. Анализ перед заседанием на устаревших данных -- особенно опасен: можно пропустить новый аргумент оппонента и не подготовить парирование.

### Фаза 1 -- Загрузка контекста (порядок критически важен)

Порядок загрузки материалов влияет на качество анализа. Доказательства и фактические материалы загружаются ПЕРВЫМИ, процессуальные документы сторон -- ПОСЛЕДНИМИ. Это позволяет агенту сформировать собственное понимание ситуации по первоисточникам, не поддаваясь влиянию позиции, изложенной в процессуальных документах.

**Шаг 1 -- Описание ситуации (case.yaml + позиция):**
1. Прочитай `.vassal/case.yaml` -- стороны, суд, предмет, хронология. Возьми `case.judge`, `case.court` (для глобального профиля судьи) и `inn`/`name` оппонента из `parties[]` (для глобального профиля оппонента).
1.1. **Определи профиль дела** по `case.category` (+ `bankruptcy.procedure` для банкротства) через [`shared/category-routing.md`](../../shared/category-routing.md). Профиль задаёт: номенклатуру готовящегося документа (исковая / банкротная -- см. «Типы процессуальных документов»), какой чек-лист просительной применять и какие нормы-маркеры брать в правовое обоснование. Зафиксируй профиль в prep-артефакте (§6).
1.2. **Сверка статуса компетенции (F.9) -- до генерации документа.** Вывод о форуме этот скилл раньше принимал молча: фаза загрузки брала карточку, индекс, позицию и `analysis/*`, но отдельной сверки компетенции не делала -- и «средняя» уверенность по подсудности не останавливала ничего. Прочитай `case.jurisdiction` (+ `.vassal/analysis/jurisdiction.md`, если есть) и примени правило [shared/conventions.md](../../shared/conventions.md) → «Статус вывода о компетенции (F.9)»:

| Что видишь | Что делаешь |
|---|---|
| `confidence: высокая` либо `confirmed_by_user: true` | Обычный ход |
| Ниже высокой **+ готовится первичная подача** (иск / заявление по существу / заявление об обеспечительных мерах -- форум выбираем мы) | **Блок.** К apply не переходить. Покажи вывод о подсудности вместе с его слабым местом и спроси прямо: «Подтверждаешь форум?». «Да» → запиши `case.jurisdiction.confirmed_by_user: true` (**единственное** поле блока `jurisdiction`, которое пишет `prepare-hearing`) и продолжай. «Нет» / сомнение → верни вопрос в `legal-review` на пересмотр компетенции |
| Ниже высокой **+ документ в идущем деле** (отзыв, ходатайство, пояснения -- форум уже определён судом) | **Флаг, не блок.** Громкая пометка в preview + отдельно оцени, не заявить ли о неподсудности самостоятельным доводом |
| `special_norm_checked: false` или поле пусто | Шаг 0 (профильный закон на специальную норму о компетенции) не прогонялся -- вывод неполный независимо от заявленной уверенности. Для первичной подачи -- как «ниже высокой» |
| `case.jurisdiction` пуст (`legal-review` не проводился) | Документ в идущем деле не блокируй; для первичной подачи предложи прогнать `legal-review` -- иначе форум не проверялся вовсе |

2. Прочитай `.vassal/index.yaml` -- полный реестр документов.
3. Загрузи актуальную позицию из корня дела — `* позиция.md`. По правилу архивации (F.12) она там **одна**; сортировать снимки по дате не нужно, а эволюция позиции лежит в `.vassal/analysis/position-*`. Не нашлось в корне → посмотри в `Архив/` и скажи об этом.
3.1. **Загрузи глобальную память** (если есть) -- по правилу из [shared/conventions.md](../../shared/conventions.md) → раздел «Глобальная память (кросс-дельная)». Это даёт Opus-субагенту в фазах 2-3 фон «что у этого судьи и этого оппонента уже наблюдалось в моих прошлых делах»:
   - Разрезолви `$VASSAL_GLOBAL_DIR` **по правилу «Резолв переменной и онбординг (F.26)»** (в PowerShell — `$env:VASSAL_GLOBAL_DIR`; буквальное `$VASSAL_GLOBAL_DIR` там молча даёт пустоту и уводит в fallback даже при заданной переменной). Не задана → fallback `~/.vassal-global/` + разовое уведомление за сессию, не молча.
   - **Каталог образцов (F.22).** Собери имя шарда `samples/{файл по таблице категорий}.yaml` (имя — **строго по таблице** канона → «Каталог образцов» → «Расположение и ключ»; собирать слаг на глаз запрещено: писатель и читатель обязаны получать побайтово одно имя) и найди записи с пересечением по `case.qualification.applicable_norms[]`; при пустых нормах — по `relation_type` + типу готовящегося процдокумента. Показывай найденное **лидом**: «по этим же нормам в деле {номер} был {тип} от {дата} — открыть?». **Текст найденного документа не читать и в работу не втягивать** — канон → «Глобальная память» → «Каталог образцов». Файла шарда нет — работать без, не падать.
   - **Глобальный профиль судьи:** `judges/{ФИО-slug}--{court-slug}.md` -- если файл существует, загрузи. Это критично для подбора аргументации (что заходит судье, что вызывает раздражение) и тактики стресс-теста (как обычно реагирует на наши доводы).
   - **Глобальный профиль оппонента:** `counterparties/inn-{ИНН}.md` (или fallback `noinn-{slug-name}.md`) -- если файл существует, загрузи. Это критично для Red team: типовые доводы оппонента, тактика, известные представители -- модель сразу строит парирование с учётом «уже знакомого» оппонента, а не «нового».
   - Если файлов нет -- работай без глобального фона, не падай.
3.2. **Хук `revise-position` (фильтр отозванного):** прежде чем принять загруженную позицию и `.vassal/analysis/*` / prep-артефакты за истину, прочитай `.vassal/analysis/retractions.md` (если есть) и **исключи** отозванные выводы / факты / практику по правилу из [shared/conventions.md](../../shared/conventions.md) → «Леджер отзывов позиции (revise-position)». Иначе в документ к заседанию попадёт уже отозванный довод из осевшего в служебном слое старого вывода. При наличии замены -- бери новую формулировку из леджера.
3.3. **Хук трекера задач (Asana/Notion) -- штатный опциональный (E.16).** По правилу из [shared/conventions.md](../../shared/conventions.md) → «Чтение трекера задач (Asana/Notion)» подтяни историю работы по делу из трекера Сюзерена -- это может дать почти готовый материал (в бою Asana выдала два прежних отказа по нашему АУ = фактически готовый раздел против него):
   - **Проба коннектора** (feature-detect): короткий `search_tasks` (Asana MCP) / `notion-search` (Notion). Недоступен / не авторизован → **тихий skip** + отметка в `.vassal/`-логе, не блокируя подготовку (в Cowork-сессии без интерактивной auth это норма). Штатно запускается при доступном коннекторе.
   - **Запрос:** по `case.number` (№ дела) + ФИО/наименованиям сторон из `case.parties[]` + ФИО АУ (`parties[]` с ролью «Арбитражный управляющий»). Оба коннектора гейтятся независимо; конфиг (workspace/project) -- только для сужения области.
   - **Находки → в контекст фазы 2** как материал для Red team / Парирования / Blue team.
   - **verify-before-assert (критично):** находка трекера -- **лид, а не установленный факт**. Ссылка на определение / решение из трекера **обязана резолвиться в реальный документ дела** до цитаты в подаваемый документ. Черновь раздел от лида, но помечай «найдено в трекере: {что} -- подтянуть акт в дело (`add-evidence` / `add-opponent`) и сверить перед цитированием»; в суд цитата идёт только с подтверждённым локальным источником. Зафиксируй находки + статус проверки в prep-артефакте §1.

**Шаг 2 -- Доказательства и фактические материалы:**

**Хук `study-evidence` (перед загрузкой зеркал):** проверь `.vassal/analysis/evidence-dossier.md`. Есть — загрузи как приоритетный источник фактуры (факты со ссылкой на лист, кросс-сверка сумм / реквизитов / хронологии); это прямо снимает риск «драфт гладкий, но пустой» (E.3). Нет — предложи Сюзерену (**не блокируя**) собрать досье через `study-evidence` до генерации документа; при отказе работай на зеркалах, отметив «фактура не верифицирована study-evidence».

4. Загрузи md-зеркала ключевых доказательств обеих сторон -- договоры, акты, переписку, платежные документы, акты сверки и т.д.
5. Для каждого документа формулируй мини-задачу: что из него важно для дела (права/обязанности, сроки, нарушения). Связанные короткие документы (1-2 страницы) можно загружать вместе.
6. Загрузи отчеты о предыдущих заседаниях из `.vassal/hearings/` (`{дата}-internal.md`, если есть).
6.1. Загрузи **предыдущий prep-артефакт** из `.vassal/hearings/` -- последний по дате файл `{дата}-prep.md` (если есть). Это база, на которой строилась прошлая подготовка: blue/red team, стресс-тест, аргументация. При обновлении подготовки к новому заседанию его не нужно повторно генерировать -- достаточно обновить по новым документам и фактам. Если файла нет -- стартуем с нуля.

**Шаг 3 -- Процессуальные документы (ПОСЛЕДНИМИ):**
7. Загрузи аналитику оппонента из `.vassal/analysis/opponent-*.md` (если есть).
8. Загрузи процессуальные документы оппонента (иск, отзыв, возражение) -- именно сейчас, когда контекст уже насыщен и агент может критически оценить доводы.
9. Загрузи наши предыдущие процессуальные документы.

### Фаза 2 -- Анализ (Opus-субагент)

> **verify-before-assert** (см. `shared/conventions.md`): и в Blue team, и в Red team опирайся только на сверенные по зеркалам факты/цитаты/практику — предположение о содержании документа не есть установленный факт. В стресс-тесте (фаза 3) разводи **«уязвимость по праву»** (проверяемую рассуждением — выдаёшь как вывод) и **«уязвимость по факту»** (требующую сверки с материалами — выдаёшь как задачу на проверку, не как готовый риск). Зеркало с `needs_manual_review: true` не цитируй в подаваемый документ.

Делегируй Opus-субагенту (model: "opus") глубокий анализ:

10. **Обновление ситуации** -- что изменилось с момента последней позиции:
    - Новые документы (наши и оппонента)
    - Результаты заседаний (если были)
    - Позиция суда (если обозначена)
    - Новые аргументы оппонента

11. **Red team / Blue team анализ:**

    **Blue team** (наши аргументы):
    - Основные доводы в поддержку нашей позиции
    - Доказательственная база для каждого довода
    - Ссылки на нормы и судебную практику

    **Red team** (аргументы оппонента):
    - Что заявил/заявит оппонент
    - Какие наши слабости он эксплуатирует
    - Его доказательства

    **Парирование Red team:**
    - Контраргумент на каждый довод оппонента
    - Доказательства для контраргументов
    - Процессуальные возражения (если применимы)

12. **Структура процессуального документа** -- определить:
    - Вводную часть (кто, что, о чем)
    - Фактические обстоятельства (хронология с доказательствами)
    - Правовое обоснование (нормы + практика)
    - Ответ на доводы оппонента (если это ответный документ)
    - Просительная часть (что просим у суда)
    - Приложения (список документов для приобщения)

13. **Стратегическая оценка:**
    - Оценка перспектив: стоит ли продолжать спор или выгоднее мировое соглашение
    - Если анализ показывает слабую позицию -- сообщить Сюзерену прямо, предложить альтернативные стратегии (мировое, минимизация последствий)

    **Хук на `settlement`-трек** -- условный, не блокирующий. После того как фаза 2 завершена, проверь три триггера для предложения параллельного запуска [`/vassal-litigator:settlement`](../../commands/settlement.md):

    a) **Слабая позиция по результатам blue/red team в п. 11.** Если в финальной оценке risks выше strengths -- предложи:
       > «По результатам анализа позиция в споре оценивается как слабая ({краткое summary рисков}). Рассмотреть переход в settlement-трек -- подготовка отказа от иска / признания иска / мирового соглашения? Если да -- запусти `/vassal-litigator:settlement`; этот скилл проведёт трёхстороннюю оценку зоны компромисса (BATNA / zone of agreement / прогноз оппонента) и подготовит проекты документов. Запуск settlement не отменяет подготовку к заседанию -- treks параллельные.»

    b) **Активный settlement-трек в карточке.** Прочитай `case.settlement.in_progress` из `case.yaml`. Если `true` -- предложи:
       > «По делу активен settlement-трек (`mode={case.settlement.mode}`, начат `{case.settlement.draft_date}`). К заседанию готовим документ для спора, но settlement подразумевает иной фокус. Уточни:
       >    - продолжать prepare-hearing в полном объёме (документ для спора + settlement остаётся параллельным треком);
       >    - переключиться на подготовку к заседанию **утверждения мирового** (если на заседании ожидается утверждение settlement -- логика другая, фактически нужен запуск `/vassal-litigator:settlement` в режиме фиксации, не обычный prepare-hearing);
       >    - приостановить settlement в `case.yaml` и сосредоточиться на споре.»

    c) **Явное упоминание мирового Сюзереном** в `$ARGUMENTS` команды prepare-hearing (ключевые слова: «мировое», «уступим», «выйдем на мировое», «откажемся от иска», «признаём»). Если упомянуто -- предложи:
       > «В аргументах команды упомянуто {ключевое слово}. Подготовка трека примирения -- это отдельный скилл `/vassal-litigator:settlement`. Хочешь запустить его параллельно с prepare-hearing или вместо?»

    Хук **не блокирующий**: prepare-hearing продолжает фазу 3 в любом случае. Решение о запуске settlement -- Сюзерена. Факт срабатывания одного из триггеров фиксируй в сводном файле prepare-hearing как пометку «Триггер settlement-хука сработал: {какой}; Сюзерен решил: {ответ}».

    > Подробности логики settlement-трека -- [skills/settlement/SKILL.md](../settlement/SKILL.md). Settlement и prepare-hearing -- параллельные треки, settlement не дублирует подготовку к спору, prepare-hearing не дублирует подготовку к компромиссу. См. [ARCHITECTURE.md](../../ARCHITECTURE.md) §9 «Ответвления (примирительный трек)».

Каждый вывод -- в аудируемом формате (см. `shared/conventions.md`).

### Фаза 3 -- Стресс-тест (отдельный обязательный шаг)

> "Стресс-тест -- это не просто часть анализа. Это отдельный шаг, в котором мы атакуем собственный документ, чтобы найти уязвимости до того, как это сделает оппонент." -- Мошкин С.А.

Стресс-тест проводится ПОСЛЕ формирования структуры документа, но ДО написания финального текста. Две стороны проверки — и они делаются **разными головами**: атака (a) — **отдельным субагентом**, усиление (b) — основным потоком.

**a) Критический подход (атака) -- отдельным Opus-субагентом** (канон [shared/conventions.md](../../shared/conventions.md) → «Red team отдельным субагентом»). Прежде эту атаку вёл **тот же** субагент, что в фазе 2 строил blue team и парирование — то есть модель критиковала собственную работу (consistency bias). Теперь атака делегируется независимо:
- **Делегируй отдельному Opus-субагенту** (`model: "opus"`) с системным промптом: «Ты юрист процессуального оппонента. Перед тобой структура нашего документа и материалы дела. Разбей нашу позицию: какие контраргументы дашь первым, какие уязвимости в аргументации эксплуатируешь, какие расхождения в документах (даты, суммы, имена, последовательность событий) используешь против нас. **Не имей доступа к нашему blue team и парированию из фазы 2 — работай только со структурой документа и первоисточниками.**»
- **Вход субагента:** структура документа (из п. 12) + процессуальные документы оппонента + сверенные зеркала фактов. **Не передавай** наш blue team, парирование и стратегическую оценку (п. 11, 13).
- **Реальный оппонент (приём из `cassation`):** если загружен глобальный профиль оппонента (фаза 1) — передай, чтобы атака шла с позиции конкретного противника.
- Для каждого расхождения субагент указывает: где содержится, с чем бьётся, насколько существенно, как оппонент это использует.
- **verify-before-assert сохраняется:** разводи «уязвимость по праву» (проверяемую рассуждением) и «уязвимость по факту» (требующую сверки с материалами — выдаётся как задача на проверку, не как готовый риск).

**b) Усиление позиции -- основной поток** (не субагент: усиление — конструктивная работа над нашим документом после получения атаки, свойство канона — в red-team-субагент её не втягивать):
- Поиск дополнительной аргументации
- Предугадывание контраргументов и подготовка ответов на них
- Поиск новых трактовок фактов и событий
- Улучшение структуры аргументации: самый сильный довод -- первым

    - Найденные уязвимости (ранжированные по опасности)

## Идемпотентность

Режим — **новый датированный снимок** (`shared/conventions.md` → «Идемпотентность»).

- **Тип артефакта = тип процессуального документа.** Отзыв на иск, ходатайство об отложении, пояснения — **разные типы**: они друг друга не вытесняют, каждый держит в корне свою последнюю версию.
- **Архивация своего типа при apply.** Перед записью нового снимка уведи предыдущий снимок **того же типа процдокумента** в `Архив/` (`mkdir -p`, затем `mv`) — **вместе с парным `.docx`** и его `_v2`-версиями, если они были. Уводить `.md`, оставив `.docx`, нельзя: юрист прочитает осиротевший `.docx` как актуальный. **Запись в индексе едет вместе с файлом:** обнови `file:` на путь в `Архив/`. Автосвязка по `content_hash` здесь не сработает — `Архив/` в игнор-списке скана, файл не всплывёт как «новый»; не обновить = осиротевшая запись и предложение «удалить из индекса» по живому документу.
- **Чужие типы не трогать.** Позиция, апелляционная и кассационная жалобы, проект решения (оба режима), досье, предварительный анализ, карта доводов — продукты других скиллов и штатный вход соседних; `prepare-hearing` их не архивирует.
- **Отдельно: продукты `settlement` и `analyze-hearing` — тоже чужие**, хотя формально это «процессуальные документы» и под шаблон моей строки в таблице типов подпадают. `* Ходатайство об утверждении мирового соглашения.md`, `* Заявление об отказе от иска.md`, `* Заявление о признании иска.md`, `* Замечания на протокол.md` имеют **собственные фиксированные строки**, а конкретная строка бьёт шаблонную (`shared/conventions.md` → «Правило приоритета строк»). Если я готовлю документ с таким именем — он принадлежит той строке, и архивирую я снимок **по ней**, а не по своей.
- **Изменений нет → снимка нет.** Если документ содержательно совпал бы с предыдущим — новый файл не создавай и ничего не архивируй; скажи Сюзерену, что изменений нет.
- **`.vassal/hearings/{дата}-prep.md` не архивируется** — служебная зона остаётся на месте целиком: `analyze-hearing` читает prep-артефакт после заседания («что готовили» vs «что произошло»), а `cassation` — при повторном заходе.
- Повторный прогон в ту же дату при **изменившемся** содержании → суффикс `-{ЧЧММ}`, предыдущий снимок в `Архив/`.

## Постусловия

Перед завершением `apply` Opus-субагент сверяется с чек-листом из [shared/conventions.md](../../shared/conventions.md) → «Постусловия скиллов». `prepare-hearing` относится **одновременно к двум категориям**: 2 (аналитическая, при сохранении prep-артефакта) и 3 (document-producing, при создании процдокумента). Минимум:

- `.md` процессуального документа создан в корне дела по шаблону из «Продукты плагина».
- `.docx` создан через `format-doc` (`python-docx`) ИЛИ при его недоступности -- `.md`-fallback с явным предупреждением Сюзерену (по шаблону раздела «Внешние зависимости и fallback»); `arbitrum-docx` -- опц. альтернатива.
- **`*-prep.md` создан в `.vassal/hearings/`** со всеми 7 разделами. Если какой-то блок пропущен (например, стратегическая оценка не давалась) -- явно `not_applicable: <причина>` во frontmatter и одна строка в теле.
- Чек-лист просительной части пройден (или явно отмечены пропущенные пункты), результат продублирован в `*-prep.md` §6.
- Приложения перечислены в самом процдокументе и связаны с `index.yaml` через двойные ссылки.
- Запись в `.vassal/history.md` зафиксирована -- с именами `.md`, `.docx`, `*-prep.md` и состоянием fallback.

## Типы процессуальных документов

| Тип | Когда | Особенности |
|-----|-------|-------------|
| Отзыв на исковое заявление | ответчик отвечает на иск | Структура: возражения по каждому требованию |
| Возражение на отзыв | истец отвечает на отзыв ответчика | Контраргументы на доводы отзыва |
| Ходатайство | любая сторона просит суд | Четкая просительная часть, правовое обоснование |
| Письменные пояснения | по запросу суда или инициативно | Разъяснение позиции по конкретным вопросам |
| Дополнение к позиции | новые аргументы / доказательства | Акцент на том, что нового |
| Заявление | процессуальное действие | Конкретная просьба (приобщение, отвод, отложение) |

**Банкротные обособленные споры** (профиль `category = банкротство`) -- иная номенклатура:

| Тип | Когда | Особенности |
|-----|-------|-------------|
| Заявление о включении требования в реестр | кредитор заявляет требование | Очередь + разделение долг / финсанкции; повышенный стандарт реальности; см. банкротный чек-лист просительной |
| Возражения на требование кредитора | оспаривание чужого требования | Против реальности / размера / очереди; повышенный стандарт к заявителю требования |
| Жалоба на действия (бездействие) АУ (ст. 60) | нарушение прав действиями АУ | Какое действие / бездействие незаконно + что обязать; зеркально -- защита АУ |
| Заявление об оспаривании сделки (гл. III.1) | вывод активов должника | Состав ст. 61.2 / 61.3 + период подозрительности + последствия (реституция) |
| Заявление о привлечении к субсидиарной / о взыскании убытков (гл. III.2) | доведение до банкротства | Статус КДЛ + презумпции (ст. 61.11 / 61.12) / убытки ст. 61.20 |

Глубина составов: **включение в реестр** -- [bankruptcy-claim-registration.md](../build-position/references/bankruptcy-claim-registration.md); **ответственность и защита АУ** -- [bankruptcy-manager-liability.md](../build-position/references/bankruptcy-manager-liability.md); **оспаривание сделок III.1** -- [bankruptcy-transaction-challenge.md](../build-position/references/bankruptcy-transaction-challenge.md); **субсидиарка/убытки III.2** -- [bankruptcy-subsidiary-liability.md](../build-position/references/bankruptcy-subsidiary-liability.md) (C).

> **По оспариванию сделок справочник читается ДВАЖДЫ.** Первый раз -- здесь, на квалификации состава. Второй -- при подготовке самого документа: [bankruptcy-transaction-challenge.md](../build-position/references/bankruptcy-transaction-challenge.md) несёт процессуальный регламент обособленного спора, которого нет больше нигде в плагине. Что брать: **§16.2** -- форма заявления и кому направляются копии (типовая ошибка -- не разослать ответчику и АУ); **§16.4** -- состав лиц и извещение внешнего ответчика; **§16.5** -- три изъятия из АПК (предварительного заседания нет); **§16.6** -- резолютивная часть и зеркальный чек-лист отзыва; **§16.7** -- маршрут обжалования; **§16.9** + **§14.6** -- обеспечительные меры, в том числе в наблюдении; **§16.10** -- составная госпошлина по развилке «с последствиями / без последствий»; **§13.2** -- обязательное предложение о добровольном возврате ДО подачи (без него ответчик гасит спор возвратом, а заявитель теряет п. 2 ст. 61.6); **§14.9** -- чек-лист права на подачу до сбора доказательств; **§15.10** -- самопроверка по давности. Адресная разбивка -- Приложение Б.2 того же файла.

## Чек-лист просительной части процессуального документа

Просительная часть -- самая частая зона ошибок: пропущенные суммы, неверная солидарность, забытые проценты «по день фактической оплаты», непросуженные расходы. Перед apply Opus-субагент **обязан** прогнать просительную часть по чек-листу. Чек-лист зависит от типа документа **и профиля дела** (Фаза 1.1): исковой профиль → разделы «Для иска / отзыва / ходатайства / судрасходов» ниже; **банкротный профиль → раздел «Для банкротных обособленных споров»** ниже.

**Сверка приложений и сумм (заявлено vs вложено).** Перед apply сверь: перечень приложений в документе -- с фактически собранными файлами (у каждого приложения есть файл; тип/содержание соответствует описанию); число и реквизиты единиц (платёжки и т.п.) -- с извлечёнными из файлов-доказательств; итоговые суммы -- пересчётом. Расхождение → явный флаг Сюзерену и `needs_manual_review`, не подавать до сверки.

### Для иска / встречного иска / уточнения иска

1. **Состав требования полностью раскрыт:**
   - Основной долг -- точная сумма с указанием валюты.
   - Неустойка -- сумма на дату подачи **+ формула «по день фактической оплаты»** (если применимо), с указанием базы и ставки (договорная / ст. 395 ГК / ст. 332 ГК).
   - Проценты по ст. 395 ГК -- с расчётной формулой и периодом начисления. Знаменатель -- **фактическое число календарных дней в году (365 или 366)**: правило «год = 360 дней» отменено п. 84 ППВС ВС РФ № 7 от 24.03.2016, жёсткий делитель 365 в високосном году даёт неверную сумму.
     **Дата начала, ставка, разбивка периода, поведение при недоступности источника -- по канону** [shared/conventions.md](../../shared/conventions.md) → «Расчёт денежных требований: дата начала и ставка (F.10)». Оттуда же точные адреса базы ЦБ. Ключевое, что нельзя терять при подготовке просительной части: **дата начала -- это выбор**, и Сюзерену показываются варианты **с ценой каждого** (боевая цена молчаливого выбора -- недозаявленные 1,14 млн ₽); ставка -- со значением, датой начала действия и источником; период с несколькими ставками разбивается.
   - Убытки -- с разложением (реальный ущерб / упущенная выгода) и доказательственной поддержкой.
2. **Несколько должников:**
   - Явно указано «солидарно» / «в долях» (с указанием долей) / «субсидиарно» (с указанием основного должника).
   - При солидарной ответственности -- ссылка на основание (ст. 322 ГК для договорной, ст. 1080 ГК для деликтной).
3. **Госпошлина:**
   - Сумма пошлины указана точно.
   - При снижении (льготы, рассрочка) -- ходатайство приложено.
   - **При частичном удовлетворении** -- проверить пропорциональность распределения.
4. **Судебные расходы:**
   - Расходы на представителя -- сумма с приложением договора и подтверждающих документов.
   - Расходы на эксперта / переводчика / нотариуса -- если применимо.
5. **Обеспечительные меры** -- если требуются, отдельным заявлением с обоснованием по ст. 90 АПК / ст. 139 ГПК.

### Для отзыва на иск / возражения

1. **По каждому требованию истца -- явный ответ:**
   - Признаём (с указанием в какой части и в какой сумме) ИЛИ
   - Не признаём (со ссылкой на основание возражения).
2. **Если есть встречные требования** -- они подаются отдельным иском (встречный иск), не в просительной отзыва.
3. **Просительная часть отзыва:** «отказать в удовлетворении исковых требований полностью / в части N» с указанием конкретных пунктов резолютивной требований истца.
4. **Расходы на представителя** -- если ответчик планирует их взыскать в случае отказа в иске, заявить **до окончания рассмотрения дела по существу** (п. 28 Постановления Пленума ВС РФ от 21.01.2016 № 1).

### Для ходатайства

1. **Конкретная просьба** -- одна или несколько чётких просьб, без рассуждений в просительной части.
2. **Правовое основание** -- ссылка на норму, дающую право заявить такое ходатайство (ст. 159 АПК, конкретные статьи по типу: 64 АПК для приобщения доказательств, 144 АПК для отложения, 21-26 АПК для отвода).
3. **Перечень документов, прилагаемых к ходатайству** -- если есть.
4. **Для ходатайства о приобщении доказательств** -- обоснование относимости и допустимости + почему не было представлено ранее (если поздняя стадия).

### Для заявления о судебных расходах (после вынесения решения)

1. **Точная сумма** -- по каждому виду расходов отдельно.
2. **Подтверждающие документы** -- договор с представителем, акты выполненных работ, платёжные документы; при экспертизе -- договор и квитанция; при нотариусе -- квитанция.
3. **Срок** -- 3 месяца со дня вступления в силу последнего судебного акта (ст. 112 ч. 2 АПК).
4. **Разумность размера** -- обоснование (объём работы, категория сложности дела, ставки в регионе).

### Для банкротных обособленных споров (профиль `category = банкротство`)

Строится **как дельта к исковому чек-листу выше** -- не с нуля. По типу документа:

**Включение требования в реестр / возражения на требование:**
1. **Просительная -- «включить в реестр требований кредиторов {должник} в составе {N} очереди»** (НЕ «взыскать»). Очередь -- ст. 134 / 137 (вторая -- выплаты работникам; третья -- основная; залоговые -- ст. 138).
2. **Раздели основной долг и финансовые санкции** -- неустойка / пени / штрафы учитываются в реестре отдельно (п. 3 ст. 137), голоса не дают; не суммируй с основным долгом в одной строке.
3. **Мораторные проценты** -- после введения процедуры договорная неустойка / ст. 395 ГК не начисляются; вместо них -- мораторные проценты. Не проси договорную неустойку за период после введения процедуры.
4. **Состав требования** (основной долг + проценты до даты введения процедуры) -- по исковому чек-листу выше (точные суммы, формулы, валюта; прописью -- опционально, E.9).
5. Повышенный стандарт доказывания реальности (особенно аффилированный кредитор) -- это блок **доказывания** (фазы 2-3), НЕ просительная часть.
6. Глубина состава (очередь, мораторные проценты, повышенный стандарт, субординация аффилированного заявителя) -- [bankruptcy-claim-registration.md](../build-position/references/bankruptcy-claim-registration.md).

**Жалоба на действия (бездействие) АУ (ст. 60):**
1. Просительная -- «признать незаконными {действия / бездействие} арбитражного управляющего {ФИО}, выразившиеся в {...}» + при необходимости «обязать устранить {...}».
2. Конкретизируй: какая обязанность АУ нарушена (ст. 20.3 / специальные) и чем именно нарушены права заявителя.
3. Зеркально (защита АУ) -- [bankruptcy-manager-liability.md](../build-position/references/bankruptcy-manager-liability.md), раздел 4.

**Оспаривание сделки (III.1) / субсидиарка / убытки (III.2):**
1. Просительная -- «признать недействительной сделку {...} + применить последствия (реституция / восстановление требования)» / «привлечь {КДЛ} к субсидиарной ответственности» / «взыскать убытки (ст. 61.20)».
2. Просительная по оспариванию сверяется по **§16.6** [bankruptcy-transaction-challenge.md](../build-position/references/bankruptcy-transaction-challenge.md) -- готовый чек-лист из девяти позиций (момент оценки стоимости, проценты, зачёт, цепочка, третьи лица, обеспечительные, расходы) плюс зеркальный чек-лист отзыва: что ответчик обязан заявить **в первой инстанции**, иначе довод теряется. По п. 29 Пленума № 63 суд применяет последствия и без просьбы заявителя, но в §16.6 объяснено, почему полагаться на это нельзя -- просительную часть пишем полностью. Пошлина по такому заявлению составная, **§16.10**.
3. Состав -- маркеры: период подозрительности (ст. 61.2 / 61.3) -- глубина [bankruptcy-transaction-challenge.md](../build-position/references/bankruptcy-transaction-challenge.md) (B); статус КДЛ + презумпции доведения до банкротства (ст. 61.10 / 61.11 / 61.12) либо локальный вред (убытки ст. 61.20 / ст. 53.1 ГК) -- глубина [bankruptcy-subsidiary-liability.md](../build-position/references/bankruptcy-subsidiary-liability.md) (C). Для субсидиарки/убытков: при недоказанности размера до окончания расчётов -- просить определение об основаниях + приостановление (п. 7 ст. 61.16).

### Универсальные требования к просительной части любого документа

- Никаких «решить дело по справедливости / по закону / на усмотрение суда» -- такие фразы делают документ непрофессиональным.
- Суммы -- **цифрами**; дублирование **прописью НЕ требуется** (решение Сюзерена 2026-06-30, E.9): это **не** пункт чек-листа и **не** блокирует его прохождение. Согласовано с `format-doc`, который и так убирает суммы прописью из `.docx` (`format-doc/references/style-spec.md`). При коллизии чек-листа и типографики/стиля приоритет -- у **стиля / решения Сюзерена**.
- Полное наименование сторон с ИНН/ОГРН для юрлиц, ФИО + дата рождения для физлиц.
- В исках -- цена иска (для расчёта пошлины).

**Постусловие** (см. [shared/conventions.md](../../shared/conventions.md) → «Постусловия скиллов» категория 3): после генерации текста Opus-субагент сверяет просительную часть с чек-листом выше и в Preview явно отмечает: «Чек-лист пройден / пропущенные пункты: ...». Без явного прохождения чек-листа не переходить к шагу подтверждения Сюзереном.

## Приоритеты в аргументации

Порядок расположения аргументов:
1. Самый сильный довод -- первым (суд читает внимательно начало)
2. Ответ на самый опасный аргумент оппонента -- вторым
3. Остальные доводы -- по убыванию силы
4. Процессуальные аргументы -- в конце (если есть)

## Работа с профилем судьи

**Источники профиля по приоритету:**

1. **Глобальный профиль** -- `$VASSAL_GLOBAL_DIR/judges/{ФИО-slug}--{court-slug}.md` (загружается в фазе 1 шаг 3.1, если есть). Накопительный по всем твоим делам с этой парой (судья × суд) -- содержит устные паттерны (от `analyze-hearing`) и письменный стиль решений (от `draft-judgment`). **Главный источник** для подгонки структуры документа и тона под предпочтения судьи: что заходит, что отвергает, какие триггеры.
2. **Локальный профиль** -- `.vassal/hearings/judge-profile.md` текущего дела (если есть). Накопительный только по этому делу. Дополняет глобальный наблюдениями, специфичными именно для этого спора (например, как судья реагирует на конкретных свидетелей по этому делу).
3. **Решения судьи, предоставленные Сюзереном** ad-hoc -- 3-5 решений по аналогичным делам, если глобальный/локальный профили пусты или Сюзерен хочет «свежий» анализ. Тогда нужно проанализировать стиль (структурные и стилистические особенности вводной, мотивировочной, исследования доказательств, резолютивной) и подход к применению норм. Этот разовый анализ не сохраняется автоматически в профиль -- если Сюзерен хочет накопить, отдельно запускается `draft-judgment` (он пишет в judge-profile, локальный + глобальный).

**Как использовать в подготовке:**
- Адаптировать структуру и стиль процессуального документа под предпочтения судьи.
- Учесть, какие аргументы у этого судьи обычно «работают», какие -- мимо.
- В стресс-тесте (фаза 3) -- учесть «как судья обычно реагирует на наши доводы» (что переспрашивает, что отбрасывает) при поиске уязвимостей.

## Копирование стиля (опционально)

Если Сюзерен загрузил образец документа как эталон стиля:
- Проанализировать структуру, формулировки, способ изложения
- Генерировать новый документ максимально близко к этому стилю
- Сюзерен получает документ, который выглядит как его собственный
